# 1.5.0 App Store Connect brief — upload the store page and verify it

**Status: written 2026-11-23 in the owner's planning chat; not started.**
For an agent working in this repository and through the App Store Connect
API (as Codex did for 1.4.0: `docs/1.4.0-asc-brief.md`,
`screenshots/1.4.0/asc/`, `tool/marketing/store_130/asc_execute_140.cjs`,
`asc_replace_header_140.cjs`; reuse their JWT, upload and read-back code).

**Goal:** the 1.5.0 version in App Store Connect carries build 8, the new
store texts in eight languages, the new iPhone and iPad screenshots, the new header
image and the new Notes for Review; then every field is read back and
compared with the sources below. **The owner submits for review himself.**

## 0. Rules

1. **Never submit.** No `reviewSubmissions` item, no submission endpoint,
   no release. The version stays `PREPARE_FOR_SUBMISSION`, release type
   `MANUAL`.
2. **Never touch 1.4.0** (live, `READY_FOR_SALE`) or any older version:
   every write goes to the 1.5.0 version and its localizations, or to the
   header placements of 1.5.0.
3. No change to prices, subscriptions, in-app purchases, territories,
   availability (Mac and Apple Vision stay as they are), the age rating,
   App Privacy, the app name, the subtitle, the keywords, the promotional
   text, the URLs, or the App Review contact details.
4. **Credentials:** the key ID, the issuer ID and the `.p8` path are given
   by the owner in the prompt. Read the key from that path at run time.
   Never print the key or a token, never copy the key, never write any of
   the three into a file in the repository, a log, a commit or a report.
   Run logs go outside the repository (as in 1.4.0:
   `~/Pictures/GrammarLens/1.5.0-asc/<date>/`), method, path and status
   only.
5. Delete only inside the 1.5.0 version, and only what §3 names.
6. No change under `lib/`, `ios/`, `proxy/`, `test/`, and no build.
7. Git: stage exact paths, small commits, no force push, no history
   rewrite. Commit what §6 lists; **do not commit any image under
   `screenshots/1.5.0/`** (the owner decides later what to keep).
8. **One stop:** after the dry run (§2) stop and wait for the owner's
   "OK". Everything after it runs without stopping unless something fails.

## 1. Sources (read, do not rewrite)

  tr, de-DE, es-MX, pt-BR, ja, ko, ar-SA; same shape as
  `screenshots/1.4.0/asc/metadata.json`). Readable copy:
  `docs/1.5.0-store-texts.md`. Upload `description` and `whatsNew` exactly
  as written. `subtitle`, `keywords`, `promotionalText`, `supportUrl`,
  `privacyPolicyUrl` in that file equal 1.4.0's: do not write them, only
  read them back and compare.
- **Notes for Review:** `docs/1.5.0-review-notes.txt`, exactly as written
  (3,977 characters; the limit is 4,000).
- **iPhone 6.9" screenshots:** `screenshots/1.5.0/revizyon-11/<lang>/iphone-6.9/`,
  six PNGs per language, 1320 × 2868, in file-name order 01 → 06.
  Folder → locale: `en` → en-US, `tr` → tr, `de` → de-DE, `es` → es-MX,
  `pt-BR` → pt-BR, `ja` → ja, `ko` → ko, `ar` → ar-SA. (Turkish file

- **Header image:** `screenshots/1.5.0/revizyon-11/product-page/header.png`

Before anything else, check every source: the JSON parses and has the
eight locales; each `description` and `whatsNew` is at most 4,000
characters; 48 iPhone PNGs, each 1320 × 2868, and 48 iPad PNGs, each
2064 × 2752, all RGB without alpha (report any with alpha; do not convert
without saying so); the header is 3840 × 1646. (Checked in the planning
chat on 2026-11-23: all 96 and the header match; check again, the files
may have changed.) Record the size and SHA-256 of every file for the dry run.

## 2. Read first, then the dry run (no writes)

1. The app id (`bundleId` `com.ahmettayfur.grammarlens`).
2. The app's iOS versions: 1.4.0 `READY_FOR_SALE`; is there a 1.5.0?
   - If none: plan `POST /v1/appStoreVersions` (iOS, `1.5.0`, `MANUAL`).
   - If 1.5.0 exists: its state must be `PREPARE_FOR_SUBMISSION`; anything
     else, stop and report.
3. Build 8 of 1.5.0: `VALID`, its id; is it already attached?
4. For 1.5.0 (or, if it does not exist yet, for 1.4.0 read-only, since a
   new version copies from it): every version localization and its
   fields; every screenshot set (display type, count, file names) per
   locale; the header placements; the App Review details (notes, contact,
   demo account flag, attachments).
5. Write the dry run to `screenshots/1.5.0/asc/dry-run.md` (text only, no
   images): every request in order with its body (no credentials),
   which records are read, created, changed or deleted, and a table per
   locale of the planned final state. Stop and wait for the owner.

## 3. Execute (after the owner's OK)

**Version and build**
1. Create 1.5.0 if it does not exist (§2.2). Read it back.
2. Attach build 8 (`PATCH /v1/appStoreVersions/{id}/relationships/build`).

**Texts (eight locales)**
3. On each 1.5.0 version localization: `PATCH` `description` and
   `whatsNew` from the JSON. If a locale is missing, `POST` it with every
   version field from the JSON (description, keywords, whatsNew,
   promotionalText, supportUrl). If an existing record conflicts (409),
   read its id and `PATCH` instead.
4. App Review details of 1.5.0: `notes` = the review notes file. Leave the
   contact details and the demo account setting as they are. **Attachments**
   (1.4.0 carried a screen recording of 1.3.0): do not delete; list them
   in the report for the owner.

**Screenshots: iPhone 6.9" and iPad 13" (eight locales)**
5. In each locale's iPhone 6.9" set of 1.5.0: remove the placements that
   came from 1.4.0 (eight), never the library assets behind them; upload
   the six new files (reserve → upload parts → commit with MD5 → poll
   until `COMPLETE`; stop on `FAILED`); set the order 01 → 06. If the set
   is missing, create it with the display type 1.4.0 used (read it, do not
   guess).
6. The same for each locale's iPad 13" set: remove the six placements
   copied from 1.4.0 and upload the six new iPad files, order 01 → 06.
   96 uploads in all (48 iPhone, 48 iPad).
7. Any other display type found in 1.5.0 (for example a copied 6.3"
   set): report it, change nothing.

**Header**
8. Upload `header.png` once to the asset library and place it on the
   eight 1.5.0 localizations, replacing the placements copied from 1.4.0
   (the 1.4.0 method: `asc_replace_header_140.cjs`,
   `screenshots/1.4.0/asc/header-v5-plan.json`). Keep the old library
   image. If the API cannot do it, report it; the owner uploads it in the
   web interface.

## 4. Verify — read everything back

Read the 1.5.0 version from the API after the last write and compare it,
field by field, with the sources. Write `screenshots/1.5.0/asc/read-back.md`
(and the raw `read-back.json`, no credentials):

- **Version:** 1.5.0, state, release type `MANUAL`, build 8 attached and
  `VALID`.
- **Per locale (eight rows):** `description` and `whatsNew` equal to the
  JSON (exact string match; on a mismatch show the first differing
  character); `keywords`, `promotionalText`, `supportUrl` equal to the
  JSON (unchanged); `subtitle`, `name`, `privacyPolicyUrl` on the
  app info equal to the JSON (unchanged); iPhone 6.9": six screenshots,
  in order, each `COMPLETE`, file names and checksums equal to the
  sources; iPad 13": six screenshots, the same checks; no screenshot
  left from 1.4.0 in either set; any other set; the header placement and
  its image id.
- **App Review:** notes equal to the file (exact); contact unchanged;
  attachments listed.
- **Untouched:** 1.4.0 still `READY_FOR_SALE` with its own screenshots
  and texts (counts only); age rating, App Privacy, prices, availability
  not written to (from the run log: no write requests to them).
- A summary at the top: **passed** or **failed**, with every difference.

## 5. Report to the owner

In plain English, short: passed or failed; what was created, changed and
removed; the attachment note; anything the owner must still do
in the web interface before he presses Submit (for example the header if
the API could not place it, the export compliance question if App Store
Connect asks it, App Privacy's "no change" confirmation).
