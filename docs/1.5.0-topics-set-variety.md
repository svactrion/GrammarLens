# Topic Practice: making two sets of one topic differ (proposal)

**A proposal, not a change.** Written 2026-11-18 for phase C of
[`TOPICS.md`](TOPICS.md), step 5. Nothing here is built, no prompt was
changed, nothing is deployed. The owner decides.

## The problem, as measured

From [`1.5.0-topics-report.md`](1.5.0-topics-report.md) (the owner's run of
2026-11-18, six sets per new topic):

- Questions that resemble a question of another set of the same topic:
  Conditionals 15 of 30, Prepositions 11, Relative Clauses 7, Comparatives &
  Superlatives 7, Passive Voice 2; the control (Articles, three sets) 0 of
  15. No pair is inside a set: a set is varied in itself, the sets repeat
  each other. In Conditionals one group of five resembling questions reaches
  into five of the six sets.
- The cause is in the request, not in the topic. The app sends `deviceId`,
  `topicId` and `count`. The Worker uses the device id for the quota only and
  builds the model's request from the topic's fixed title and description and
  the count. Two requests for one topic and length are the same request,
  byte for byte: no seed, no earlier question, no list to avoid. Only the
  model's sampling makes two sets differ, and it starts from the same place
  every time.
- It is true of the five live topics too: they go through the same request.
  The control showed no resembling pair in three sets, which is too few sets
  to say the live topics are free of it.
- The shared Daily Test does not have the problem, because its request has
  two inputs Topic Practice lacks: a scenario theme for the day (14 themes
  in turn, approved by the owner on 2026-09-26) and the answers of recent
  days to stay away from.

What a learner sees today: a second session on a topic can bring back a
scenario, and now and then a whole question, from the first.

## What any option has to respect

- **The client sends ids, never text.** The Worker takes a `topicId` and
  looks the topic's text up in its own table, so nothing a client sends can
  reach the prompt (`proxy/src/topics.ts`). An option that puts client-sent
  sentences into the prompt gives that up.
- **Old app versions keep working.** A released app sends the three fields
  it sends today.
- **The legal pages follow the data.** A new field sent, or something new
  kept on the server, is a change to review there (the `product.yaml` rule).
- **A changed request is a new thing to measure.** The generation request of
  the five live topics has been measured as it is (1.4.0); a line added to it
  changes all ten topics.

## Option A — the Worker gives each set a scenario theme

The Worker picks a theme for the request and adds one line to the user
prompt, as the shared Daily Test does: set every item in a different
everyday situation within that theme.

- **Which theme.** Two ways, the same for everything below:
  - *At random* from the list. Simplest. One learner still meets a theme
    again soon: with 14 themes, six sets share at least one theme in about
    seven cases of ten.
  - *Stepped*, from what the Worker already has at hand: the day and the
    device's request count for the day, which the quota check reads anyway.
    Consecutive requests of one device then get different themes, nothing is
    stored and nothing new is sent. This is a sketch; the exact stepping
    rule is a detail to settle when it is built.
- **The list.** The Daily Test's 14 themes can be reused as they are
  (already approved). A longer list widens the space; it is content for the
  owner to approve.
- **App:** nothing. Every installed version gets it the day the Worker is
  deployed.
- **Worker:** the choice of theme and one line in the practice request
  (`buildGeneratePracticeSetBodyFor`); tests.
- **Prompt:** one line in the user prompt. The system prompt stays as it is.
- **Cost per set:** about 25 more input tokens, about $0.00005 on a set that
  measured $0.0078 (under 1 %).
- **New data sent:** none. The legal pages are not touched.
- **The five live topics:** yes, all ten topics, since they share the
  request.
- **New measurement:** yes, a small one. Whether sets still repeat is
  answered by the automatic duplicate check with no labels: generation only,
  for example six sets of each of the ten topics, 60 calls, about $0.47 at
  this run's price per set. Whether the questions stay as good with a theme
  imposed is a quality question; the 1.4.0 measurement and this one are the
  baselines, and how large a labelled sample to ask for is the owner's call.
- **What it does not do.** It varies the scenario, not the grammar point. Two
  sets can still test the same mistake in different settings (which is
  practice, not repetition), and within one theme two sets can still land on
  the same situation.

## Option B — the app remembers its recent themes and names them

Option A, plus a memory on the device. The Worker returns the id of the
theme it used with the set; the app keeps the last few per topic and sends
them back as a list of ids to leave out; the Worker draws from the rest.

- **App:** a new release. It stores the last themes per topic on the device
  and sends one new optional field. Only users on the new version get the
  memory; older versions get option A's behaviour.
- **Worker:** accepts the optional list (ids from its own table, bounded
  length, anything else refused), returns the theme's id with the set.
- **Prompt:** the same one line as option A.
- **Cost per set:** as option A.
- **New data sent:** yes, small: which themes a device recently had for a
  topic. Ids only, used for the draw and not stored by the Worker. It is
  derived from the learner's history, so the legal pages need a look, likely
  one sentence.
- **The five live topics:** yes.
- **New measurement:** the same as option A; the memory itself is logic that
  unit tests cover.
- **What it adds over A:** a guarantee, per learner and topic, that a theme
  does not come back within the last few sets. Whether that is needed is
  only known once option A has been measured.

## Option C — the Worker remembers each device's recent themes

Option A, plus a memory on the server: the Worker keeps the last themes per
device and topic in its key-value store and draws from the rest.

- **App:** nothing; every version gets the memory.
- **Worker:** one more read and one more write per practice request, a
  retention period, tests.
- **Prompt and cost per set:** as option A. The store's writes are free
  within the plan's daily limit, which the quota counters already draw on
  (two writes per request today); the limit has to be checked before this is
  built.
- **New data:** nothing new is sent, but something new is **kept**: today the
  server holds one counter per device and day for two days; this would hold
  which themes a device practised, for longer. The legal pages need a look,
  and it is the less private of the two memories.
- **The five live topics:** yes.
- **New measurement:** as option A.

## Looked at and set aside

- **Sending recent questions as text to avoid.** It is what the Daily Test
  does with its own answers, but there the text comes from the Worker's own
  store. From the app it would put client-sent sentences into the prompt
  (the rule above), send the learner's practice history to the model
  provider, add several hundred input tokens to every set (roughly 10 to
  20 % of its cost) and need a new app release. Option B gets the same
  effect with ids.
- **Sampling settings (a seed, a temperature).** Not a lever here: sets
  already differ in wording; they repeat scenarios because every request
  gives the model the same starting point. Not tested.
- **A reviewed pool of sets per topic, served at random.** It would allow a
  quality gate that the practice path lacks and would cost less per session,
  but it replaces fresh generation with a fixed stock and is a different
  product decision, far beyond set variety.

## Side by side

| | A: the Worker's theme | B: A + the app's memory | C: A + the Worker's memory |
|---|---|---|---|
| App change | none | new release | none |
| Worker change | small | medium | medium, plus storage |
| Prompt change | one line, user prompt | the same line | the same line |
| Cost per set | under 1 % more | as A | as A, plus store operations |
| New data sent | none | recent theme ids | none |
| New data kept on the server | none | none | themes per device |
| Legal pages | unchanged | review, likely one sentence | review (retention) |
| Applies to the five live topics | yes | yes | yes |
| Reaches installed versions | all, on deploy | only the new version | all, on deploy |
| A theme can come back soon for one learner | yes if random; rarely if stepped | no | no |
| New measurement | duplicates: about $0.47, no labels; quality: owner's call | as A | as A |

## Recommendation

**Option A, with the stepped choice of theme and the Daily Test's 14
themes.** It is the smallest change that gives the request something to
differ by: no app release, no new data, no legal change, all ten topics and
every installed version at once, and under 1 % more per set. Then measure
the duplicates again before deciding anything further; option B is the next
step only if that measurement still shows too much repetition for one
learner. Option C is not recommended: it buys the same guarantee as B by
keeping more about each device on the server.

Two things to weigh with it:

- **It changes the live topics' request.** That is its strength (they have
  the same weakness) and its cost (a deployed, measured request changes).
  The duplicate run above is the minimum; the owner decides whether a
  labelled quality sample of the live topics goes with it.
- **Order with the Conditionals re-measurement.** If Conditionals is
  measured again (the report's proposal), doing it with the theme line
  already in saves a second run and a second round of labels, at the price
  that a bad result could not be pinned on one of the two changes. The
  dollars are small either way (this run cost $0.14 for the topic); the
  labelling is the real cost.
