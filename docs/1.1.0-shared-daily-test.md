# 1.1.0 — Shared Daily Test: Batch 0 report (read-only)

Status: **proposal, awaiting owner approval.** No code, proxy, test or config
change has been made. Nothing is deployed. Written 2026-09-26 on branch
`1.1.0` (from `main` at `3bc83e3`). `lib/` and `proxy/` are byte-identical to
tag `v1.0.0` (`git diff v1.0.0 HEAD -- lib proxy` is empty), and `proxy/` is
unchanged since the deployed commit `05e8f91` (Worker version
`39f39064-0374-42ec-9257-282016c191ba`), so every line reference below
describes exactly what build `1.0.0+3` and the live proxy run.

## 0. Summary

- **Goal:** one Daily Test set per calendar date, generated once by the proxy
  and served to every 1.1.0+ client, so Daily Test API cost stops scaling
  with active devices. Today it is ~1 `generate_daily_test` call per active
  device per day at a measured ~$0.023–0.028 per set.
- **Recommended design, in one paragraph:** sets are **addressed by date**
  (`YYYY-MM-DD`, the client's local `dayKey`). A **Cloudflare Cron Trigger**
  generates each date's set **three UTC days ahead**. It validates the set
  automatically and stores it in a **new KV namespace**. A **new read-only
  route** (`GET /v1/shared-daily-test/{date}`) serves any date inside the
  window **[UTC today − 1, UTC today + 2]**. That route never imports the
  Anthropic client and never touches quota. The **1.0.0 route
  `POST /v1/generate-daily-test` stays exactly as it is.** On the 1.1.0
  client the chain is: local cache → shared set → **bundled fallback pool**
  (new hand-checked sets shipped in the app). Per-device generation is not in
  the 1.1.0 client's chain.
- **Cost after the change:** 1 generation per date (at most 3 attempts,
  capped), about $0.023–0.028/day and at most ~$0.084/day, however many
  users there are. On top of that, 1.0.0 devices keep costing
  ~$0.023–0.028 each per active day until they update. See §1 for why that
  cannot be avoided safely.

## 1. 1.0.0 compatibility (most critical)

### Current state

**What the 1.0.0 client sends.** `ClaudeService.generateDailyTestQuestions`
(`lib/services/claude_service.dart:114-125`) posts to
`{proxyBaseUrl}/v1/generate-daily-test` with headers `content-type:
application/json` and `x-grammarlens-token: <APP_TOKEN>`
(`claude_service.dart:83-86`). The body is `jsonEncode` of a two-key map:

```json
{"deviceId":"9f2c4e01a7b3d8e6c5f40a1b2c3d4e5f","count":5}
```

- `deviceId`: 32 lowercase hex chars, 16 random bytes generated once per
  install (`lib/services/storage_service.dart:726-729`).
- `count`: always `DailyTestService.questionCount = 5`
  (`lib/services/daily_test_service.dart:16`, passed at `:101-104`).
- **No date, no day key, no reason field, no app version.** The client test
  pins the body to exactly `{deviceId, count}`
  (`test/claude_service_test.dart:92`). The proxy rejects any other key with a
  400 (`proxy/src/validation.ts:77-80`, via `requireObjectWithOnlyKeys`
  `:14-27`).
- The client waits up to 40 s (`claude_service.dart:69`, `:168-170`).

**First open vs prefetch.** Both call the same private `_getSet(day)` →
`_loadOrGenerate(day)` (`daily_test_service.dart:44-59`, `:96-106`). The
first open goes through `getTodaysSet()` (`:42`, from
`lib/screens/daily_test_screen.dart:88`). The prefetch goes through
`prefetchSet(dayKeyAfter(setDay))`, started with `unawaited` right after a
completion is saved (`daily_test_service.dart:67-71`, `:132-135`). The `day`
is used **only locally**, as the key the result is stored under
(`:105` → `storage_service.dart:866-891`). It never reaches the wire. So the
two requests are **byte-identical on the wire**: same path, headers and body,
and the same default `Dart/x.y (dart:io)` user agent from `package:http`.
**The proxy cannot tell them apart.** Timing heuristics (a prefetch lands
within seconds of the device's previous request) are unreliable and would
misfire whenever a user opens the test right after finishing it.

**What the proxy does today.** `index.ts:51-57`: validate → `reserveQuota`
(1 unit of `DEVICE_DAILY_LIMIT` 15 and `GLOBAL_DAILY_LIMIT` 300, UTC day,
`proxy/src/quota.ts:34-67`) → `callAnthropic` → return `{questions:[…]}`
unmodified.

### Would turning the existing operation into "the day's shared set" repeat tests?

**Yes, deterministically.** The proxy only knows its own clock (UTC,
`quota.ts:7-9`). The client files whatever comes back under the local day it
had in mind. Three concrete failures follow:

1. **Repeat after completion (every day, for every 1.0.0 user who finishes
   the test).** A user in Türkiye (UTC+3) opens the test on local D at
   09:00 (06:00 UTC D). They get shared(UTC D) and complete it. The prefetch
   fires seconds later (still UTC D), gets shared(UTC D) **again**, and the
   client stores it under D+1 (`daily_test_service.dart:135`). On D+1 the
   cache hit (`:97-98`) serves **the test they already did**. Any user who
   completes a test before the UTC date changes hits this, which is nearly
   everyone east of UTC−0 and most users anywhere.
2. **Date skew for users west of UTC.** A user in UTC−5 who opens at 21:00
   local D (02:00 UTC D+1) gets shared(D+1) filed under D. The next
   morning's open or prefetch gets shared(D+1) again.
3. **Duplicate question ids across days do not break storage** (rows are
   keyed by `day`, `storage_service.dart:206-213`), so nothing would crash.
   The repeat would be silent, which is worse.

### Options

| | Option | Repeat risk | Cost effect |
|---|---|---|---|
| **A** | **Leave `POST /v1/generate-daily-test` unchanged** (per-device generation, quota as today). Add a new, separate read route for 1.1.0+. | None | 1.0.0 devices keep costing ~$0.023–0.028 per active day each until they update. **This is the only option here that does not lower 1.0.0 cost.** |
| B | Change the existing route to return the shared set for UTC today. | Certain (see above) | Lowest cost, broken product |
| C | Existing route returns a *different* stored set per call (e.g. from the last N published sets, chosen by `hash(deviceId, UTC day, call#)`). | Lower but not zero: the proxy cannot know which sets the device already holds. Needs a per-device KV counter write per call. | Lowers 1.0.0 cost to zero Anthropic calls, but adds KV writes (see §4, free-plan write limit) |

### Recommendation: **A**

It is the only option that keeps 1.0.0 behavior provably unchanged. The
saving from B/C only applies to devices that never update, and it costs a
visible regression on exactly those devices. The 1.0.0 client also has no way
to be asked to update: no minimum-version check and no Remote Config
(`pubspec.yaml:12-19` has only `http`, `firebase_core`, `firebase_analytics`,
`firebase_crashlytics`). An error response would put 1.0.0 users on the
"Couldn't load today's test" screen (`daily_test_screen.dart:288-296`).

**How the legacy route should behave:** exactly as now. Same validation, same
quota accounting, same prompt and `max_tokens`. The one exception is the
prompt diversity work in §8. Should it share the prompt? Recommendation: no.
Leave the legacy prompt untouched, so a 1.0.0 test's behavior is frozen.
Revisit when Workers Logs shows the legacy call count per day is small (§9);
Option C can be reconsidered then with real numbers.

**Guarantee mechanism:** in every proxy batch, the existing
`POST /v1/generate-daily-test` tests in `proxy/test/index.test.ts:155+` run
unchanged. One more test pins the legacy Anthropic request body
byte-for-byte, so a shared-prompt change cannot leak into it.

## 2. Hypothesis: date-addressed sets

### Current state

- Client "today" is the **local** calendar date:
  `_todayKey() = clockForTesting().toIso8601String().split('T')[0]`
  (`storage_service.dart:768-769`; `clockForTesting` defaults to
  `DateTime.now`, local).
- `dayKeyAfter(day)` = `DateTime(y, m, d + 1)` from the parsed fields
  (`storage_service.dart:856-862`). This is calendar arithmetic, so it is
  correct across month and year ends, leap days and DST. The build log notes
  the DST test cannot fail on a Türkiye-zone machine, but the code is correct
  by construction.
- Monthly Climb keys its ledger on the **set's own day**: `completeDailyTest`
  writes `climb_daily_entries.day = setDay` (`storage_service.dart:913-957`,
  insert at `:953-954`). The result screen passes `day: _completion.set.day`
  (`lib/screens/daily_test_result_screen.dart:123-128`), so a test finished
  after midnight still credits the day it belongs to.
- The proxy's own day is **UTC** and is used only for quota (`quota.ts:6-9`).

### Evaluation

**It fits with no contradiction.** The date string is only a label. The
client computes it exactly as today (`currentDayKey` / `dayKeyAfter`). The
proxy does no time-zone arithmetic on it at all. It only checks that the
string is a real calendar date and that it lies inside a window of UTC
dates, using `Date.UTC` arithmetic, which has no DST. So:

- **UTC vs local boundary:** local dates in use at any moment span UTC
  today − 1 (UTC−12, e.g. Baker Island) to UTC today + 1 (UTC+14, Kiribati).
  A client asking for *tomorrow's* local date adds one more day. **Window:
  `[utcToday − 1, utcToday + 2]`.** Anything outside it gets a 404, and the
  client falls back (§5). That also covers a device with a wrong clock.
- **Prefetch:** "tomorrow" is always inside the window, because a local
  tomorrow is at most `utcToday + 2`. The set must exist by then, which is
  why generation targets `utcToday + 3` (§3).
- **Monthly Climb:** unchanged. The set is still stored under the same
  local `day`, and the climb still reads `set.day`. The ledger never sees
  where the set came from.
- **DST:** no new DST surface. The proxy never converts zones. The client
  already builds date strings from calendar fields.
- **Known consequence (acceptable, worth stating):** "the same set for
  everyone" means **the same set per calendar date**, not per instant. At
  23:00 UTC, a user in Türkiye (already on D+1) and a user in London (still
  on D) see different sets. Two users only compare notes about the same
  date's set.
- **Travel:** a user flying east can reach a date whose set they already
  fetched (cache hit, as today) or skip a date. Neither repeats a test.

**Alternative considered: one global UTC day.** Rejected. The set's day and
the local climb day would diverge. The prefetch would reproduce the §1
repeat bug in the new client. For the main audience (UTC+3) the "new test"
would appear at 03:00 local.

**Recommendation:** date-addressed sets, window `[utcToday − 1,
utcToday + 2]`.

**Cost effect:** none by itself.

## 3. Generation trigger

### Current state

- `proxy/wrangler.jsonc:1-32` has **no `triggers` block** and there is **no
  `scheduled` handler** in `proxy/src/index.ts` (it exports only `fetch`,
  `:76-102`). Cron needs a config key and a handler; it is not configured
  today.
- The Cloudflare plan (Free vs Paid) **is not recorded anywhere in the repo**,
  and it matters. From Cloudflare's limits page, read 2026-09-26: Cron
  Triggers are **5 per account on Free, 250 on Paid**. CPU time per cron run
  is **10 ms on Free**, and 30 s (under a 1 h interval) or 15 min (1 h
  interval or more) on Paid. Wall duration is 15 min on both. Cron runs on
  **UTC**. The config key is `"triggers": { "crons": [...] }`. Waiting on
  `fetch` is not CPU time. JSON parsing and validating a ~6 KB set should fit
  in 10 ms, but that has to be **measured** (`wrangler tail` shows CPU time),
  not assumed.
- Generation takes a while: one live `generate-daily-test` took 27.6 s
  (build log 2026-09-24, "proxy deployed"). Five local runs used output
  tokens 1319–1496 against a 3072 budget
  (`proxy/src/anthropic.ts:28-30`).

### Options

| | Option | Double-generation risk | User-facing wait | Cost |
|---|---|---|---|---|
| **A** | **Cron only:** an hourly run makes sure every date in `[utcToday, utcToday + 3]` has a set, and generates a missing one (attempt cap per date). | Only if two cron runs overlap, which is practically impossible with a ~30 s job on an hourly schedule. Also guarded by "read before write" and immutable publish. | None, because the set exists ≥ 34 h before its earliest fetch | 1 call/date, at most 3 |
| B | Generate on first request and lock | Real: KV has no compare-and-swap (`quota.ts:25-33` already documents this), so a lock needs D1 or a Durable Object | The first user each date waits ~27 s+, up to the 40 s client timeout | 1/date plus losers of any race |
| C | A + B (on-demand as a backup when the cron missed) | As B, but rare | Rare | As A, plus rare extras |

### Recommendation: **A (cron only)**

The read route never generates. This is also what makes the §6 guarantee
("a read never reaches Anthropic") structural rather than conditional.

- Schedule: one cron expression, hourly (e.g. `"7 * * * *"`). This uses 1 of
  the 5 Free cron slots. Each run looks at dates `utcToday … utcToday + 3`
  and, for each date with no published set and fewer than
  `MAX_ATTEMPTS_PER_DATE` (3) recorded attempts, makes one attempt. Normally
  only `utcToday + 3` is missing, so there is one Anthropic call per day.
- Why +3 and not +2: the earliest fetch of date D is a UTC+14 user
  prefetching D right after completing D−1, which starts at UTC (D−2) 10:00.
  A set generated at UTC (D−3) 00:07 exists **~34 h** before anyone can ask
  for it. That gap is the owner's **optional** review window (§8), and the
  time for up to 2 retries.
- Double generation: each attempt reads the attempt counter and the set key
  before calling Anthropic, and writes the set only if the key is still
  absent. Overlapping hourly runs of a ~30 s job would need a >1 h stall, and
  even then the cost is one extra call. The existing set is never
  overwritten, so users never see the set change under them.
- Retries: the attempt cap stops a persistent failure (bad prompt, Anthropic
  outage, a validation rule that always fails) from spending more than 3
  calls per date. After the cap, the date stays empty and clients use the
  fallback (§5).

**Cost effect:** 1 generation per date normally, hard ceiling 3 per date
(≈ $0.084/day at the top of the measured range).

## 4. Storage

### Current state

`wrangler.jsonc:26-31` binds exactly one KV namespace, `QUOTA_KV`
(`types.ts:12`). There is no D1, R2 or Durable Object binding, and no Cache
API use. `QUOTA_KV` holds `d:{utcDay}:{deviceId}` and `g:{utcDay}` counters
with a 2-day TTL (`quota.ts:3-4`, `:36-37`, `:63-66`).

KV limits (Cloudflare docs, read 2026-09-26): reads **100,000/day on Free**,
unlimited on Paid. Writes to different keys **1,000/day on Free**, unlimited
on Paid. Writes to the same key 1/s. Values up to 25 MiB. `cacheTtl` minimum
30 s. Consistency: **eventual; a write can take 60 s or more to be visible
elsewhere, and negative lookups (key absent) are cached the same way.**

> **Side finding, independent of this work:** every quota-counted request
> does 2 KV writes (`quota.ts:63-66`). On the Free plan's 1,000 writes/day
> that caps real traffic at ~500 counted requests/day. With
> `GLOBAL_DAILY_LIMIT` 300 that is 600 writes, so today's configuration fits.
> Raising the global limit past ~500 on Free would make `put` fail, which
> becomes an `internal_error` 500 (`index.ts:95-99`) for every user. **The
> owner should confirm the plan.**

### Options

| | Store | Fit |
|---|---|---|
| **A** | **KV, new namespace `DAILY_SETS_KV`** (one immutable key per date) + **Cache API** in front of reads | Write-once, read-many, ~6 KB values. Eventual consistency does not matter because a date is published ≥ 34 h before it can be read and never rewritten. Negative-lookup caching cannot bite either, because a date is out of the window, and gets a 404 without a KV read, until long after it is published. |
| B | D1 | Strongly consistent, and `INSERT OR IGNORE` gives a real lock. Only needed for option 3B, which is rejected. Adds a schema and migrations to the proxy. |
| C | R2 | Object storage for large blobs. No benefit at 6 KB. |
| D | Cache API alone | Per data center, not replicated, evictable. Not a store, only a read accelerator. |

### Recommendation: **A**

- Separate namespace rather than a `QUOTA_KV` prefix: sets can be listed,
  inspected and wiped without touching live quota counters, and the two
  kinds of data have different lifetimes. (On Free, the write limit is per
  account either way. Sets add ~2–4 writes/day: set + attempt counter.)
- Keys: `set:{date}` →
  `{ date, questions, generatedAt, promptVersion, attempt }`;
  `attempts:{date}` → integer.
- Reads: the Worker checks the token, the date format and the window
  **before** any KV read. It then tries `caches.default` (key: a synthetic
  GET URL for the date, so the token is never part of the cache key), then
  `DAILY_SETS_KV.get(key, { type: 'json', cacheTtl: 3600 })`, then
  `cache.put` with `max-age=3600`. At steady state, KV reads are about
  (data centers hit) × (dates in window) per hour, far below 100k/day.
- **Retention: `expirationTtl` 35 days on `set:*`**, 7 days on `attempts:*`.
  35 days covers the window, gives the diversity avoid-list (§8) the last 7
  sets, and keeps a month for audit. Storage is ~200 KB.

**Cost effect:** no Anthropic cost. KV/Cache usage is inside Free limits at
current scale.

## 5. Fallback plan

### Current state

- On a generation failure, the 1.0.0 client shows an error screen: "Couldn't
  load today's test" with Try again, or "Today's limit reached" with **no
  action at all** (`daily_test_screen.dart:283-297`). Offline, a day with no
  cached set is this error screen. **That is the "empty Daily Test" the
  requirement forbids.**
- `kDayZeroQuestions` (`lib/data/day_zero_daily_test.dart:22+`) is one
  hand-written 5-question set with ids `day0_1…day0_5`, one question per
  topic, 3 fill-in / 2 error-correction, with explanations and predicted
  wrong answers. `seedDayZeroSet()` (`daily_test_service.dart:80-88`) writes
  it as today's set with `source: bundled` **only when today has no set**, so
  it can never overwrite anything. `test/day_zero_daily_test_test.dart`
  checks the set the way a learner would: every key graded `correct` by
  `checkDailyTestAnswer`, every predicted wrong answer graded `commonWrong`
  with its comment, and so on.
- `DailyTestSource` is `{generated, bundled}` (`lib/models/daily_test_set.dart:6`).
  It is stored as text with default `'generated'`
  (`storage_service.dart:206-213`), and an unknown value reads back as
  `generated` (`:1195-1196`).

### Options for the chain (after the local cache)

| | Chain | Never empty? | Cost |
|---|---|---|---|
| **A** | shared(date) → **bundled fallback pool** | Yes, including offline | Zero Anthropic cost in any failure |
| B | shared(date) → per-device generation (legacy route) → bundled pool | Yes | **Raises cost** in exactly the situations where the proxy is already unhealthy (an outage makes every device pay once). It also spends quota. |
| C | shared(date) → the *previous* date's shared set | No guarantee (can be missing too) | Zero, but a user who did yesterday's test sees it again: the repeat the design exists to avoid |

### Recommendation: **A**

- **Proxy side:** no in-proxy substitution. A missing or out-of-window date
  is a clean 404 (`{error:"not_found"}`). That keeps the proxy honest about
  what exists, and the client owns the "never empty" guarantee.
- **Client:** `getTodaysSet` becomes local cache → `GET shared(date)` with a
  short timeout (~10 s; a KV read, not a 40 s generation) → fallback pool.
  Every step is inside the existing single-flight (`daily_test_service.dart:44-59`).
- **Reuse of the day-0 machinery: yes, directly.** A new
  `kFallbackDailyTestSets` constant beside `kDayZeroQuestions`, same types,
  with unique id prefixes (`fb01_1…`) so stored answers never collide. The
  same write-only-if-empty rule as `seedDayZeroSet`. A new
  `DailyTestSource.fallback`. The same learner-style test file pattern.
  Selection: the first pool set whose ids appear in no stored
  `daily_test_sets` row. When all have been used, the least recently used
  one. No schema change: the question ids inside `questions_json` identify
  the set.
- **Pool size (owner decision):** 7 sets covers a week-long outage with no
  repeats, and 14 covers two. Authoring options: hand-written (owner time,
  no API cost), or model-generated once and owner-reviewed (a one-time
  ~$0.025 per set, ~$0.35 for 14).
- The "Today's limit reached" state disappears from the Daily Test for 1.1.0
  clients: the read route never returns `quota_exceeded`.

**Cost effect:** A adds none. B would add up to one generation per
affected device per failed day. This report does not recommend B.

## 6. Quota and abuse

### Current state

- Every operation route runs `requireAppToken` (`index.ts:37`,
  `proxy/src/auth.ts:21-26`: a static shared secret, which the code comment
  says can be extracted from the binary). It then runs `reserveQuota` before
  Anthropic (`index.ts:47, 54, 61`), which counts 1 unit against device and
  global limits.
- Every non-POST except `GET /health` is a 404 (`index.ts:80-86`). A GET
  route has to be matched before that check.

### Options for protecting the read route

| | Protection | Effect |
|---|---|---|
| 1 | **App token** (same header as today) | Filters casual scanning. Rejected with 401 before any KV or Cache read. |
| 2 | **No `deviceId`, no `reserveQuota`** | Reading the set never uses up `DEVICE_DAILY_LIMIT` or `GLOBAL_DAILY_LIMIT`. |
| 3 | **Cache API in front of KV** | Repeated reads cost a Worker invocation only. |
| 4 | Cloudflare WAF rate-limiting rule on `/v1/shared-daily-test/*` (zone level) | Protects the **Worker request allowance** (on Free, a flood could exhaust daily Worker requests and take the paid practice routes down with it). Whether a rule is available on the zone's plan must be checked in the dashboard. |
| 5 | Workers Rate Limiting binding keyed by IP | Possible, but it adds a binding and state for a route whose worst case is Worker requests, not Anthropic spend. |

### Recommendation: 1 + 2 + 3, and 4 if the zone allows it

**"A read never reaches Anthropic" is guaranteed in three layers:**

1. **Structural.** The read handler lives in its own module
   (`shared_daily_test.ts`), which imports neither `anthropic.ts` nor
   `quota.ts`. Only the `scheduled` handler imports the generator.
2. **Tested.** The read-route tests mock global `fetch` and assert
   **zero outbound calls**, and assert that `QUOTA_KV` is unchanged, after
   many reads: hit, miss, out of window, bad date, bad token.
3. **Behavioral.** A miss is a 404, never "generate now" (§3).

Response headers to the app: `Cache-Control: private, max-age=0`. The client
stores the set in SQLite, so HTTP caching on the device adds nothing.
Server-side caching is done with the Cache API as in §4.

**Cost effect:** no Anthropic cost. It also removes 1 quota unit per device
per day, which frees headroom in `DEVICE_DAILY_LIMIT` 15 (today: 10 practice
units + 1 test + 1 prefetch = 12, per the build log 2026-09-22).

## 7. Client

### Current state

- **Prefetch:** after every successful completion, including the day-0
  completion (`daily_test_service.dart:126-137`). The build log (2026-09-22)
  and roadmap ("Prefetch waste") record that this costs one generation per
  active day, one wasted generation per skipped day, and one for every
  install that stops after day 0.
- **Home / lifecycle:** Home only *reads* today's cached set
  (`lib/screens/home_screen.dart:383-399`). On `resumed` it re-reads locally
  and never generates (`:218-228`). The app-level observer
  (`lib/app.dart:109-115`) does analytics and medal finalization only.
  Generation happens only when the Daily Test screen opens
  (`daily_test_screen.dart:88`) and in the post-completion prefetch.
- **Cache semantics:** `saveDailyTestSet` replaces an unfinished row and
  never a completed one (`storage_service.dart:866-891`).
  `getDailyTestSet(day)` is the only read path (`:841-852`), and it is always
  called with today or tomorrow.

### Options

| | Prefetch | Notes |
|---|---|---|
| **A** | **Keep it; point it at `shared(tomorrow)`** | Free (no Anthropic). Tomorrow is always in the window (§2), so the next open works offline. |
| B | Remove it | Every open then needs the network, and more opens land on the fallback |
| C | A, plus "make sure today's set is cached" on Home load/resume | Most of the fallback's offline cases go away. It adds a network read on resume, which contradicts the documented "resume is a local read" rule in `home_screen.dart:220-221` (a behavior change to decide on, not a cost). |

**Recommendation: A** in 1.1.0, with C as a small, separate, optional batch.

- **Is the set ready before local midnight?** Yes. Local tomorrow is at most
  `utcToday + 2`, and the cron has produced dates up to `utcToday + 3`.
- **Owner replacing a set after a device prefetched it:** the device keeps
  its copy (cache hit, `daily_test_service.dart:97-98`). The review window
  (§8) ends before any device can fetch, so this only matters for a
  late pull. Accepted, and documented.
- **Old `daily_test_sets` rows:** only today and tomorrow are ever read
  (`storage_service.dart:836`, `:841`), so **no schema migration is needed.**
  Rows need no new column either: `day` already is the shared date, and
  `source` is free text with a default. Proposed cleanup: a delete run once
  per launch of rows with `day < today − 7 AND completed_at IS NULL` (unused
  prefetches and abandoned days). **Keep completed rows.** They are ~6 KB
  each, hold the only record of the answers, and deleting them is
  irreversible. `resetProgressData` (`storage_service.dart:1310-1316`) does
  not touch this table today, and this proposal does not change that.
- **Transition:** a 1.0.0 user who updates keeps any 1.0.0-generated set
  already stored for today or tomorrow (cache hit). They switch to shared
  sets from the next uncached date. There is no repeat risk: dates are
  distinct.
- **`AppLifecycleState` / day rollover:** not affected. The single-flight is
  per day key (`daily_test_service.dart:28, 44-59`). A screen opened just
  after midnight asks for the new date, and the set's own day is still what
  completion and the climb use.

**Cost effect:** A and C add no Anthropic cost. They remove the legacy
prefetch's paid call (one per active 1.1.0 device per day).

## 8. Quality and variety

### Current state

- The proxy does **no content validation** of a Daily Test response. It
  `JSON.parse`s the text block and returns it (`anthropic.ts:406-416`).
  Structured output enforces the JSON Schema (`anthropic.ts:223-265`: `id`,
  `type` ∈ {fill_in_blank, error_correction}, `instruction`, `topicId` ∈ the
  5 topic ids, `correctAnswer`, `explanation`, `commonWrongAnswers[{answer,
  comment}]` required). It does not enforce the count, unique ids, 2–3 wrong
  answers, explanation length, or answer-key sanity. Proxy tests even pass a
  1-question response for `count: 5` (`proxy/test/index.test.ts:156-177`).
- Client grading is `checkDailyTestAnswer` (`lib/utils/answer_matching.dart:127-172`),
  checked in this order: `normalizeAnswer` equality with `correctAnswer`
  (`:13-23`: curly-to-straight quotes, trim, collapse whitespace, lowercase,
  drop one trailing `.`/`!`/`?`) → Turkish-keyboard fold equality
  (`keyboardVariant`, `:41-56`) → each predicted wrong answer → `fallback`.
- Measured explanation length with the "fewer than 25 words" prompt (build
  log 2026-09-24): min 12, median 21, max 27 words. 5 of 25 were 25–27.
- **Topic list:** exactly 5 topics, in `proxy/src/topics.ts:16-42`, mirrored
  from `lib/data/topics.dart:9-40`: `gerundVsInfinitive`, `modalVerbs`,
  `modalPastForms`, `tenseSelection`, `articles`. **No sub-skill or scenario
  list exists** anywhere in the repo. The prompt is one fixed sentence
  (`anthropic.ts:45-48`). Ten sampled sets had the same topic order and
  recurring scenarios ('admit', "needn't have looked", 'train had already
  left'; build log 2026-09-24).

### Automated validation (a failed set is not published; the next hourly run retries within the cap)

Proposed as a pure function `validateSharedSet(json, count)` in the proxy,
with a fixed-vocabulary reason code for each rule:

1. **Shape:** exactly `count` (5) questions. Ids non-empty, unique, ≤ 100
   chars. Types and topic ids are in their enums. Every string within a
   length bound (reuse `MAX_TEXT_LENGTH` 2000, `validation.ts:6`).
   `commonWrongAnswers` has 2–3 entries. Every field that
   `DailyTestQuestion.fromJson` requires is present
   (`lib/models/daily_test_question.dart:78-87`, `PracticeItem.fromJson`).
2. **Answer-key consistency with `checkDailyTestAnswer`:** a TypeScript
   port of `normalizeAnswer` and `foldKeyboardVariants`, kept in sync by
   **one shared JSON fixture of input → normalized pairs, read by both a Dart
   test and a vitest test** (either side drifting turns a test red). Rules:
   `correctAnswer` normalizes to non-empty. **No predicted wrong answer
   normalizes or folds to the correct answer** (such an answer could never
   be reached, because correct and keyboard variant are checked first, so it
   shows a key the model itself got confused about). Wrong answers are
   pairwise distinct after normalizing. For `error_correction`, the
   normalized `context` differs from the normalized `correctAnswer` (the
   "correction" actually changes something).
3. **Explanation:** exactly one sentence (no internal `. ` followed by a
   capital letter), **≤ 35 words**. The prompt still asks for fewer than 25.
   35 sits above the measured max of 27, so ordinary outputs are not
   rejected (each rejection is a paid retry). Does not open with praise or
   "Not quite" (a small fixed prefix list).
4. **Topic coverage:** the day's topic plan (below) is met.

Each attempt logs one line (see §10). A reject costs one generation, and the
cap (§3) bounds it.

A consideration, not a proposal: a fill-in item's `context` containing
`___` is how the day-0 set is written, but the generation prompt never asks
for it. Adding it as a rule without first sampling the real outputs could
reject good sets. Measure first.

### Optional owner review (never a required step)

- A set is published (readable) as soon as it passes validation, but no
  client can read it for ~34 h (§3).
- To inspect: `wrangler kv key get --binding DAILY_SETS_KV "set:2026-10-05" --remote`.
  To pull: delete `set:{date}` (and `attempts:{date}` to reset the cap), and
  the next hourly run regenerates it. Nothing has to be approved for a set
  to go live. No new admin surface or secret is needed in the first version.
- Later, if the owner wants it: an admin route behind a separate secret,
  or a daily summary line.

### Variety

**Rotation (deterministic from the date, so a regeneration of the same date
gets the same plan):**

- **Topic order:** a date-seeded permutation of the 5 topics, still one
  question per topic.
- **Type split:** alternate 3 fill-in / 2 error-correction and
  2 fill-in / 3 error-correction by date. Which topics get which type
  rotates with the permutation.
- **Scenario theme of the day:** from a fixed list, e.g. work, travel,
  health, study, family, technology, food, money, sport, environment,
  shopping, housing, media, science. **This list does not exist yet and is
  new content for the owner to approve.** Nothing in it is user data.
- **Avoid list:** the `correctAnswer`s of the last 7 published sets (read
  from KV, ≤ 35 short strings), with "do not reuse these answers or
  scenarios".

**Cost effect (stated explicitly):** the avoid list and plan add input
tokens to the one daily call. Today's input is 1173 tokens per call (build
log 2026-09-24). ~300–500 more is roughly +25–45% input on a single call per
day. Output dominates the per-set cost (1319–1496 output tokens), so the
per-day total rises by a small fraction of one set's cost. This is a real
increase, but far below one extra device's legacy call.

**Prompt versioning:** `promptVersion` is stored with each set. The legacy
prompt (§1) is unchanged.

## 10. Billing verification

### Current state: what gets logged, per failure mode, for `generate_daily_test`

| Situation | `anthropic_usage` | `anthropic_failure` | Code |
|---|---|---|---|
| `fetch` throws (network) | — | `network_error` | `anthropic.ts:359-363` |
| Non-200 (429, 5xx, …) | — | `http_error` + status + whitelisted type | `:365-382` |
| 200, body not JSON | — | `unreadable_body` | `:384-393` |
| 200, no text block | ✔ | `no_text_block` | `:396-404` |
| 200, text not JSON (**this includes `max_tokens` truncation**) | ✔ | `invalid_json_content` | `:406-416` |
| 200, valid JSON but a shape the app rejects (missing field, wrong type) | ✔ | **nothing**. The proxy passes it through, and the client's `fromJson` throws, so nothing is stored | `anthropic.ts:407`, `daily_test_question.dart:78-87`, `daily_test_service.dart:96-106` |
| The app's 40 s timeout fires first | ✔ if the Worker finishes, but **the Worker may be cancelled when the client disconnects** (Cloudflare docs: tasks "may be canceled", and there is no `waitUntil` here), and then **no line at all** | — | `claude_service.dart:69`, `:171-175` |
| The proxy's own call to Anthropic hangs | nothing until the platform ends it: **there is no timeout or `AbortSignal` on the proxy's `fetch`** | — | `anthropic.ts:350-358` |
| 200 received, app killed before save | ✔ | — | client-side |

`logUsage` carries `event, kind, operation, item_count, input_tokens,
output_tokens, duration_ms` (`usage_log.ts:47-59`). It does **not** carry
`stop_reason`.

**Can "billed but not stored" be derived from the token log?** **No.** The
proxy never learns whether the client stored the set. `usage − failure`
lines count responses the proxy *sent*, not sets the app *kept*. Requests
cancelled mid-flight may be billed with no line at all. Whether Anthropic
bills a request the Worker abandoned cannot be decided from this repo; only
the Console can show it. The roadmap item "Verify whether timed-out or
unparseable generations are still billed" (`docs/roadmap.md:97-99`) is
therefore not answerable with the current logs.

### Options

1. **For the shared path (recommended, part of the proxy batches):** the
   cron is the only caller, runs up to 15 min with no client to disconnect,
   and knows whether it stored the result. Each attempt writes one
   fixed-field line, `shared_set_generation` with `{date, attempt, outcome}`,
   where `outcome` ∈ `published | rejected:<reason_code> | upstream_failed |
   already_published`, along with the usual usage line. Then **billed but not
   published = usage lines for `generate_shared_daily_test` − `published`
   outcomes**, exactly. Also give the Anthropic `fetch` an
   `AbortSignal.timeout(90_000)` on the cron path, so a hang becomes a
   logged `network_error` rather than a silent 15-minute stall.
2. **Add `stop_reason` to `anthropic_usage`** (a fixed vocabulary, anything
   else is `unknown`). Truncation (`max_tokens`) then shows directly instead
   of being inferred from `invalid_json_content`. The line stays privacy-safe
   under the same whitelist approach as `upstream_error_type`
   (`error_log.ts:15-42`).
3. **For the legacy path:** add nothing to the 1.0.0 client (it cannot
   change). One cross-check per week instead: the Anthropic Console's
   request count for the key vs the total count of `anthropic_usage` +
   `anthropic_failure` lines. A persistent gap measures calls that were
   billed but abandoned. Optionally, a separate Anthropic API key for the
   cron makes the Console split shared vs legacy spend exactly.

**Cost effect:** none. These are logs only.

## 11. Proposed batch plan

Every batch is small, has its own tests, and is committed on its own on
`1.1.0`. Proxy batches are **additive only**: no existing route, prompt,
validation or quota behavior changes. **Deploys happen only on owner
approval**, at the marked points.

| # | Batch | Scope | Tests (must include) |
|---|---|---|---|
| P1 | Shared-set core (proxy, no wiring) | `shared_daily_test.ts`: date parsing and window (`Date.UTC`), `validateSharedSet` + TS `normalizeAnswer`/fold, the shared normalize fixture, the date-seeded plan, the new operation `generate_shared_daily_test` in `AnthropicOperation`, its body builder (new prompt, `promptVersion`), `usageKind` → `daily_test`, `stop_reason` in `logUsage` | window edges (−2/−1/+2/+3, month/year/leap); every validation rule red and green; fixture parity (Dart side added in C1); **legacy `generate-daily-test` Anthropic body pinned byte-for-byte**; usage-log privacy tests still pass |
| P2 | Cron generation (proxy) | `scheduled` handler, `triggers.crons` (hourly), `DAILY_SETS_KV` binding, attempt cap, read-before-write immutable publish, 35-day TTL, `shared_set_generation` line, `AbortSignal.timeout` on this path | a missing date is generated once; a present date is not regenerated; cap stops at 3; a rejected set is not written; two overlapping runs write once; nothing calls `reserveQuota`; logs carry no content |
| **D1** | **Deploy (owner)** | `wrangler kv namespace create`, deploy | Watch 2–3 days: one set per date, outcomes, CPU time per run (**Free plan: 10 ms**). Nothing reads the sets yet, and 1.0.0 is untouched |
| P3 | Read route (proxy) | `GET /v1/shared-daily-test/{date}`: token → format → window → Cache API → KV → 200/404 | **zero outbound `fetch`** and **`QUOTA_KV` unchanged** over hit/miss/out-of-window/bad token; the 404 envelope; the existing POST tests unchanged |
| **D2** | **Deploy (owner)** | deploy | `curl` today / tomorrow / out of window. The 1.0.0 app on a device still generates as before |
| C1 | Client: shared fetch | `DailyTestSource.shared`/`fallback`; `ClaudeService.fetchSharedDailyTest(date)` (GET, ~10 s timeout); `DailyTestService` chain cache → shared → fallback (single-flight kept); prefetch → shared(tomorrow); Dart side of the normalize fixture | no generation request is ever made by 1.1.0; 404/timeout/offline → fallback; tomorrow prefetch costs one GET; `set_source` values; the climb still keys on `set.day` |
| C2 | Client: fallback pool content | `kFallbackDailyTestSets` (N sets, owner-approved content), selection by unused ids | the day-0-style learner test for every set; never overwrites; no repeat until the pool is exhausted |
| C3 | Client: cleanup (optional C: ensure-today on resume) | delete old unused rows at launch | completed rows are kept; today and tomorrow are never deleted |
| Dx | Docs | `analytics-plan.md` (§9 here), `roadmap.md`, `build-log.md`, `proxy/README.md` | — |
| R | Release | `1.1.0+N` build, only after D2 has served real dates for ≥ 3 days | full suites, `preflight.sh` |

**Why this order keeps 1.0.0 safe:** 1.0.0 only ever calls
`POST /v1/generate-daily-test`, which no batch modifies (it is pinned by a
test from P1 on). The proxy is fully live and observed before any client
depends on it. The 1.1.0 client treats *any* failure of the new route (404,
5xx, timeout, route missing after a rollback) as "use the fallback", so the
client works even if the proxy side is rolled back completely.

**Relation to `main`:** all work stays on `1.1.0`. A 1.0.x fix made on
`main` is merged into `1.1.0`, never the other way round, until 1.1.0 is
released. Proxy deploys from `1.1.0` are additive, so a later 1.0.x proxy
hotfix from `main` would have to include them. Otherwise, deploying from
`main` would remove the cron and the read route. **Rule: after D1, proxy
deploys are made from `1.1.0` only (or from `main` after merging `1.1.0`'s
proxy commits into it).**

## 12. Risks and rollback

| Risk | Likelihood | Mitigation / rollback |
|---|---|---|
| A bad set passes validation and everyone gets it | Low–medium | ~34 h optional review window; pull = delete the key → regenerated within the hour; optional `set_date` analytics shows it on day 1. Devices that already prefetched it keep it (accepted). |
| Cron silently stops (config lost in a deploy from `main`, plan limit, Anthropic outage) | Medium | Clients fall back, never empty. Dates are produced 3 days ahead, so 2 days of slack before any user is affected. Watch `shared_set_generation` lines. The deploy rule in §11. |
| Free-plan CPU (10 ms) exceeded in the cron | Unknown until measured | Measured at D1 before any client depends on it. If exceeded: simplify validation, or move to Paid (a cost increase, stated). |
| Fallback pool exhausted in a long outage | Low | Least-recently-used reuse, so a repeat but never an empty screen. The pool size is the owner's choice. |
| Legacy (1.0.0) spend stays high because users do not update | Medium | Accepted by design (§1). Measured weekly (§9). Option C of §1 can be revisited with data. |
| Proxy change breaks existing routes | Low | Changes are additive, and the existing tests plus the pinned legacy body run in every batch. **Rollback:** `wrangler rollback` to the previous Worker version (currently `39f39064-0374-42ec-9257-282016c191ba`), or redeploy `v1.0.0`'s `proxy/`. KV data is not rolled back, and it does not need to be: nothing else reads `DAILY_SETS_KV`. Whether a rollback also removes the cron trigger should be checked in the dashboard at D1. If it does not, the cron simply keeps filling KV at 1 call/day, and it can be removed with a deploy that has no `triggers`. |
| Kill switch needed without a rollback | — | Recommended addition in P3: a plain var `SHARED_DAILY_TEST_ENABLED` (in `vars`, like the limits in `wrangler.jsonc:22-25`). When `"false"`, reads return 404 and the cron does nothing. 1.1.0 clients then fall back. |
