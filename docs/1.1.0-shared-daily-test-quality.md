## 0. Summary

**The problem, measured.** The owner reviewed the published sets for
2026-09-26 and 2026-09-27: **4 of 10 questions are defective**, and a fifth
has a minor fault. `validateSharedSet` checks structure and the answer key's
consistency with the app's grader. It does not check grammar, and it cannot.
Three failure patterns:

- `error_correction` items whose "flawed" sentence is acceptable English
  (case c: "I knew I must study harder"; case d: "go to a library on campus").
- Questions with more than one defensible answer, where exact-match grading
  marks a right answer wrong (case b: "must" / "should"), and predicted
  "wrong" answers that are acceptable (case c: "had to"; the 26 Sept
  `tenseSelection` "I already had taken").
- Hints, explanations and comments that teach a rule that does not exist
  (case a: "should becomes should have in reported speech"; case c: "must has
  no past, so use should").

**Owner decision (given): three layers.** Prompt v2; a daily check call in a
separate cron run (generate → pending → check → publish or discard);
`acceptedAnswers` as a schema now, with client grading in C1.

**What this report recommends, in one paragraph.** Prompt v2 is a **new
system prompt used only by the shared operation**. The legacy constant
`DAILY_TEST_SYSTEM_PROMPT` is not touched, and its byte-for-byte pin stays
green. It adds explicit correctness rules and one new deterministic
validator rule: an `error_correction` answer may differ from the original in
**one contiguous span** only. The checker is a separate operation with its own
structured output. The proxy turns the checker's per-question fields into
publish/reject **deterministically**. It never takes the model's verdict
alone, and it never publishes against it. Alternatives the checker finds
become `acceptedAnswers` (at most 2 per question) instead of a rejection,
unless they contradict the set: an acceptable "wrong" answer, an explanation
that rules the alternative out, or an original sentence that is not wrong.
Those are always a rejection. The check is **fail-closed**: an unchecked set is never
published, and a long Anthropic outage means clients use the bundled fallback
pool. Checker model: a **different, not weaker** model than the generator,
chosen by a small local evaluation (≈ $3–4) before deploy. The default
candidate is Claude Sonnet 5 with adaptive thinking.

**The number that matters most.** The whole set is rejected when any one
question fails. At the observed 40% per-question defect rate, a set passes
with probability 0.6⁵ ≈ 8%, and a date gets a published set within the
3-attempt cap only ~22% of the time (§2.6). **Prompt v2 has to bring the
defect rate to about 10% or lower** for the pipeline to publish reliably. So
measuring before deploy (§10) is recommended, not optional polish.

**Cost.** It stays independent of the number of users. Expected ≈ $0.09–0.15
per day at a 5–20% defect rate. The ceiling is ≈ $0.22 per date (3
generations + 3 checks), against $0.084 in the P0 design. §4.5 has the
details.

## 1. Prompt v2

### 1.1 Current state

- One model constant for every operation: `MODEL = 'claude-sonnet-4-6'`
  (`proxy/src/anthropic.ts:13`).
- The shared set **reuses the legacy Daily Test system prompt, schema and
  budget unchanged**. It differs only in the user prompt
  (`anthropic.ts:328-341`, `buildGenerateSharedDailyTestBody`). The legacy
  body builder is `anthropic.ts:318-326`, and its bytes are pinned by
  `proxy/test/index.test.ts:157-170`. So **prompt v2 cannot edit
  `DAILY_TEST_SYSTEM_PROMPT` or `dailyTestSchema()`**: both are shared with
  the legacy route (the comment at `anthropic.ts:269-272` says so). v2 needs
  its own constant and, if the schema changes, its own schema function.
- `DAILY_TEST_SYSTEM_PROMPT` (`anthropic.ts:129-168`) today:
  - Says the answer key "matters more than usual" and is compared exactly
    (`:133-137`), but gives **no rule on what makes an item valid**. It never
    says the flawed sentence must be unambiguously wrong, that only one answer
    may be right, or that stated rules must be standard.
  - Refers the model to "the same 'context' / 'instruction' split, and the same
    production-over-recognition weighting, as regular practice generation"
    (`:139-141`). **The model never sees the practice prompt**
    (`GENERATION_SYSTEM_PROMPT`, `:96-127`), so that sentence refers to
    nothing. The one line that would help here, "Keep each item self-contained
    and unambiguous" (`:99`), is **only** in the practice prompt.
  - **Never defines `hint`.** The schema allows it (`anthropic.ts:286`), the
    validator passes it through (`shared_daily_test.ts:384`), and the model
    writes it with no guidance. Case (a) had a fabricated rule in the hint.
  - `error_correction`: "put the single flawed sentence in context and require
    the full corrected sentence back" (`:142-146`).
  - Explanation: one sentence, fewer than 25 words, "which rule is at work"
    (`:158-165`). It asks for a rule without asking that the rule be true.
- The user prompt (`anthropic.ts:63-94`) **forces a type per topic** from the
  date's plan (`shared_daily_test.ts:162-183`): e.g. "articles:
  error_correction", in a fixed theme. The model cannot decline a combination
  that has no clear-cut error, so it invents one. Cases (c) and (d) are both
  forced `error_correction` slots.
- `SHARED_PROMPT_VERSION = 1` (`shared_daily_test.ts:26`), pinned by a request
  fingerprint (`proxy/test/shared_daily_test.test.ts:687-699`).

### 1.2 Proposed change (text diff, not yet code)

New constant `SHARED_DAILY_TEST_SYSTEM_PROMPT_V2`, used only by
`buildGenerateSharedDailyTestBody`. `SHARED_PROMPT_VERSION` → 2, with a new
fingerprint. The legacy pin is unchanged. The text below is the proposal the
owner approves. The wording is final only after §10's measurement.

It starts from the current Daily Test prompt, with these changes:

**Replaced:** the "same split … as regular practice generation" sentence
becomes the rules themselves (self-contained):

> Put the scene in "context" and the task in "instruction" (one short
> sentence). Keep every item self-contained and unambiguous.

**Added: a correctness section, placed before the format rules:**

> Every item is graded by exact string match, with no human or model in
> between, and the same set is shown to every learner. An item that is wrong
> or ambiguous teaches everyone the wrong thing. These rules come before
> variety, the theme or the plan:
>
> 1. **Single correct answer.** Before you settle on an item, list every
>    answer a careful English teacher would accept. If there is more than one,
>    rewrite the context until exactly one remains (add a time phrase, a
>    speaker's intention, a fact that rules the others out). Differences of
>    register or regional usage count as acceptable answers.
> 2. **error_correction: the original must be clearly wrong.** The sentence in
>    "context" must contain exactly one error that any standard grammar
>    reference marks as incorrect in all contexts. A less common or less
>    formal choice is not an error, and neither is a different modal, a
>    different article or a different tense that a native speaker could
>    defend. If you cannot make an error of that kind for this topic in this
>    theme, pick another situation. The correction changes only the erroneous
>    words. Everything else in the sentence stays exactly as it is. Keep the
>    sentence short: one clause, at most 15 words.
> 3. **Predicted wrong answers must be wrong.** Every entry in
>    "commonWrongAnswers" must be an answer a teacher would mark incorrect in
>    this context. Never list a form that is acceptable, even if it is less
>    natural than "correctAnswer".
> 4. **Only true, standard rules.** The explanation, the hint and every comment
>    may state only rules found in mainstream reference grammars, stated no
>    more strongly than those references do ("usually", "in this context").
>    Never state a rule you are not certain of; choose a different item
>    instead. Do not describe a rule for a structure the item does not test.
> 5. **"hint"** is optional. It points to where to look ("Think about what
>    comes after 'avoid'") and never states a rule or gives the answer.

**Unchanged:** the answer-key sentences, predicted wrong answers (2–3, with
comments to the learner), the explanation's length and tone, the no-praise /
no-"Not quite" opening, and the user prompt's plan and avoid list. The user
prompt gets one added clause: "If a slot's type cannot be written for its
topic under the rules above in today's theme, keep the topic and type, and
move the situation to a different part of the theme." The plan stays
binding. `plan_mismatch` is still a rejection, because a free choice of type
would break the P1 rotation.

**New deterministic validator rule, P4:** `error_correction_multi_edit`.
After `normalizeAnswer`, a word-level diff between `context` and
`correctAnswer` must be **one contiguous changed span of at most 4 words on
either side**. This proves "one error fixed, nothing else touched" without a
model. It costs microseconds (≤ ~30 words per side). It sits next to
`unchanged_error_correction` (`shared_daily_test.ts:414-416`).

**Optional, owner decision:** a short "safe ground" list per topic (e.g.
articles → *a/an* missing before a singular countable noun, *the* before a
general plural). It would steer `error_correction` toward error classes that
are unambiguous. This is new content, like the theme list was. Not included
by default: it narrows variety, and §10 can show whether rules 1–4 are
enough.

*As built in P4 (2026-09-27): rule 5 also allows the base form of a word to
change ("(travel)"), and the clause says "without breaking the correctness
rules". See the build log, 2026-09-27, P4.*

**Why each piece:** rule 1 → case (b). Rule 2 → cases (c) and (d). Rule 3 →
case (c) "had to" and the 26 Sept "already had taken". Rule 4 → cases (a) and
(c). Rule 5 → case (a), whose hint stated the invented rule. The diff rule is
the one part of this that code can check.

**Cost:** about +450 input tokens per generation (≈ 1,380 → ≈ 1,830; the
first live run was 1,380 input, build log 2026-09-26). At $3/MTok that is
≈ +$0.0014 per generation. Output is probably unchanged (~1,300–1,650
tokens). **CPU:** none; the prompt is a constant string.

### 1.3 Does the full-sentence `error_correction` answer raise the risk?

Yes. It raises the **grading** risk, not the risk that the model invents an
error:

- **More valid answers per item.** A longer answer admits more acceptable
  variants: a different fix of the same error (case c: "had to" / "should" /
  "must" all work), or a learner who fixes the error and also rephrases.
  Exact match marks all of them wrong.
- **Internal punctuation counts.** `normalizeAnswer` only drops **one
  trailing** `.`/`!`/`?` and folds case, whitespace and curly quotes
  (`lib/utils/answer_matching.dart:14-23`). A missing or extra comma inside
  the sentence is a mismatch (`fallback`, shown as wrong). The model is never
  told about this.
- **What causes invented errors** is the forced type per slot (§1.1), not the
  answer shape. Cases (c) and (d) failed at step one: the original was fine.

Options: (A) keep full sentences, and limit length (rule 2) and the size of
the edit (the diff rule); alternatives go into `acceptedAnswers`. (B) accept
the corrected fragment as well as the full sentence. That is a grading change
in C1, and it needs a way to tell which fragment is meant. (C) normalize
internal punctuation in the client, which changes `normalizeAnswer` for every
set, including day 0 and the shared fixture. **Recommendation: A** in this
round. Measure the `fallback` share on `error_correction` after C1 before
choosing B or C.

## 2. The check call

### 2.1 Checker prompt (draft)

A new operation, `check_shared_daily_test`, has its own system prompt and
schema. The input is the pending set's questions as JSON (ids included), the
date's plan (topic and type per slot) and the grading contract. It gets no
avoid list and no theme instructions.

> You review English grammar exercises for Turkish learners at B1–C1 before
> they are published. Every learner gets the same set. Answers are graded
> automatically: the learner's text is compared with "correctAnswer" after
> lowercasing, trimming, collapsing spaces and dropping one final full stop,
> question mark or exclamation mark. Nothing else is forgiven. A learner who
> types an acceptable answer that is not in the key is told they are wrong.
>
> Assume the set may contain mistakes, and look for them. For each question:
>
> 1. For error_correction: is the sentence in "context" wrong in standard
>    English in every reading, or could a careful native speaker or a
>    reference grammar accept it? If it can be defended, it is "acceptable".
> 2. Is "correctAnswer" correct in this context?
> 3. List every other answer a careful teacher would accept, typed in the same
>    shape as "correctAnswer" (the full sentence for error_correction). Do not
>    list spelling or punctuation variants of the key.
> 4. List any entry of "commonWrongAnswers" that is in fact acceptable.
> 5. Check every rule stated in "hint", "explanation" and each wrong answer's
>    "comment": is it a real rule as mainstream reference grammars state it,
>    and no stronger? Name the fields that are not.
> 6. Does the explanation say or imply that any answer you listed in step 3
>    is wrong?
>
> Then give a verdict. Judge only grammar and correctness, not style, theme
> or difficulty.

### 2.2 Output schema (structured output, per question)

```json
{
  "questions": [{
    "id": "string",
    "originalSentence": "clearly_wrong | acceptable | not_applicable",
    "correctAnswer": "correct | incorrect | uncertain",
    "acceptableAlternatives": ["string"],
    "acceptableWrongAnswers": ["string"],
    "incorrectRuleFields": ["hint | explanation | comment"],
    "explanationExcludesAlternatives": true,
    "verdict": "pass | pass_with_alternatives | reject"
  }]
}
```

Enums rather than free text, so each outcome maps to a fixed log code. There
is no free-text rationale field. Reasoning goes in the model's thinking,
which is neither stored nor logged (§3).

### 2.3 Decision rule (in the proxy, deterministic)

The proxy decides question by question. The set is published only if every
question passes.

| # | Condition | Result | Reason code |
|---|---|---|---|
| 0 | Output unparseable, wrong count, unknown or duplicate id | **check failed** (not a rejection: the pending set is kept and the check retried) | `check_unreadable` |
| 1 | `error_correction` and `originalSentence` ≠ `clearly_wrong` | **reject** | `original_not_wrong` |
| 2 | `correctAnswer` ≠ `correct` (`uncertain` included) | **reject** | `key_incorrect` |
| 3 | `incorrectRuleFields` non-empty | **reject** | `wrong_rule` |
| 4 | `acceptableWrongAnswers` non-empty | **reject** | `wrong_answer_acceptable` |
| 5 | Alternatives non-empty **and** `explanationExcludesAlternatives` | **reject** | `explanation_excludes_alternative` |
| 6 | More than 2 alternatives remain after the mechanical checks | **reject** | `ambiguous_question` |
| 7 | An alternative equals `context` (normalized) | **reject** (the checker is contradicting itself about the original) | `alternative_is_original` |
| 8 | An alternative equals or folds to a predicted wrong answer | **reject** | `alternative_conflicts_wrong_answer` |
| 9 | `verdict` = `reject` although 1–8 all pass | **reject** (conservative) | `checker_verdict` |
| — | Otherwise | **pass**; the alternatives become `acceptedAnswers` | — |

Mechanical cleanup before rules 6–8: an alternative that is blank, over the
length limit, or that normalizes or folds to `correctAnswer` is **dropped**,
not rejected. It is harmless noise.

### 2.4 Alternatives as `acceptedAnswers` instead of a rejection

**Yes, within limits.** It fixes case (b), where the question is fine and the
grading is too narrow, without paying for a regeneration. It also stops
unfair "wrong" results. It stops being safe when the alternative contradicts
something the learner is shown. That is why rules 4, 5, 7 and 8 reject rather
than add:

- Case (c): "had to" is listed as **wrong**, and its comment explains why.
  Accepting it would grade the learner correct while the comment says
  otherwise. **Reject** (rule 4).
- An explanation that says "should is wrong here" while "should" is accepted
  contradicts the result. **Reject** (rule 5).
- More than 2 alternatives means the question does not test one thing.
  **Reject** (rule 6), in line with prompt rule 1.

A possible later refinement is dropping an acceptable predicted wrong answer
when at least 2 remain. It is not recommended now: the explanation or the
other comments may rely on it, and nothing mechanical can tell.

**Always a rejection, never repaired:** an `error_correction` original that
is not wrong (cases c, d), a key that is not correct, and any false rule in a
hint, explanation or comment (cases a, c). The set is wrong for everyone in
those cases, and `acceptedAnswers` cannot fix it.

### 2.5 What the check costs (estimate; §10 replaces it with measurements)

Input ≈ 2,800 tokens: the checker prompt (~800), the schema (~300), and the
set as input (~1,700, since the set came out as 1,620 output tokens). Output
without thinking ≈ 700 tokens (5 × ~120 + JSON). Thinking adds ≈ 1,500–2,500
tokens, billed as output. §3 has the cost per model.

### 2.6 Why the whole-set rule makes the defect rate decisive

Per-question defect rate *p* (true defects plus checker false alarms). A set
passes with probability (1−*p*)⁵. Three generations are allowed per date.

| *p* | Set passes | Date published within 3 attempts | Expected generation+check pairs per date |
|---|---|---|---|
| 0.40 (observed v1, 4/10) | 7.8% | 22% | 2.77 |
| 0.30 | 16.8% | 42% | 2.52 |
| 0.20 | 32.8% | 70% | 2.12 |
| 0.10 | 59.0% | 93% | 1.58 |
| 0.05 | 77.4% | 99% | 1.28 |

The observed 4/10 comes from two sets. Its 95% interval is roughly 17–69%,
so it can only say that the rate is high, not how high.
`acceptedAnswers` turns case (b) into a pass, but cases (a), (c) and (d)
remain rejections. **If v2 does not reach ~10%, the options are:** (i) a
higher cap (cost); (ii) **regenerate only the failing slot**: a one-question
generation (~1/5 of the output) and a check of that question, which needs more
state; (iii) accept more fallback days. That decision should be made on §10's
numbers, not now.

## 3. Checker model

Prices are Anthropic first-party list prices per million tokens (input /
output). Token counts are the §2.5 estimates. For Sonnet 5 and Opus 5 they are
scaled ×1.3 for the newer tokenizer ("~30% more tokens for the same text" for
Sonnet 5).

| Model | $/MTok | Per check, no thinking | Per check, with thinking (~2k) | Notes |
|---|---|---|---|---|
| `claude-sonnet-4-6` (the generator) | 3 / 15 | ≈ $0.019 | ≈ $0.049 | Same model as the generator. Thinking must be requested (`{type:"adaptive"}`); the generator runs without it today |
| `claude-haiku-4-5` | 1 / 5 | ≈ $0.006 | ≈ $0.014 | Cheapest, weakest at the nuanced acceptability judgments this job consists of. Thinking uses `budget_tokens` |
| `claude-sonnet-5` | 2 / 10 | ≈ $0.016 | ≈ $0.042 | Newer, stronger model, cheaper per token; adaptive thinking is **on by default**. Sampling parameters would be rejected, but we send none |
| `claude-opus-5` | 5 / 25 | ≈ $0.041 | ≈ $0.106 | Strongest option, 2–3× the Sonnet 5 cost |

**Self-blindness.** The risk is real but unmeasured. Case (a)'s rule and case
(c)'s rule came from `claude-sonnet-4-6`. A reviewer that makes the same
mistakes tends to accept plausible rules of its own making. Mitigations:
(1) a **different** model; (2) adversarial framing ("assume there are
mistakes"; enumerate alternatives before judging); (3) thinking. The job is
also **harder than generation**: deciding whether an alternative is
acceptable is exactly where the generator failed. That argues against a
weaker model for the check.

**Recommendation:** a different, not weaker model, with thinking on. Default
candidate: **`claude-sonnet-5`** with adaptive thinking (≈ $0.04 per check).
Compare it in §10 with `claude-sonnet-4-6` + thinking on the labelled items.
Haiku 4.5 only if §10 shows it catches all four known cases. The model is a
**constant in code, not a var**. It goes into the published record
(`checkModel`) and the log line, so a set is traceable to what checked it.

Out of scope, noted only: moving the **generator** to Sonnet 5 (cheaper per
token, stronger). It would need a model constant separate from the legacy
route's, and it would change two variables at once. At most a §10 variant.

## 4. State machine

### 4.1 Current state

- An hourly cron at `:07` (`proxy/wrangler.jsonc:33-35`). The `scheduled`
  handler passes the trigger's `scheduledTime` (`proxy/src/index.ts:123-130`).
- One run looks at UTC today … today + 3 (`GENERATION_AHEAD_DAYS = 3`,
  `shared_generation.ts:28`), nearest first, and makes **at most one**
  Anthropic call (`:156-180`).
- `attempts:{date}` → `{count, leaseUntil}` (`:53`, `:58-62`). The attempt is
  counted **before** the call (`:191-195`). Cap `MAX_ATTEMPTS_PER_DATE = 3`
  (`:31`). Lease = timeout + 30 s = 120 s (`:41`, `:45`). TTLs: set 35 days,
  attempts 7 days (`:47-48`).
- `set:{date}` is write-once. It is read again right before the write
  (`:219-222`), and the read route reads only this key
  (`shared_read.ts:98`, `setKey` at `shared_daily_test.ts:440`).

### 4.2 Proposed keys (all in `DAILY_SETS_KV`)

| Key | Value | TTL | Written by |
|---|---|---|---|
| `pending:{date}` | `{date, promptVersion, generatedAt, generation, questions}` (validated, in plan order) | 4 days | generation run |
| `set:{date}` | as now, plus `checkedAt`, `checkModel`, `checkVersion`; questions may carry `acceptedAnswers` | 35 days (unchanged) | check run |
| `attempts:{date}` | `{generations, checks, leaseUntil}` | 7 days (unchanged) | both runs, **before** the call |
| `review:{date}:{generation}` *(optional, owner decision)* | pending set + checker output + decision | 14 days | check run |

`pending:*` is **structurally unreadable** by clients: the read route builds
only `set:{date}`. P6 adds a test for it. `review:*` is the only place a
rejected set and the checker's reasoning survive. That is useful for
measuring checker false alarms in the first weeks. It is content in KV, not
in logs, which the privacy contract does not cover (it covers log lines).

**Read-route guard (recommended):** `responseBody` (`shared_read.ts:59-70`)
additionally requires `checkVersion` to be a number. A record the checker
never saw (a v1 set, or anything written by a rolled-back Worker) then answers
404. That makes "never serve an unchecked set" a property of the read route
too, not only of the cron.

### 4.3 One run (still one Anthropic call at most)

For each date from UTC today to today + 3, nearest first:

1. `set:{date}` exists → next date (a KV read only, as now).
2. Lease active → next date.
3. `pending:{date}` exists:
   - `checks` < `MAX_CHECKS_PER_DATE` (3): count the check, then call the
     checker. **Publish:** write `set:{date}` (only if still absent), then
     delete `pending`. **Reject:** delete `pending` (and write `review` if
     enabled). **Check failed** (upstream, timeout, unreadable): keep
     `pending` for the next run. **Stop the run.**
   - Checks used up → delete `pending` and next date. The date then needs a
     new generation, if generations are left.
4. No pending, `generations` < `MAX_GENERATIONS_PER_DATE` (3): count the
   generation, generate, validate (P1 rules + the diff rule). Valid → write
   `pending:{date}`. Invalid → nothing written. **Stop the run.**
5. Otherwise → next date.

Generation and check are never in the same run (owner rule). A date needs at
least two runs. A check always sees a pending set that is at least an hour
old, so KV's ~60 s propagation and negative-lookup caching do not matter.

### 4.4 Counters and cap

- The counters are separate because the two calls cost different amounts and
  fail for different reasons, and the log needs to tell them apart. Both are
  counted before the call, like today.
- **Per-date ceiling: 3 generations + 3 checks = 6 paid calls.** A check
  failure (network, timeout) uses a check without using a generation.
- The P0 report's ceiling was 3 calls per date. It doubles.

### 4.5 Cost

Generation v2 ≈ $0.030 (measured $0.028 on 2026-09-26 + §1.2). Check ≈ $0.042
(Sonnet 5 + thinking, estimate).

| Case | Calls | Per day |
|---|---|---|
| Normal, first set passes | 1 + 1 | ≈ $0.07 |
| Expected at *p* = 0.10 / 0.20 (§2.6) | 1.58 / 2.12 pairs | ≈ $0.11 / $0.15 |
| Worst per date (all caps) | 3 + 3 | ≈ $0.22 (≈ $0.41 with Opus 5 as the checker) |
| Worst month (every date at the cap, never in practice) | | ≈ $6.5 |

For comparison: the P0 design was $0.023–0.028 normal and $0.084 at worst.
One 1.0.0 device-day costs about $0.025. The new normal is about 3 device-days
per day, independent of the number of users. A one-off extra comes from
regenerating the v1 dates (§7): ≈ 4 × $0.07.

KV writes (Free: 1,000/day per account, shared with the `QUOTA_KV` counters):
normally 2 (generation: attempts, pending) + 3 (check: attempts, set, delete
pending) = **5/day**, or 6 with `review`. Worst per date: 18.

### 4.6 Timing

The earliest read of date D is UTC (D−2) 10:00: a UTC+14 user prefetching
tomorrow (P0 report §3). Date D enters the horizon at UTC (D−3) 00:00.

| Case | Published at | Margin before the earliest read |
|---|---|---|
| Normal: generation at (D−3) 00:07, check at 01:07 | (D−3) 01:07 | ≈ 33 h |
| All 6 calls used, one date in flight | (D−3) 05:07 | ≈ 29 h |
| Two dates in flight at once (nearest first), worst | (D−3) ~11:07 | ≈ 23 h |

The one-hour delay between generation and check costs 1 hour per attempt
pair. **UTC today + 2**, the latest date a client can ask for, is always
published a day or more before that. **No change to the generation horizon
is needed.** `GENERATION_AHEAD_DAYS` and the serving window stay as they
are. A date that exhausts its caps stays empty, and clients use the fallback
pool (§6).

## 5. CPU (Workers Free: 10 ms per invocation)

### 5.1 What is known

- Measured: the highest cron CPU so far is **8.73 ms**, on the first
  generation. That is **87% of the limit**; margin ≈ 1.3 ms. No
  per-step breakdown exists. The logs record duration, not CPU per step.
- The JSON work in a generation run today is small. Up to 11 KV reads
  (4 sets, the attempt record, 7 avoid-list sets; `shared_generation.ts:84-100`
  parses each of the 7 older sets in full, ~6–7 KB each). Then
  `JSON.stringify` of the request (~8 KB with the system prompt and schema),
  `response.json()` of the envelope (~8 KB) and `JSON.parse` of the text block
  (~6 KB) (`anthropic.ts:497`, `:527`), `validateSharedSet`, one
  `JSON.stringify` of the set, and 2 KV writes.
- The first run had **no** older sets, so no avoid list, and was still the
  most expensive. **Hypothesis, not a measurement:** a large share of the
  ~8 ms is fixed per-invocation cost (script start-up, the TLS/`fetch`
  machinery), not the JSON work. If that is right, splitting the work does
  not halve CPU. Each phase pays the fixed part.

### 5.2 Per phase (estimate)

| Phase | Work beyond the fixed cost | Expectation |
|---|---|---|
| Idle run | ≤ 8 small KV reads | well below today's runs |
| Generation (v2) | As today (avoid list, request, parse, validate) + the diff rule (µs) + write `pending` instead of `set` | ≈ today: up to ~8.7 ms |
| Check | Parse `pending` (~7 KB), build the request (~10 KB), parse the envelope and the checker output (~6–10 KB, thinking blocks are in the envelope), the decision (µs), `acceptedAnswers` normalization (µs), write `set` (+ `review`) | Similar to generation. **Not provably below 10 ms** |

Neither phase can be assumed safe with a 1.3 ms margin. **A CPU kill after
the Anthropic response arrived is the costly failure**: the call is billed
(`anthropic_usage` is logged before parsing, `anthropic.ts:505-508`), the
result is lost, and the next run repeats it until the cap. Signature in the
logs: an `anthropic_usage` line with no `shared_set_generation` /
`shared_set_verification` line for the same run.

### 5.3 Measurement plan

1. **Before deploy (no API cost):** a local Node micro-benchmark of each
   phase's pure work (parse, build, validate, decide) on recorded
   responses, including a realistic checker response with thinking blocks.
   It shows the JSON share of the budget. It does not reproduce Workers' own
   accounting.
2. **After D3:** CPU time per invocation from the same source as the 8 ms /
   8.73 ms readings (Workers Logs / dashboard), split by run type via the log
   line of that run. Watch 3 days: generation, check and idle runs, max and
   typical.
3. Threshold: any run ≥ 9.5 ms, or any "exceeded CPU" run → act.

### 5.4 If the limit is exceeded

1. **Trim the avoid list.** At publish time, also store `answers:{date}`: the 5
   correct answers, ~200 bytes. The next generations read 7 small values
   instead of parsing 7 full sets. +1 KV write per day.
2. **Drop redundant work.** The check run need not re-run `validateSharedSet`
   (the pending set already passed it). Only the `acceptedAnswers` rules run.
3. **Smaller checker input:** send only the fields the check needs (no
   `id` slugs in the prompt beyond an index).
4. **Workers Paid, $5/month.** 30 s CPU per cron run, and KV writes are no
   longer capped at 1,000/day. **This is a cost increase** and reverses the
   2026-09-26 "stays Free" decision. Owner decision.

## 6. Failure policy

| Event | Result |
|---|---|
| Check: network error, HTTP error, timeout | `checks` +1, `pending` kept, retried next run, logged `upstream_failed` |
| Check: output unreadable (§2.3 row 0) | Same as above, logged `check_unreadable` |
| Checks used up | `pending` deleted; a new generation if any are left, else the date stays empty |
| Generations used up | Date stays empty (as today) |
| Kill switch off | No KV, no Anthropic (as today). `pending` expires by TTL; when switched back on, a still-present `pending` is checked |

**Fail-closed: yes, recommended without exception.** An unchecked set is
never published, and there is no switch that skips the check. Such a switch
would be the one path back to the defects this work exists to stop.
Consequence: during an Anthropic outage longer than the ~1–1.5-day margin
(§4.6), dates stay empty and 1.1.0 clients get the **bundled fallback pool**
(7 owner-reviewed sets, P0 report §5, §13 item 3). **That is acceptable, and
it is better** than an unchecked set. The fallback content was reviewed by
the owner. The `set_source = fallback` analytics value makes those days
visible. The legacy route for 1.0.0 is not affected.

Timeout: the check gets its own constant (`CHECK_TIMEOUT_MS`, proposed 120 s).
With thinking, a check can take longer than its token count suggests. The
lease becomes timeout + 30 s, per phase. If §10 shows the generator with
thinking, `GENERATION_TIMEOUT_MS` (90 s) has to be revisited too.

**Kill switch and rollback:** one var, `SHARED_DAILY_TEST_ENABLED`, still
gates both phases and the read route. **Warning for rollback:** rolling back
to `5089ae26` restores the single-phase cron, which **publishes unchecked
sets** for any missing date, and restores that version's vars (switch
`"true"`). The rollback procedure therefore becomes: turn the switch off
first, then roll back, then check the var. This goes into
`proxy/README.md`.

## 8. `acceptedAnswers` schema

### 8.1 Field

In each published question: `acceptedAnswers: string[]`, **always present**
in v2 sets (possibly empty). Absent in legacy, day-0, fallback and v1 sets. The
client reads a missing field as `[]`. Written only by the check run, never by
the generator's schema. The generator is asked for a single answer, and the
checker adds alternatives.

### 8.2 Validation rules (proxy, P5)

1. At most 2 entries (§2.3 rule 6). Each is a string, non-blank, ≤ 300
   characters.
2. `normalizeAnswer` is non-empty. Neither normalized nor folded does it equal
   `correctAnswer` (dropped, §2.3).
3. Pairwise distinct after normalization and folding.
4. No entry equals or folds to any `commonWrongAnswers[].answer` (reject,
   rule 8). Such a wrong answer would be unreachable, and its comment would
   be wrong.
5. `error_correction`: no entry equals the normalized `context` (reject,
   rule 7).

**Grading order (the contract C1 implements):** correct → keyboard variant of
correct → **accepted (exact, then keyboard variant)** → predicted wrong →
fallback. Rules 2–4 guarantee each branch can be reached.

### 8.3 Shared fixture

The normalization fixture already exists
(`proxy/test/fixtures/answer_normalization.json`, 28 normalize/fold cases,
produced from the Dart functions). P5 adds a **grading fixture**
(`proxy/test/fixtures/daily_test_grading.json`): a question with
`correctAnswer`, `acceptedAnswers` and `commonWrongAnswers`, and a list of
`input → expected kind`. The proxy tests it against a TS port of the order
above, and C1 tests `checkDailyTestAnswer` against the same file. Neither
side can drift without a red test.

### 8.4 Client, C1 (summary only)

- `DailyTestQuestion`: an `acceptedAnswers` field, lenient `fromJson`
  (missing or non-list → `[]`), and in `toJson` so the local cache keeps it
  (`lib/models/daily_test_question.dart:78-103`).
- `checkDailyTestAnswer` (`lib/utils/answer_matching.dart:127-168`): the new
  branch, with a new `AnswerMatchKind.accepted` carrying the matched
  alternative.
- It counts as correct: `DailyTestAnswerResult.isCorrect`
  (`lib/models/daily_test_completion.dart:85-87`). So it is never "Needs work",
  never goes to the error profile, and counts in `computeDailyTestScore`
  (Home, `lib/screens/home_screen.dart:856`).
- The result screen shows it as correct, with the key as "also correct: …".
  The copy is an owner decision in C1.

as `shared_set_generation` (`shared_generation.ts:102-133`):

```json
{"event":"shared_set_verification","date":"2026-10-08","generation":1,"check":1,

```

- `outcome`: `published | rejected | upstream_failed | check_unreadable |
  already_published`.
- `reason`: the §2.3 code of the **first** failing question (fixed
  vocabulary). `questions_rejected`: how many failed (a count). It shows
  whether a set failed on one question or on all of them, which is what
  decides §2.6's option (ii).
- **No content:** no question, answer, alternative or rule text, and no
  question id (ids are model-written slugs). The existing planted-secret
  tests extend to it.

`shared_set_generation` gains the outcome `pending` (stored, awaiting the
check) in place of `published` for v2 generations. `published` now appears
only on the verification line.

### 9.2 `usageKind`

Today: `generate_daily_test` and `generate_shared_daily_test` → `daily_test`
(`proxy/src/usage_log.ts:7-11`). Options for `check_shared_daily_test`:

- **(A) `daily_test`** (recommended). `kind` answers "what does the Daily
  Test cost". The check is part of that cost, and leaving it out would
  overstate the saving. `operation` still separates it.
- (B) a new kind `daily_test_check`. It changes the `UsageKind` vocabulary and
  every consumer of the two-value split, for information that `operation`
  already carries.

**Verifying the saving** changes accordingly. Shared cost per day = the sum
over `generate_shared_daily_test` + `check_shared_daily_test` usage lines. The
P0 formula "billed but not published" becomes: usage lines of both operations
minus `published` verification lines. A usage line with no matching
generation or verification line in the same run is the CPU-kill signature
(§5.2).

### 13.2 A. Over-generation and slot-only regeneration

Three strategies, with *p* = the per-question defect rate (true defects plus
checker false alarms):

- **S1, one set, rejected whole** (the §4 design).
- **S2, over-generate:** one generation call asks for 2 candidates per plan
  slot (10 questions, same topic and type as the slot). The checker checks
  all 10. Per slot, a clean candidate is chosen, preferring one with no
  `acceptedAnswers`, then the first. The set is published when every slot has
  one.
- **S3, repair the slot:** a full set is generated and checked. Only the
  failing slots are regenerated in a later run (a smaller prompt: the slot
  plus the questions that are kept, to avoid repeats) and checked in the run
  after that. Up to 3 generation calls and 3 checks per date, as decided.

Probability and expected cost per date. Independence between questions is
assumed, which flatters S2 and S3 if a topic–type pair is hard every time

generation (v2 ≈ $0.030; 10 questions ≈ $0.054) + Sonnet 5 check with thinking
(5 questions ≈ $0.042; 10 ≈ $0.060). S3: ≈ $0.027 per repaired slot
(generation + check). All token counts are estimates until E.

**Recommendation:** choose after E, on measured *p*, tokens and CPU. The
starting assumption: **S2 if its CPU fits**, because it is the only strategy
whose publish rate barely depends on *p*, and it keeps the set written in one
call. **S3 if S2 does not fit in 10 ms.** S1 only if v2 alone reaches
*p* ≈ 5%. E measures S1 and S2 directly. S3 is **simulated** from S1's
per-question outcomes and per-question token counts, because its slot prompt
would only be written if S3 is chosen. That is a stated assumption: a
regenerated slot is as good as a first-attempt question.

### 13.3 B. `claude-sonnet-5` as the generator

- **Scope:** the shared operation only. `MODEL` (`anthropic.ts:13`) is
  shared by every route today, so the shared operation gets its own model
  constant, and the legacy request stays byte-identical (pinned test).
- **Cost on the list price alone** looks lower ($2/$10 vs $3/$15). On measured
  tokens it may not be. The same text counts ~30% more tokens (§13.1), and
  adaptive thinking adds billed output tokens. Estimate for one 5-question
  set: Sonnet 4.6 v2 ≈ 1,830 in / 1,600 out ≈ **$0.030**. Sonnet 5 ≈ 2,380 in
  / 2,080 out + ~1,500–3,000 thinking ≈ **$0.041–0.056**; without thinking
  ≈ $0.026. **E settles it with measured `usage`.**
- **The request shape for Sonnet 5** has no sampling parameters (none are sent
  today) and an explicit `thinking` setting. E measures with thinking on,
  because correctness is the goal. Thinking off is a later cost lever.
- **Coupling with decision 6.** The checker must differ from the generator
  and be at least as strong. If E picks `claude-sonnet-5` as the generator,
  the default checker candidate (`claude-sonnet-5`) is excluded, and
  `claude-sonnet-4-6` is not stronger. The remaining candidate is
  **`claude-opus-5-5`** ($4/$20; check ≈ $0.085, estimate), so E also runs it
  on the Sonnet 5-generated sets and the reference sets (§13.6). That
  combination costs ≈ $0.13 per attempt. It is still independent of users.

### 13.4 C. Message Batches API

**How it would fit the two-phase design.** One run submits a batch of one
request and stores `batch:{date}` (`{id, kind, submittedAt}`). Every later
run polls it (one small GET). When it has ended, the run downloads the one
result line and processes it exactly as today's response. With the
no-generation-and-check-in-one-run rule, that is 4 runs at minimum: submit
generation → collect + validate + `pending` → submit check → collect +
decide + publish.

| Aspect | Effect |
|---|---|
| Saving | 50% of token cost: a normal day ≈ $0.07 → $0.036, **≈ $1.1/month**; the worst date ≈ $0.22 → $0.11 |
| Latency | "Most" batches end within an hour, but the only bound is 24 h, and "processing may be slowed down based on current demand". Two slow phases can take 48 h, more than the ≈ 33 h margin (§4.6). |
| Horizon | Has to move from +3 to **+5**, so that two slow phases plus one retry still fit: date D enters at (D−5) 00:00, and the earliest read is (D−2) 10:00, ≈ 82 h. That is a constant, but it means sets exist longer before use (a longer pull window if a bad one slips through) |
| CPU | No more than today, and a little less per run: a submit run builds a request and gets a small JSON back, a poll run parses a few hundred bytes, a collect run parses the same ~8 KB as today. Batch does not hurt the 10 ms budget |
| Caps | Counted at submit, as today. An expired request is not billed but still uses an attempt (conservative) |
| State and code | New `batch:*` keys, polling, `expired` / `errored` / `canceled` results, a results download, and log lines whose duration means "submit → collect". The state machine roughly doubles |
| Accounting | `anthropic_usage` would be written at collection; "billed but not published" still works per `custom_id` (the date) |
| Data | Results stay in the workspace for 29 days: generated content only, no user data |

**Decision (as asked, the evaluation decides): not in the production cron in
1.1.0.** Saving about $1 a month does not pay for doubling the state machine,
moving the horizon to +5, and publication times that depend on Anthropic's
queue. Revisit only if the shared pipeline's daily cost grows several-fold,
or if more cron work is added. **Use it for E**, where nothing waits on the
result and the matrix is large: it halves E's cost (§13.6). E keeps a small
synchronous subset, because only a synchronous call measures wall time, and
the timeouts depend on that.
