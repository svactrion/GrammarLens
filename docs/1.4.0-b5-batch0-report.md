## 1. Translation method, batching and order

**Method (D6):** written in this session, key by key from `app_en.arb`,
each key's description as the brief. The descriptions already say where a
string sits, its length budget ("Short: one of three segments"), what is
uppercase in English, and which names are never translated. Fixed in
every language:

- **Feature names, verbatim:** Daily Test, Topic Practice, Review, Monthly
  Climb, Premium, including inside sentences (Turkish attaches suffixes
  with an apostrophe: "Daily Test'i"; German keeps the English noun:
  "der Daily Test"). The four `feature*` keys keep their English value.
- **Names, verbatim:** GrammarLens; Anthropic, Claude, Anthropic (Claude);
  Figma Community; Cute Animal 3D Icons, Tran Mau Tri Tam, CC BY 4.0;
  IELTS, TOEFL.
- **English content inside interface strings stays English:** the topic
  descriptions' example sentences ("I enjoy swimming"); the hint cards are
  not in the ARB at all (B3 §8 Q2), nor are the questions and the AI
  feedback (D2). Topic, theme, medal, save point and avatar names are
  translated.
- **Uppercase labels** (YOU WROTE, DAILY TEST, FREE …) are uppercase only
  where the script has case; ja, ko and ar use the plain form.

**Batching (proposed):** one language per commit, all 477 keys at once,
each commit green on its own: the new `app_<lang>.arb`, the completeness
test of §5 passing for it, the layout test of §4 run for it, and its
back-translation file (§2). A language never lands half-done, so the
picker never offers an incomplete one (§6).

**Order (proposed):** Turkish first (the owner reads it, and it sets the
tone for the rest), then German, Spanish, Portuguese (Latin script, the
longest strings), then Japanese and Korean, then Arabic last (right to
left; its layout is B6). Seven commits, then one commit for `Info.plist`
and the picker test (§6), then one push.

## 2. Back-translation check (D6)

**What:** for each target language, the legal- and App-Review-weight
strings translated back into English and set beside the original, so the
owner can compare meaning without reading the target language.

**Which keys (proposed, 83):** the 32 flagged in B4 (the AI permission
screen's heading, intro, "What is sent", "Who receives it", "What is never
sent"; onboarding's privacy note and every "Your data & AI" row; the
Data screen's AI line; the paywall's benefit lines, prices, trial, billing,
button and renewal terms, cancelled and pending messages) plus 51 that
complete those screens: the AI permission screen's remaining headings and
buttons ("Agree and continue", "Not now" and its note, the personal-details
line, "Change this any time"), the Data screen's switch and its states,
the practice "not sent" message, the paywall's plan names, saving badge,
"per {period}", every period, span and trial-length form, the comparison
rows, restore and purchase outcomes. 83 × 7 = 581 lines.

**How (proposed):** a separate pass per language by a subagent that is
given only the target strings and their keys, never the English, and asked
for a literal English rendering. **Limit, stated:** it is the same model
family that wrote the forward translation, so it is a consistency check,
not an independent review; it catches dropped clauses, changed numbers,
a trial that became a discount, "auto-renews" lost, a recipient changed.

**Where and in what format:** `docs/translations/back-translation-<lang>.md`,
one Markdown table per language, committed with that language:

| Key | English (original) | Back-translation | Δ |
|---|---|---|---|
| `paywallDisclosureTrial` | {span} free, then {pricePerPeriod}, auto-renews unless cancelled. | … | ✓ / note |

The Δ column is mine: ✓ when the meaning matches, otherwise one line on
the difference and whether the target string was changed. The target
language itself is not in the table (the owner compares English to
English); it is one click away in the ARB. The owner signs off per file.

## 3. Plural and grammar risks

### 3.1 Plural categories

| Language | CLDR categories | What the 31 plural keys need |
|---|---|---|
| ja, ko | other | `other` only; the counter word carries the meaning ("{count}問", "{count}문제"). `=1` cases may be dropped. |
| tr | one, other | Turkish nouns stay singular after a number ("5 soru"), so `one` and `other` read alike; keep both, identical where natural. |
| de, es, pt | one, other | Straight `one` / `other`. pt-BR: `one` covers 0 and 1 in CLDR for pt ("0 ponto"), check each. |
| ar | zero, one, two, few, many, other | **All six**, each with its own noun form: dual for 2, plural for 3–10, singular accusative for 11–99. `=1` alone is not enough. The completeness test (§5) requires the six in every Arabic plural message. |

The 31 plural keys: `settingsMedalsEarned`, `practiceDailyLimitBody`,
`lengthPickerSemantics`, `lengthPickerStart`, `keyboardNoteTyped`,
`recencyDays`, `recencyWeeks`, `recencyMonths`, `frequencyTimes`,
`topicStatsPracticed`, `topicStatsWeakSpots`, `homeDailyUnitQuestions`,
`reviewDailyRemaining`, `reviewFocusCount`, `weakSpotRemaining`,
`topicPracticeCount`, `medalPoints`, `medalPointsUnit`, `medalActiveDays`,
`monthCardSteps`, `monthCardNearMiss`, `paywallBenefitWeakSpotsBody`, and
the nine paywall period and span forms (`paywallPeriod*`, `paywallSpan*`,
day/week/month/year, plus `paywallSpanUnknown`).

### 3.2 Unit words split from their number

Three keys are a bare unit next to a number the code draws in another
style: `homeDailyUnitQuestions` ("5" + "questions"), `medalPointsUnit`
("120" + "points"), `monthCardSteps` ("12 / 30" + "steps"). They work in
every language as long as the unit follows the number; ja/ko put a
counter after the number too ("5" "問"), Arabic reads right to left with
the number first in logical order. Risk only in the visual pairing, B6.

### 3.3 Placeholders that move

94 keys carry placeholders; the translations reorder them freely (ICU
names, not positions). Watch-points:

- **Turkish suffixes on placeholders:** never attach a case ending to a
  `{name}`, `{tier}`, `{month}`, `{topic}` (vowel harmony depends on the
  value). Rephrase instead ("{topic} konusunda").
- **Arabic gender and number agreement** with `{tier}` and `{theme}`
  (medal and theme names are nouns with gender): use constructions that
  do not inflect around the placeholder ("ميدالية {tier}").
- **German case and gender** around `{tier}`, `{plan}`, `{theme}`: likewise.
- **Sentences the code concatenates** (the order is fixed in code, not in
  the ARB): the climb score bar's "… {tier} reached." appended with a
  space; the plan card's VoiceOver pieces (`paywallPlanSemantics` +
  `paywallPlanSemanticsMonthly` + detail + `paywallPlanSemanticsReference`,
  each with a leading comma); the keyboard note's two clauses; the medal
  progress card's "Top medal " / "Next medal " + tier span. All VoiceOver
  or label-value pairs, safe with a colon or comma in the target; noted per
  language in the commit if a target needs a different joiner.
- **List separators in code:** `_joinWithOr` (the paywall's "3, 5 or 10",
  visible) joins with ", " and the VoiceOver lists (save points,
  thresholds, the hint card's points) with ", " or ". ". Japanese uses
  "、", Arabic "،". §8 Q5 proposes one `listSeparator` key.

### 3.4 Register and forms of address

Proposed (§8 Q2): German **du**; Spanish **tú**, neutral Latin American
vocabulary, no *vosotros* (one text for Mexico and Spain, D1); Brazilian
Portuguese **você**; Turkish **sen**, friendly, matching the English
tone; Japanese polite **です・ます**, buttons as plain nouns or verbs
("始める"); Korean polite **해요체**, buttons as nouns ("시작하기"); Arabic
Modern Standard, second person masculine generic where a verb needs a
gender, gender-free nominal phrasing where it reads naturally.
Gendered adjectives elsewhere (Spanish "Bienvenido/a") are avoided by
phrasing ("Te damos la bienvenida").

### 3.5 Numbers and dates

- **Counts and scores** are `int` placeholders without a format, so they
  print with Latin digits in every language (Dart `toString`).
- **Dates** come from `DateFormat` in the interface locale: month names
  translate themselves (ja "10月", ko "10월", ar "أكتوبر"). For Arabic,
  intl may print Arabic-Indic digits in "أكتوبر ٢٠٢٦" while the counts
  beside it are Latin. §8 Q4 proposes Latin digits everywhere
  (`DateFormat.useNativeDigits = false` for `ar`), to be verified in B5.
- **Prices** come from the App Store already formatted for the storefront;
  the monthly equivalent uses `NumberFormat.simpleCurrency` on the device
  locale. Neither is translated.
- **"pts", "/day"** (`medalGoalPoints`, `medalThresholdPoints`,
  `paywallFreePerDayShort`) are abbreviations: each language gets its own
  short form ("Pkt.", "puan", "نقطة").

**Proposed check (B5):** a test, `test/l10n_layout_test.dart`, that for
every locale pumps each site above at 320 × 568 and the Large text size
(with the bundled Nunito Sans, as the existing layout tests do) and
asserts: no layout exception (`tester.takeException()` is null), and no
`RenderParagraph` that is a one-line label not meant to truncate has
`didExceedMaxLines` (an allowlist names the two that truncate by design:
page titles, the greeting's name). It runs in the suite, so a later string
change that overflows fails it. The existing manual sweep
(`tool/design_measure/v120/text_size_sweep_test.dart`) gets a
`DESIGN_MEASURE_LOCALE` switch for the full-screen report per language.

**Limit, stated:** Nunito Sans has no Japanese, Korean or Arabic glyphs,
and `flutter test` has no system font fallback, so those three languages
are measured with fallback boxes, not the real fonts iOS uses. The test
catches gross overflow there; real widths and heights are the device's
(Arabic in B6, ja/ko in the §7 pass).

## 5. Completeness and the untranslated heuristic

**Proposed test, `test/l10n_completeness_test.dart`** (replaces the
untranslated-messages file B3 dropped), for every `app_<lang>.arb`:

1. **Same keys** as `app_en.arb` (the target files carry values only, no
   `@` metadata: the descriptions live in the template).
2. **Same placeholders** per key, by name; a plural key stays a plural.
3. **Plural forms:** Arabic plural messages define `zero`, `one`, `two`,
   `few`, `many` and `other`; every other language at least `other`.
4. **Names survive:** every feature name, the brand and the fixed names of
   §1 that occur in the English value occur verbatim in the target value.
5. **Not left in English:** a target value identical to the English one
   fails, unless the key is on a per-language allowlist with a reason.
   Known-English exceptions in every language: `featureReview`,
   `featureDailyTest`, `featureTopicPractice`, `featurePremium`,
   `offerChip` and `paywallHeaderPremium` ("PREMIUM"); per language, words
   that are the same by nature (de "Gold", "Bronze", "Standard"; es/pt
   "Premium"-only values; tr none expected). The allowlist is reviewed in
   each language's commit.
6. **Script check for ja, ko, ar:** a value with letters must contain at
   least one Kana/Han, Hangul or Arabic character respectively, unless
   allowlisted (values that are only a feature name).

gen-l10n itself rejects malformed ICU, so syntax is covered by the build.

## 6. iOS and the picker

- **`CFBundleLocalizations`** in `Info.plist`: `en`, `ja`, `ko`, `es`,
  `pt-BR`, `tr`, `ar`, `de`. iOS then lists GrammarLens under Settings →
  Language with these, and a per-app choice of "Português (Brasil)"
  arrives as `pt-BR`, which resolves to the `pt` strings
  (`resolveAppLocale`). Xcode's `knownRegions` gets the same eight. No
  `InfoPlist.strings` (no usage descriptions; the display name is the
  brand). Added in the commit after the last language, so iOS never offers
  a language the app cannot show.
- **The picker** offers a language once gen-l10n has its ARB
  (`AppLanguage.available`); with §5's test red on any missing key, an
  incomplete ARB cannot be committed, which is B3's rule enforced. A test
  then pins `AppLanguage.available()` to all nine entries (System default
  and the eight).
- **Endonyms** (unchanged, never translated): English, 日本語, 한국어,
  Español, Português (Brasil), Türkçe, العربية, Deutsch.
