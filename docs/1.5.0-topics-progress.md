## Phase A — what was built

`npm run eval -- topics --dry-run` and `npm run eval -- topics run [--out DIR]`
(from `proxy/`). Code: `proxy/eval/lib/topics_measurement.ts` (the plan, the
request bodies, the built answers, the estimate), `proxy/eval/lib/topics_checks.ts`
(the gate and the five automatic checks), the two commands in
`proxy/eval/run.ts`. One change in the Worker's source, with no change in
behaviour: `buildGeneratePracticeSetBodyFor` takes a third parameter
(decision T-1).

The run has three stages and then the checks:

1. **Generation.** For each first-wave topic 6 Topic Practice sets of 5
   questions, and 3 sets of the control topic `articles`: 33 calls, 165
   questions. The request is what the proxy sends for Topic Practice today
   (`PRODUCTION_PRACTICE`: `claude-sonnet-5-5`, effort `low`, the D3 prompt,
   the same schema and token budget), with the first-wave topics known for
   that request only.
2. **Answers.** A practice question carries no answer key (T-2). One harness
   call per generated set (`claude-sonnet-5-5`, `low`) writes, per question:
   the key, a second correct answer when one really exists, and two typical
   learner mistakes (a written sentence: one right sentence and one with a
   mistake). The verdict of each answer is by construction: key and second
   answer right, mistakes wrong.
3. **Scoring.** Every built answer goes through the production scoring cell
   (`PRODUCTION_SCORING`, 1.4.0's C8: `claude-haiku-5-5`, `low`, D3 + D11),
   one generated set's questions per call, as the app sends a finished set.
4. **Automatic checks**, per question, written to `checks.json` in the run
   folder: about its topic; one natural answer per blank; duplicates inside
   a set and across sets; length and level; the hint card against the key.

A run folder (`proxy/eval/out/topics-…`, gitignored) holds `records.json`
(every call with its tokens, cost, time and parsed output), `progress.log`,
`sets.json` (the gate per set), `items.json`, `answers.json`,
`answer-problems.json`, `scoring-calls.json`, `checks.json` and
`run-report.md` (measured against the estimate, and the checks per topic).

## Decisions

Question · options · choice · why.

- **T-1 How the measurement turns the first-wave topics on.** Flip the
  constant for the run · an environment variable · a parameter on the
  request builder. **A parameter:** `buildGeneratePracticeSetBodyFor(req,
  variant, firstWave = FIRST_WAVE_TOPICS_ENABLED)`. The routes never pass it,
  so the Worker's behaviour is unchanged; a test holds that the route still
  refuses the five ids and that the constant is `false`. An environment
  variable would be a second switch someone could leave on.
- **T-2 Where the answers come from.** `TOPICS.md` speaks of "the key" and
  "an accepted variant when the item lists one", but a practice question has
  neither: the practice path returns `id`, `type`, `context`, `instruction`,
  `hint`. Rules in code (cannot write a corrected sentence or a learner's
  sentence) · take the scorer's own corrected answer as the key (circular:
  the scorer would be judged by itself) · one harness call per set that
  writes them. **The harness call**, as 1.4.0's S-free writer was
  (`claude-sonnet-5-5`, `low`): 33 calls, about $0.57. Consequences: the key
  is model-written, so a wrong key shows up as a scoring disagreement and is
  settled by the owner's labels in phase C; the phase B report says so up
  front. The writer is told that a second answer counts only when it differs
  in the tested structure (not a contraction or a spelling).
- **T-3 The control topic.** Any of the five live topics. **`articles`,**
  3 sets: like prepositions and relative pronouns it is a closed word class,
  and those are the two new topics where "several answers fit" is most
  likely, so the control shows whether a flag rate is new or the baseline.
- **T-4 What "the quality gate" of the practice path is.** There is no
  semantic gate on that path: the Worker returns the model's output as it
  is, and the app's parser needs an id, a known type and an instruction.
  **The measurement's gate:** that acceptance (1.4.0's `sGenItemsFrom`)
  plus the prompt's rules a program can check: a fill-in-the-blank question
  has 1 to 4 blanks, an error-correction question carries a sentence of at
  least 3 words; and per set, 5 questions in the 2 : 2 : 1 mix the request
  names. The report gives the pass rate per set and per question.
- **T-5 Which answers share a scoring call.** 1.4.0's one shuffle over all
  answers · per generated set. **Per set:** a call holds answers to one
  set's questions, at most one per question and five in all, right and
  wrong mixed by a shuffle fixed per set. It is what the app sends, and a
  resumed folder scores only the sets that are new. Cost: 132 calls at most
  instead of 106 (about $0.03 more). The id the scorer sees for an answer
  is opaque (`a` + eight hex digits): it cannot read the verdict from it.
- **T-6 "Length and level within the existing limits".** The limits that
  exist: the proxy's 2,000 characters for a question's text and 100 for an
  id (a longer one could not be scored at all), the prompt's one-sentence
  instruction, and the shared Daily Test's rule that a correction changes
  one run of at most 4 words (applied to the written key). There is no
  existing limit for level, so two proxies: a sentence over 35 words, or two
  or more words of 15 letters or more in one question. Whether a question is
  B1–C1 is the owner's judgment in phase C.
- **T-7 What an automatic check is.** A word-level rule that knows nothing
  about meaning: it raises a flag for a person to look at, never a verdict,
  and the report will show how the flags relate to the owner's labels.
  - *Topic:* the text names the topic, or the key shows the structure; for
    prepositions and articles the blank or the correction must be of that
    word class.
  - *One natural answer* (fill in the blank only): the writer listed a
    second correct answer, or a blank's key is a word with a known rival in
    that place (who / that in a defining clause, in / at before "station",
    was / were after "if I", a passive with a verb in brackets and no time
    marker, "clever" taking both -er and more…).
  - *Duplicates:* the same words, or at least 60 % of the scenario words
    shared (an error correction's sentence; otherwise the whole text without
    function words and stock instruction words), same topic only.
  - *Hint card:* the app's card for the topic against the key:
    `card_conflict` when the key does what a line says not to (will / would
    in the if-part, "that" after a comma, a superlative without "the", "on
    May 5th" against "in: a period (in May)"), `card_silent` when the card
    has no line for the key's structure (unless, a mixed or zero
    conditional, whom, as … as). The cards are copied into the harness and a
    test fails when a copy differs from `lib/data/topic_hints.dart`.
  - A check that needs the key and has none is recorded as "not run".
  - The control's hint-card and one-answer rules are thinner than the new
    topics' (only a / an by sound, and the writer's second answer), so the
    comparable columns are the gate, topic, duplicates, length and the
    writer's second answers.
- **T-8 The estimates.** Input tokens from each built body with 1.4.0's
  calibrated ratio (2.33 characters a token, an upper bound). Output:
  generation by 1.4.0's formula (1,500; it measured 571); scoring from
  1.4.0's measured C8 mean (2,538 for five answers), because its formula was
  1.7 × too low for Haiku; the writer 1,400 (≈ 200 a question plus
  thinking).
- **T-9 Synchronous calls, not batches.** Batches are half the price and
  take up to 24 hours. **Synchronous, five in flight,** as the 1.4.0
  measurement: the whole run is about $1.30, and each stage needs the one
  before it.
- **T-10 The key.** From `ANTHROPIC_API_KEY` in the environment only (the
  1.4.0 measurement's reader; not `proxy/.dev.vars`), sent to
  `api.anthropic.com`; every file, log line and printed report goes through
  the run's check that refuses text containing it. The dry run needs no key
  and says only whether one is set.
- **T-11 A run that is not complete says so.** Its last line is "topics run
  incomplete: …" and the exit code is 1; the same folder is run again with
  `--out`. Only "topics run done" means the folder is ready for phase B.
