## Phase A — what was built

`npm run eval -- topics --dry-run` and `npm run eval -- topics run [--out DIR]`
(from `proxy/`). Code: `proxy/eval/lib/topics_measurement.ts` (the plan, the
request bodies, the built answers, the estimate), `proxy/eval/lib/topics_checks.ts`
(the gate and the five automatic checks), the two commands in
`proxy/eval/run.ts`. One change in the Worker's source, with no change in
behaviour: `buildGeneratePracticeSetBodyFor` takes a third parameter
(decision T-1).

The run has three stages and then the checks:

1. **Generation.** For each first-wave topic 6 Topic Practice sets of 5
   questions, and 3 sets of the control topic `articles`: 33 calls, 165
   questions. The request is what the proxy sends for Topic Practice today
   (`PRODUCTION_PRACTICE`: `claude-sonnet-5-5`, effort `low`, the D3 prompt,
   the same schema and token budget), with the first-wave topics known for
   that request only.
2. **Answers.** A practice question carries no answer key (T-2). One harness
   call per generated set (`claude-sonnet-5-5`, `low`) writes, per question:
   the key, a second correct answer when one really exists, and two typical
   learner mistakes (a written sentence: one right sentence and one with a
   mistake). The verdict of each answer is by construction: key and second
   answer right, mistakes wrong.
3. **Scoring.** Every built answer goes through the production scoring cell
   (`PRODUCTION_SCORING`, 1.4.0's C8: `claude-haiku-5-5`, `low`, D3 + D11),
   one generated set's questions per call, as the app sends a finished set.
4. **Automatic checks**, per question, written to `checks.json` in the run
   folder: about its topic; one natural answer per blank; duplicates inside
   a set and across sets; length and level; the hint card against the key.

A run folder (`proxy/eval/out/topics-…`, gitignored) holds `records.json`
(every call with its tokens, cost, time and parsed output), `progress.log`,
`sets.json` (the gate per set), `items.json`, `answers.json`,
`answer-problems.json`, `scoring-calls.json`, `checks.json` and
`run-report.md` (measured against the estimate, and the checks per topic).

## Decisions

Question · options · choice · why.

- **T-1 How the measurement turns the first-wave topics on.** Flip the
  constant for the run · an environment variable · a parameter on the
  request builder. **A parameter:** `buildGeneratePracticeSetBodyFor(req,
  variant, firstWave = FIRST_WAVE_TOPICS_ENABLED)`. The routes never pass it,
  so the Worker's behaviour is unchanged; a test holds that the route still
  refuses the five ids and that the constant is `false`. An environment
  variable would be a second switch someone could leave on.
- **T-2 Where the answers come from.** `TOPICS.md` speaks of "the key" and
  "an accepted variant when the item lists one", but a practice question has
  neither: the practice path returns `id`, `type`, `context`, `instruction`,
  `hint`. Rules in code (cannot write a corrected sentence or a learner's
  sentence) · take the scorer's own corrected answer as the key (circular:
  the scorer would be judged by itself) · one harness call per set that
  writes them. **The harness call**, as 1.4.0's S-free writer was
  (`claude-sonnet-5-5`, `low`): 33 calls, about $0.57. Consequences: the key
  is model-written, so a wrong key shows up as a scoring disagreement and is
  settled by the owner's labels in phase C; the phase B report says so up
  front. The writer is told that a second answer counts only when it differs
  in the tested structure (not a contraction or a spelling).
- **T-3 The control topic.** Any of the five live topics. **`articles`,**
  3 sets: like prepositions and relative pronouns it is a closed word class,
  and those are the two new topics where "several answers fit" is most
  likely, so the control shows whether a flag rate is new or the baseline.
- **T-4 What "the quality gate" of the practice path is.** There is no
  semantic gate on that path: the Worker returns the model's output as it
  is, and the app's parser needs an id, a known type and an instruction.
  **The measurement's gate:** that acceptance (1.4.0's `sGenItemsFrom`)
  plus the prompt's rules a program can check: a fill-in-the-blank question
  has 1 to 4 blanks, an error-correction question carries a sentence of at
  least 3 words; and per set, 5 questions in the 2 : 2 : 1 mix the request
  names. The report gives the pass rate per set and per question.
- **T-5 Which answers share a scoring call.** 1.4.0's one shuffle over all
  answers · per generated set. **Per set:** a call holds answers to one
  set's questions, at most one per question and five in all, right and
  wrong mixed by a shuffle fixed per set. It is what the app sends, and a
  resumed folder scores only the sets that are new. Cost: 132 calls at most
  instead of 106 (about $0.03 more). The id the scorer sees for an answer
  is opaque (`a` + eight hex digits): it cannot read the verdict from it.
- **T-6 "Length and level within the existing limits".** The limits that
  exist: the proxy's 2,000 characters for a question's text and 100 for an
  id (a longer one could not be scored at all), the prompt's one-sentence
  instruction, and the shared Daily Test's rule that a correction changes
  one run of at most 4 words (applied to the written key). There is no
  existing limit for level, so two proxies: a sentence over 35 words, or two
  or more words of 15 letters or more in one question. Whether a question is
  B1–C1 is the owner's judgment in phase C.
- **T-7 What an automatic check is.** A word-level rule that knows nothing
  about meaning: it raises a flag for a person to look at, never a verdict,
  and the report will show how the flags relate to the owner's labels.
  - *Topic:* the text names the topic, or the key shows the structure; for
    prepositions and articles the blank or the correction must be of that
    word class.
  - *One natural answer* (fill in the blank only): the writer listed a
    second correct answer, or a blank's key is a word with a known rival in
    that place (who / that in a defining clause, in / at before "station",
    was / were after "if I", a passive with a verb in brackets and no time
    marker, "clever" taking both -er and more…).
  - *Duplicates:* the same words, or at least 60 % of the scenario words
    shared (an error correction's sentence; otherwise the whole text without
    function words and stock instruction words), same topic only.
  - *Hint card:* the app's card for the topic against the key:
    `card_conflict` when the key does what a line says not to (will / would
    in the if-part, "that" after a comma, a superlative without "the", "on
    May 5th" against "in: a period (in May)"), `card_silent` when the card
    has no line for the key's structure (unless, a mixed or zero
    conditional, whom, as … as). The cards are copied into the harness and a
    test fails when a copy differs from `lib/data/topic_hints.dart`.
  - A check that needs the key and has none is recorded as "not run".
  - The control's hint-card and one-answer rules are thinner than the new
    topics' (only a / an by sound, and the writer's second answer), so the
    comparable columns are the gate, topic, duplicates, length and the
    writer's second answers.
- **T-8 The estimates.** Input tokens from each built body with 1.4.0's
  calibrated ratio (2.33 characters a token, an upper bound). Output:
  generation by 1.4.0's formula (1,500; it measured 571); scoring from
  1.4.0's measured C8 mean (2,538 for five answers), because its formula was
  1.7 × too low for Haiku; the writer 1,400 (≈ 200 a question plus
  thinking).
- **T-9 Synchronous calls, not batches.** Batches are half the price and
  take up to 24 hours. **Synchronous, five in flight,** as the 1.4.0
  measurement: the whole run is about $1.30, and each stage needs the one
  before it.
- **T-10 The key.** From `ANTHROPIC_API_KEY` in the environment only (the
  1.4.0 measurement's reader; not `proxy/.dev.vars`), sent to
  `api.anthropic.com`; every file, log line and printed report goes through
  the run's check that refuses text containing it. The dry run needs no key
  and says only whether one is set.
- **T-11 A run that is not complete says so.** Its last line is "topics run
  incomplete: …" and the exit code is 1; the same folder is run again with
  `--out`. Only "topics run done" means the folder is ready for phase B.

## Decisions, phase B

The first three are the owner's (2026-11-18, `TOPICS.md`).

- **T-12 (owner) Every question is labelled, not a sample.** A sample of 10
  per topic · all of them. **All 150 questions of the five new topics and
  the control's 15.** With 10 per topic a topic passes "at most 5 %
  defective" only at 0 defects, and 0 of 10 still leaves a true rate of up
  to 26 % open (95 %); with 30, one defect passes and two fail.
- **T-13 (owner) The built answers are labelled too.** The truth by
  construction · a labelled truth. **Labelled:** by T-2 the key, the second
  answer and the mistakes are model-written, so "right / wrong by
  construction" is a claim; a "mistake" that is in fact acceptable would be
  counted against the scorer. Phase C's scoring metrics use the labelled
  truth, with `unsure` answers counted apart.
- **T-14 (owner) The sheet is blind.** It shows what a learner sees and the
  built answers, nothing else: no automatic flag, no gate result, no scorer
  verdict or explanation, and not which built answer is the key, the second
  answer or a mistake.
- **T-15 Where the sheet and the details file live.** `proxy/eval/data/`,
  where 1.4.0's sheets are (committed) · the run folder. **The run folder**
  (`sheet/`, `private/`): it is the place `proxy/.gitignore` already keeps
  out of the repository, so no generated content can reach a commit, and
  the files stay with the records they came from. Consequence: the filled
  sheet exists only on the owner's Mac; a copy elsewhere is the owner's
  call.
- **T-16 Plain text to read, CSV to fill.** Markdown · plain text for the
  questions. **Plain text:** a blank is a run of underscores, and Markdown
  turns two of them on one line into emphasis. The file to fill is a CSV
  with one row per question, read back with 1.4.0's parser. `n/a` marks a
  letter a question does not have (a dash would be written with a guarding
  apostrophe). `why` may hold more than one reason; `other` needs a note.
- **T-17 What a question shows.** `TOPICS.md` names context, instruction and
  hint. **Also the topic's title and the type as the app names it** ("Fill in
  the blank", "Find and correct the error", "Write a sentence"): a learner
  sees both on the question screen, and "off topic" cannot be judged
  without the topic. A built answer is shown as the app would send it: the
  word(s) for a single blank, the completed sentence for several blanks.
- **T-18 A sheet is never rewritten once it exists.** `topics analyze` reads
  it back instead. `--rebuild-sheet` replaces it only while no row has
  anything in it (used once here, before anyone saw the sheet, to change the
  marker of T-16). Order, keys and letters come from a fixed seed, so a
  rebuild of an untouched sheet gives the same sheet.
- **T-19 The report gives away nothing about a single question.** Counts
  and rates, as asked; and where the first draft named the failed question
  by set and position, it now gives the topic and the reason only, because a
  labeller who reads "set 6, question 5 failed the gate" has been told a gate
  result. `topics analyze` refuses to write a report that contains a
  question's text, a built answer of 20 characters or more, or a sheet key.
- **T-20 The scorer's verdict is what the app would get.** The raw
  `isCorrect` · after the proxy's `checkScoreFeedback`. **After it,** as on
  the route (it changed nothing in this run: 0 verdicts reconciled, 0
  structured fields dropped). A scoring record counts only when
  `scoring-calls.json` names it.
- **T-21 How the duplicates are counted.** From the recorded flags' texts ·
  recomputed from `items.json` with the same rule. **Recomputed,** as pairs
  (`duplicatePairs`, which the run's check now also uses; same result, the
  phase A tests pass unchanged), and the report says whether its counts
  agree with the recorded flags (they do). A group is every question joined
  by a chain of resembling pairs, so a group of 5 does not mean every two of
  its questions are a pair.
- **T-22 The details file is derived.** Plain text under `private/`, written
  again on every `topics analyze`; it carries the sheet keys, so a labelled
  row can be looked up after the labels.

## From the code: a fill-in-the-blank item that has no blank

Asked in `TOPICS.md`, phase C2, step 4. Read from the code; nothing was
changed.

**What the app shows.** A normal question screen with the type label "Fill
in the blank", the text as it came, and **one** answer box.

- `AnswerDrafts.boxCountFor` (`lib/widgets/question_view.dart`) gives one box
  per blank only for 2 to 4 blanks; with 0 blanks (and with 1, or more than
  4) it gives one box.
- The box is the fill-in kind: it starts at one line and does not
  capitalise (`minLinesFor`, `capitalizationFor`), as for a single missing
  word.
- A blank can be tapped to open its box; with no blank there is nothing to
  tap. Nothing tells the learner that the question is broken, and nothing
  crashes.
- Whatever the learner types goes to scoring as the answer of a
  `fill_in_blank` item (`answerFor`). The Worker's check of the scoring
  response expects one per-blank entry for such an item
  (`expectedBlankEntries`: at least one), so the response passes as well.
- In the first run this was one of 33 fill-in-the-blank questions: verbs
  in brackets and no place marked to answer. A learner would have had one
  short box for several verb forms.

**Whether anything on the live path stops it. Nothing does.**

- The generation prompt says a fill-in-the-blank item has at most 4 blanks;
  it does not say at least one, and does not say how a blank is written.
- The structured-output schema names the fields and the type; it cannot
  require a text to contain a blank.
- The Worker returns the model's output for a practice set as it is
  (`handleOperation` in `proxy/src/index.ts`): the Daily Test routes check
  and filter their output, the practice route does not.
- The app's parser needs an id, a known type and an instruction
  (`PracticeItem.fromJson`).
- The measurement's own gate is what found it (T-4); it exists only in
  `proxy/eval`.

**Proposed guard (not built; the owner decides).**

1. **In the Worker, on the practice response:** remove a `fill_in_blank`
   item that has no blank (the same rule would cover more than 4), serve the
   rest, and answer with the existing "unexpected response" error when fewer
   than three questions are left; log counts only. This is what the legacy
   Daily Test route already does for a correction without its sentence
   (`filterLegacyDailyTest`), so the pattern and its privacy rule exist. No
   prompt change, no app change, no extra cost; a set that had such an item
   arrives one question short (the loading screen names the count before
   the set exists, so that line can be off by one in those cases).
2. **Optionally, one sentence in the generation prompt** saying that every
   place to fill is marked with a run of underscores and there is at least
   one. It lowers the rate but guarantees nothing, and it changes the
   request of all ten topics, so it belongs with the next change of that
   prompt (the set-variety line, if that is built), not on its own.
3. A second generation call for such a set was considered and set aside:
   it costs a second set and several seconds for the learner, for what
   option 1 solves by dropping one question.

How often: 1 set of 33 in the first run. That is one observation, not a
rate.

## Decisions, phase C3

The first four are the owner's (2026-11-19, `TOPICS.md`).

- **T-45 (owner) Items without a blank get both measures.** The Worker
  removes a fill-in-the-blank item that has no blank from a practice
  response and serves the rest; and the generation prompt says such an item
  has 1 to 4 blanks, each written as underscores.
- **T-46 (owner) Set variety: option A, for all ten topics, now.** A
  scenario theme per practice set from the Daily Test's 14, stepped per
  device from what the quota check already reads; one line in the user
  prompt; no app change, no new data sent.
- **T-47 (owner) Comparatives & Superlatives is not waved through.** The
  scoring prompt gets the two proposed changes as a candidate, checked
  against the labelled answers; it becomes the production prompt only on
  the owner's word.
- **T-48 (owner) The configuration that will ship is measured once more as
  a whole,** the five live topics included, because every topic's request
  changes.
- **T-49 What the guard removes, and when it refuses.** Exactly what T-45
  names: a `fill_in_blank` item with no blank, counted where the app shows
  blanks (context and instruction; a blank is two or more underscores). An
  item with more than 4 blanks is left: the decision does not name it and
  the app shows it with one box. The response is refused only when the
  guard has emptied it, because the app cannot show an empty set. The
  response is filtered, never the request, and a response with nothing to
  remove is passed on as the same object.
- **T-50 The line on blanks replaces the earlier sentence** rather than
  standing beside it ("at most 4" and "1 to 4" would say the same thing
  twice). The earlier sentence stays in the code as a constant, so a test
  can show what the request changed by.
- **T-51 How the theme is stepped.** At random · from the device and what
  the quota check reads. **Stepped,** as the owner chose: index = (a hash of
  the device id + the day's number + the device's request count that day)
  mod 14. `reserveQuota` now returns the day and the count it read; nothing
  else is read or stored. Within a day a device never gets a theme twice in
  its first 14 requests; from day to day the sequence moves on by one;
  devices start in different places. It is a step, not a memory: it does
  not rule out a repeat across midnight or after 14 requests in a day.
- **T-52 The theme cannot come from the client.** It is a field of the
  request object the Worker builds after validation; the validation still
  refuses any field but the three, so a client that sends `theme` gets a
  400. The line is the last of the user prompt, and a request without a
  theme (the measurement's earlier runs) is byte for byte what it was.
- **T-53 The candidate's wording.** The two changes as two paragraphs after
  the production prompt, which is left untouched, so "the production prompt
  plus two paragraphs" is exactly true and testable. **The verdict rule is
  written in both directions:** the owner's sentence names one (a corrected
  answer that changes the tested structure means not correct); the
  Conditionals re-measurement showed the other once (the key rejected while
  the scorer's corrected answer was the same sentence), and "the verdict
  follows the scorer's own correction" covers both. The examples in the
  spelling paragraph ("hotter", "luckier") occur in no question and no
  built answer of the two labelled runs (checked), so the rescore does not
  test the prompt on its own examples; a first draft's example did occur in
  them and was replaced.
- **T-54 The themes of the measurement.** Each topic is one made-up device
  on one fixed day, its six sets at request counts 0, 2, 4, 6, 8, 10 (a
  session is a generation and a scoring): six different themes per topic,
  and the topics start at different themes, so more of the 14 are tried.
- **T-55 The sheet shows what the Worker would serve.** The guard is
  applied before the sheet, so an item it removes is counted and is not on
  the sheet: at most 225 questions, fewer by each removed item. What the
  measurement's own gate still faults after the guard is on the sheet and
  counted apart, as before.
- **T-56 Which sets of a live topic are labelled.** The first three of its
  six; all six are generated and checked for duplicates.
- **T-57 Both prompts score the same calls.** The candidate's calls hold the
  same answers in the same order as the production prompt's, in the final
  run and in the rescore, so the prompt is the only difference. One scoring
  per prompt: a single changed verdict can be chance (1.4.0: the same prompt
  gave the same verdict on 98.9 % of answers scored twice); the sections
  say so.
- **T-58 What `topics rescore` scores.** Every earlier run whose sheet is
  complete (the first run and the Conditionals re-measurement), found by
  reading the folders; a folder of its own; its section is written by the
  command itself when the run is complete, and again by `topics analyze` on
  its folder.
- **T-59 The later sections of the report.** Each is a marked block after
  the first run's part, in the order added (the re-measurement, the
  candidate on the labelled answers, the final configuration); the line
  under the status names them. Writing one again replaces only that one.
- **T-60 The automatic checks on the four other live topics.** Their hint
  cards were added to the harness (the sheet shows them; a test compares
  them with the app's file). The topic check and the hint-card check have
  rules only for the six topics of the first run, so for Gerund vs.
  Infinitive, Modal Verbs, Modal Past Forms and Tense Selection those two
  raise no flag; the duplicate, length and one-answer checks run for all
  ten. The duplicates, which are what the final run is about, compare with
  the first run for the six topics that were in it.
- **T-61 The worst case and the cap.** The dry run says when the worst case
  is over the cap (it is, for the first time) and that the check before
  each call is what holds the cap.
- **T-62 The legal fields need no change.** The app sends what it sent; the
  theme is worked out in the Worker from the device id and the request
  count it already reads for the quota, and nothing new is stored; no
  service is added. `legal.data_collected` and `legal.third_parties` stay
  as they are.
