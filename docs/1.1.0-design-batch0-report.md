# 1.1.0 design side tracks — Batch 0 report (read-only)

**Date:** 2026-09-27. **Branch:** `1.1.0-design`. **Scope:** read-only check
of the current code against every decision in
[`1.1.0-design-side-tracks.md`](1.1.0-design-side-tracks.md). No code, test,
config or asset changed; this file is the only file written. Nothing here is a
decision: where a question is open, one recommendation is given with its
reason, and the owner decides.

**How the numbers were obtained.**

- File and line references are to the code on `1.1.0-design` at `c629397`.
  `lib/`, `ios/`, `test/`, `assets/` and `pubspec.yaml` are **identical to
  `main`** (`git diff --stat main 1.1.0-design -- lib ios test pubspec.yaml
  assets` is empty), so every finding describes the 1.0.0 app.
- Home layout sizes (items 12–13) were **measured** with a throwaway widget
  test kept outside the repository (in the session scratchpad; not committed).
  It pumps the real `HomeScreen` inside the real `FloatingNavShell` with the
  app theme at each text size, loads the bundled `NunitoSans` font (without
  it, the test font's wide glyphs cause false overflows and wrong line
  counts), and uses status bar / home indicator insets of 20/0 pt (568 and
  667 pt tall screens) and 44/34 pt (812 pt). Known limits: fake storage (8
  steps, no Daily Test done, no weak spots, free user); the variable font is
  rendered at its default instance, so bold text widths can differ slightly
  from a device. Heights of non-text elements (the 350 pt mountain, paddings)
  are exact; text heights are close but not device-confirmed.
- Trail lengths (item 2) were computed by replicating `ClimbRoute`'s cubic
  segments numerically (2,000 samples per leg), in scene units.
- Durations are the constants in the code. Where the code has no number
  (launch work timing), the report says **unknown**.

## Findings 1–21

Each item: **finding**, **evidence**, **conflict with the decisions file**.

### Scene and trail

**1. How the mountain and trail are drawn.**
- Finding: **entirely code-drawn, no image files.** One `CustomPainter`
  (`_MountainPainter`) paints, in a fixed 320 × 740 logical scene scaled to the
  card width: three flat polygons (mountain body, ridge, stone cap), the trail
  as two stroked copies of one cubic `Path` (26 and 21 units wide), one rounded
  rectangle per step (20 × 13), four landmarks, and a flag. The sky is a flat
  `ColoredBox`. The avatar is a widget (`AvatarTile`, a WebP image) positioned
  over the painter.
- Evidence: `lib/widgets/monthly_climb/monthly_mountain.dart:163-332`
  (painter), `:119-152` (sky, scroll view, avatar); geometry in
  `lib/widgets/monthly_climb/climb_route.dart:4-50`; palette in
  `lib/theme.dart:607-635`.
- Conflict: none with "default: drawn in code". The layer-slot architecture
  does not exist yet (see recommendation b).

**2. Step positions; 28/29/30/31-day months; which day is the summit.**
- Finding:
  - The trail is **already a serpentine**: cubic legs between fixed stops at
    days 0, 7, 14, 21, 28 and, for 29–31-day months, `days`. X positions
    alternate 88 → 239 → 91 → 209 → (160 for 28 days, else 128) → 160. So
    **4 legs in a 28-day month, 5 legs in 29–31-day months.**
  - Y is linear in the day: `y = 690 − 570 × day / days`. Within a leg a step
    sits at an equal share of that leg's arc length; legs differ in length,
    so **spacing along the trail is not even**.
  - The last day always ends at (160, 120), the trail's end. The flag is
    drawn at the mountain's peak vertex (162, 56 → 20), **64 units above the
    trail's end**; the pawn never reaches the flag.
  - Month lengths outside 28–31 throw.
- Measured spacing (scene units per step, per leg):

  | Days | Legs | Leg lengths | Step spacing per leg | Even spacing would be |
  |---|---|---|---|---|
  | 28 | 4 | 219.7, 217.3, 194.8, 153.7 (total 785.5) | 31.4, 31.0, 27.8, 22.0 | 28.1 |
  | 29 | 5 | 216.2, 213.8, 191.0, 166.1, 39.6 (826.7) | 30.9, 30.5, 27.3, 23.7, **39.6** | 28.5 |
  | 30 | 5 | 213.0, 210.6, 187.6, 162.2, 52.3 (825.7) | 30.4, 30.1, 26.8, 23.2, 26.2 | 27.5 |
  | 31 | 5 | 210.1, 207.6, 184.3, 158.6, 66.3 (826.9) | 30.0, 29.7, 26.3, 22.7, 22.1 | 26.7 |

- Evidence: `climb_route.dart:12-14` (28–31 guard), `:15-23` (stops and X),
  `:38` (Y), `:40-49` (`pointAt`); flag `monthly_mountain.dart:245-257`;
  locked by `test/monthly_climb_preview_test.dart:10-31` (summit at
  (160, 120), X within 29–291, landmarks within the scene).
- Conflicts:
  - "Serpentine (zigzag) trail, 4–5 legs" is **already true**; Batch 3 lists it
    as new work. What is actually new is even spacing.
  - "Spaced evenly along the trail" is **not true today** (spread 22.0–39.6
    units per step). Changing it moves every step on screen, which is a
    visible change for 1.0 users.
  - "The summit is a layer that sits on the trail's shared end point": the
    trail's end (160, 120) and today's peak and flag (162, 56) are **two
    different points**.

**3. Landmarks at days 7, 14, 21, 28.**
- Finding: **present and code-drawn.** `_landmark` draws a campfire (7), a
  tent (14), a cabin (21) and a lookout terrace (28), each with an elliptical
  ground shadow, in palette colors (`stone`, `accent`, `ridge`, `ink`). Each
  is placed 42 units beside the trail point (toward the scene's center) and 22
  units up. In a 28-day month the day-28 lookout sits next to the summit
  point. The VoiceOver label lists them word for word.
- Evidence: `monthly_mountain.dart:238-244` (placement), `:261-325` (shapes),
  `:109-112` (semantics label).
- Conflict: the decisions file does not mention them. Together with 4–6
  environment items they exceed the "4–6 objects in the whole scene" budget.
  See recommendation a.

**4. Separate dark mode colors.**
- Finding: **yes.** `ClimbPalette.of(brightness)` returns a separate dark
  palette (sky `#182327`, mountain `#405C53`, ridge `#2E463F`, trail

  versus light (sky `#EAF0EC`, mountain `#ACC4AC`, ridge `#789B86`, trail

- Evidence: `lib/theme.dart:607-635`; read at

- Conflict: **yes.** "The scene is the same in light and dark mode" would

**5. Avatar in the scene; mirroring; step animation.**
- Finding:
  - `AvatarTile(radius: 29 × scale)` is placed at the trail point minus
    (29, 55) scene units, so the 58 × 58 tile stands centered on the point.
    `AvatarTile` has **no flip parameter**, but it is a plain widget (image
    plus blurred ground shadow), so wrapping it in `Transform.flip(flipX:)`
    mirrors it. That is not tried on a device.
  - Step animation: **850 ms, `Curves.easeInOut`**. The pawn glides along the
    trail path (the day value is interpolated, then mapped through
    `pointAt`); there is **no hop**. The inner scroll view follows the pawn,
    keeping it at 72 % of the viewport height.
  - With Reduce Motion, or when the month length changes, the pawn jumps and
    `onMotionEnd` fires after the frame.
- Evidence: `monthly_mountain.dart:147-151` (avatar), `:50-51` (controller,
  850 ms), `:42-43` (curve), `:56-85` (Reduce Motion, jumps), `:91-96`
  (follow at 0.72); `lib/widgets/avatar_tile.dart:43-77`, `:109-125`.
- Conflict: none. Mirroring and the hop are new work, as planned.

### Data and rules

**6. Monthly Climb record: schema, storage, theme field.**
- Finding: SQLite through `sqflite`, schema **v22**.
  - `climb_daily_entries`: one row per Daily Test day. Columns `day` (PK),
    `completed_at`, `step` 0/1, `correct_count`, `wrong_count`,
    `skipped_count`, `rule_version`.
  - `monthly_medal_results`: one row per **finalized** month. Columns `month`
    (PK, `YYYY-MM`), `tier`, `score`, `max_score`, `active_days`, the three
    counts, `rule_version`, `finalized_at`. It is written only **after** a
    month ends (at launch, on resume, from Profile), and only for months with
    at least one ledger row.
  - **There is no theme or mountain field anywhere, and no per-month record
    exists while a month is running.** "Write the theme id into that month's
    record when the month starts" has no record to write into.
  - The safe way to add one is the existing migration pattern: bump to v23
    with an idempotent `CREATE TABLE IF NOT EXISTS` step (the file requires
    every step to be idempotent because sqflite lowers the version on a
    downgrade without changing tables). A new table does not touch existing
    rows, and a 1.0 build that downgrades ignores it.
- Evidence: `lib/services/storage_service.dart:30` (`_dbVersion = 22`),
  `:246-258` (`climb_daily_entries`), `:260-273` (`monthly_medal_results`),
  `:1046-1103` (`finalizePastMedalMonths`), `:330-341` (idempotency rule),
  `:529-552` (`_hasColumn`, `_addColumnIfMissing`), `:493-495` (last step,
  v22).
- Conflict: **yes, wording.** "Written into that month's record" assumes a
  record that does not exist. See recommendation c.

**8. Medal rule: code vs rule v1; thresholds; [N].**
- Finding: **the code matches rule v1 exactly.**
  - `score = correct × 2 + wrong`; skipped answers add 0.
  - `maxScore = daysInMonth × 10`.
  - `threshold = (maxScore × pct + 99) ~/ 100`, which is ceil(pct %), with 25 /
    50 / 75.
  - Only the highest tier is awarded; there is no minimum-day gate.
  - `ruleVersion = 1` is stored with each finalized month.
  - `active_days` counts `step = 1` days only.
  - The `× 10` is a literal, not derived from the question count (see item 9).
- Evidence: `lib/services/monthly_medal_rules.dart:3-37`; used at
  `storage_service.dart:1155-1156` (progress) and `:1066-1070` (finalization);
  tests `test/monthly_medal_rules_test.dart` (3 tests).
- Thresholds and [N] (with [Q] = 5, see item 9; [N] = ceil(Bronze ÷ [Q] × 1)):

  | Days | Max | Bronze | Silver | Gold | [N] | Fallback line from day (N > days left incl. today) |
  |---|---|---|---|---|---|---|
  | 28 | 280 | 70 | 140 | 210 | 14 | 16 |
  | 29 | 290 | 73 | 145 | 218 | 15 (14.6) | 16 |
  | 30 | 300 | 75 | 150 | 225 | 15 | 17 |
  | 31 | 310 | 78 | 155 | 233 | 16 (15.6) | 17 |

- Conflict: none. The worked example in the decisions file (30 days → 15,
  31 days → 16) is confirmed.

**9. Where the daily question count comes from.**
- Finding: **not a single constant.** The value 5 lives in five places:

- Evidence: `lib/services/daily_test_service.dart:16`, `:103`;

**10. How a blank (0-point) answer happens.**
- Finding: **only by moving on with an empty field.** There is **no timer**
  (no `Timer` or time limit in the Daily Test screen).
  - "Next"/"Finish" is disabled while the field is empty.
  - The separate **Skip** action advances with the field empty. A user can
    also go back and clear an earlier answer.
  - An answer that is empty after trimming counts as skipped.
  - **Leaving the test early** ("Leave Daily Test?" → Leave, or the system
    back gesture) **discards everything**: no completion and no ledger row, so
    no 0-point answers are written.
  - An all-skipped test writes a ledger row with `step = 0`: no step and no
    score.
- Evidence: `lib/screens/daily_test_screen.dart:127-130` (`_currentHasAnswer`),
  `:137-143` (`_advance`), `:161-183` (exit dialog), `:212-219` (`PopScope`),
  `:392-397` (footer: `primaryEnabled`, `onSkip: _advance`);
  `lib/models/daily_test_completion.dart:26-29`, `:66-72` (trim → skipped).
- Conflict: none. "Answer all [Q] questions" means "do not use Skip", which is
  accurate.

**11. How the code knows a user is in their "first month".**
- Finding: **it does not; no such concept exists.** The Welcome badge is
  "the first `step = 1` ledger row ever", decided inside the completion
  transaction; it is not tied to a month. The only first-launch signal is "no
  saved profile", which drives the Welcome → onboarding → Day-0 flow.
  - A usable definition from existing data: **no `climb_daily_entries` row
    before the current month.** It is one indexed query on `day`, the primary
    key.
  - Using the badge's `earned_at` month instead would miss a user whose first
    month had only all-skipped tests.
- Evidence: `storage_service.dart:913-991` (`completeDailyTest`, badge),
  `:1119-1129` (`getWelcomeBadge`); `lib/app.dart:69-75` (profile as the
  first-launch signal).
- Conflict: case (c) needs a definition. The one above is recommended.

**14. All Home animations and their order.**
- Finding:
  - **Normal Daily Test return** (`_openDailyTest`): Daily Test route →
    result route. The save sets `_pendingClimbDay`; after the result route's
    pop transition completes, `_loadClimb` runs. Home first scrolls the
    mountain into view (**250 ms**, 0 ms with Reduce Motion), then the pawn
    moves (**850 ms**).
  - **Day-0 flow:**
    1. Welcome screen: the brand mark's entrance takes **900 ms** (fade,
       scale 0.86 → 1, un-rotate). After 1.4 s an **endless 6 s breathing
       loop** starts.
    2. Onboarding, then the Day-0 Daily Test.
    3. Results: the Welcome card eases in (**350 ms**). "Start my climb"
       plays the confetti (**1.8 s**, with a 2.5 s fallback; none with Reduce
       Motion).
    4. The shell's Home mounts the pawn one step back. `ensureVisible` runs
       (250 ms), then the pawn (850 ms). `onMotionEnd` is followed by a
       **600 ms** pause, then the first-day Premium screen is pushed (default
       route transition), once, through a one-time flag.
  - **Others:** the avatar `Hero` flight to the picker. Indeterminate
    progress indicators while loading (the climb's `LinearProgressIndicator`
    and the Today card's `CircularProgressIndicator`) are endless while
    visible.
- Evidence: `home_screen.dart:425-461`, `:237-318`, `:147` (600 ms),
  `:319-329`, `:671`, `:778`, `:846`; `monthly_mountain.dart:50-51`;
  `lib/screens/welcome_screen.dart:303-329`;
  `lib/screens/daily_test_result_screen.dart:59`, `:65`, `:146-181`;
  `lib/widgets/confetti_burst.dart:143`;
  `lib/screens/first_launch_flow.dart:105-129`.
- Conflict: none. The first-day paywall and the month card cannot both be
  pending, because the paywall only follows the Day-0 test (the first month)
  and case (c) shows no card. Also note: Home determines "this month" on every
  load, including resume (`home_screen.dart:219-229`, `:241-242`). A new month
  can therefore begin on a **resume**, not only on a cold start.

**15. `one_time_flags` keys; a per-month key.**
- Finding: table `one_time_flags(key TEXT PRIMARY KEY, set_at TEXT NOT
  NULL)`, schema v22. `claimOneTimeFlag(key)` is atomic: `INSERT OR IGNORE`
  plus `SELECT changes()` in one transaction, so it returns true exactly once
  per key, even for overlapping callers. The only key in use is
  `day0_paywall`. It is claimed just before the Premium screen is pushed, so
  an app kill in between loses it; that is by design.
- **A per-month key such as `month_card_2026-10` fits**: keys are free text,
  there is no key limit, and the claim is race-safe. Twelve rows a year is
  negligible.
- Debug-only `resetOnboarding` deletes only `day0_paywall`.
- Evidence: `storage_service.dart:125-135`, `:1288-1305`, `:1327-1334`;
  `home_screen.dart:338-363`; `test/storage_service_one_time_flag_test.dart`
  (8 tests).
- Conflict: none. **Related risk found:** case (a) needs last month's tier.
  `finalizePastMedalMonths` runs asynchronously at app launch
  (`lib/app.dart:90`) while Home loads in parallel, so on the first open of a
  month the frozen row may not exist yet when Home reads it. Computing last
  month's tier from the ledger with the same rule (`getMonthlyMedalProgress`
  + `MonthlyMedalRules.tierFor`), or awaiting finalization first, avoids the
  race.

### Other

**16. Launch screen today; cold start vs resume.**
- Finding:
  - **No package** (no `flutter_native_splash`; dependencies listed in
    `pubspec.yaml`).
  - `LaunchScreen.storyboard` shows an image view centered on a named color
    `LaunchBackground` (Any `#FAF3EC`, Dark `#1C1B1F`). **`LaunchImage` is
    still Flutter's 1 × 1 transparent placeholder** (all three scales are the
    same 1 × 1 PNG, identical MD5), so today the launch screen is a plain
    color.

    launch image will need a PNG export of it, kept in sync by hand or by a
    test.
  - Cold start work, in order: `lockAppOrientation()` →
    `Firebase.initializeApp` (+ Crashlytics hooks) →
    `SubscriptionService().initialize()` (RevenueCat), **all awaited before
    `runApp`**. Then `GrammarLensApp.initState` starts, without awaiting,
    medal finalization and the theme mode, text size and profile reads. A
    `LoadingView` on `surfaceContainerLow` shows until the profile read
    returns, then Home or the Welcome flow.
  - **Durations: unknown.** There is no timing instrumentation in the code;
    measuring needs a device (Instruments or log timestamps).
  - Cold start and resume **are distinguishable**: cold start runs `main()`
    and `initState`; resume arrives as `didChangeAppLifecycleState(resumed)`,
    both in `app.dart` and in Home.
- Evidence: `ios/Runner/Base.lproj/LaunchScreen.storyboard`;
  `ios/Runner/Assets.xcassets/LaunchBackground.colorset/Contents.json`;
  `ios/Runner/Assets.xcassets/LaunchImage.imageset/` (1 × 1 px each);

  `lib/widgets/brand_mark.dart:1-26`; `docs/build-log.md` 2026-09-23
  (submission prep).
- Conflicts:
  - "Runs in parallel with launch work": the first Flutter frame cannot

    are awaited before `runApp`. Either those awaits move after `runApp`, or
    the animation starts only after them.
  - "The static launch screen is identical to the animation's first frame":
    **not possible for a user whose in-app theme differs from the system
    appearance.** The storyboard can only follow the system appearance; this
    known limit is recorded 2026-09-23.
  - Reuse note: Welcome's `_AnimatedBrandMark` already does a
    fade + scale-up entrance, but also a rotation and an endless breathing
    loop. The launch animation needs neither.

## Recommendations

**a) Landmarks on the serpentine.** Keep the four existing landmarks
(campfire, tent, cabin, lookout) as **one shared, neutral set in all four
themes**, still at days 7/14/21/28, colored from each theme's palette (they
already are). Count them inside the 4–6-object budget, so each theme adds at
most two environment items. *Reason:* they mark days, which is what the trail
counts, so they do not have the camps' points-vs-days problem. They already
follow the palette, they are in the VoiceOver label, and keeping them costs no
new art. The budget keeps the scene as sparse as decided.

**b) Layer slots in the current drawing structure.** Split `_MountainPainter`
into ordered layers inside the existing `Stack` (`monthly_mountain.dart:140`),
all in the same 320 × 740 logical scene and the same `scale`:

1. sky
2. far background
3. mountain body (shared silhouette, **up to the trail's end**)
4. environment items
5. trail + steps + landmarks (always code, shared)
6. summit (anchored at (160, 120), owning the area above)
7. avatar (unchanged widget)

Each themeable slot is a widget: `Image.asset` of the theme's WebP with an
`errorBuilder` that returns that slot's `CustomPaint`, or the `CustomPaint`
directly when the theme names no file. *Reason:*

- the trail, steps and pawn keep one shared geometry and stay testable
  exactly as today;
- a missing or broken file falls back per slot with a built-in Flutter
  mechanism;
- the scene scale stays in one place, since images are sized to the logical
  scene and scaled by the same `scale`.

**c) Migration for the theme.** Schema v22 → v23 with an idempotent step
`CREATE TABLE IF NOT EXISTS climb_month_themes (month TEXT PRIMARY KEY,
theme_id TEXT NOT NULL, assigned_at TEXT NOT NULL)`.

- **No backfill:** a month without a row resolves to Green Slope, which is
  exactly what 1.0 users saw.
- The row is written with `INSERT OR IGNORE` the first time a month is
  resolved (Home's climb load and the completion transaction), so a month's
  theme is stable from its first use.
- Rotation: **a global calendar formula** (the same theme for every user in a
  given month), with the anchor month chosen by the owner.

*Reason:*

- A new table touches no existing row and is ignored by a downgraded 1.0
  build.
- The global calendar keeps "month 3 drop" and "that month's theme"
  separable across install cohorts, which is the measurement reason for
  storing the theme. A per-user rotation that starts every user on Green
  Slope would tie theme and tenure together permanently.

**d) The score bar's place.** Directly **under the mountain window, inside
the same rounded card**. Merge the requested title into the existing header
instead of adding a row: "Mountain of Learning" replaces "Monthly Climb" on
the header's first line, and the month and "n / N steps" stay on the second.
*Reason:*

- The card and its header are already the climb's single unit on Home.
- The header already exists and already wraps to two rows, so the title costs
  0 pt instead of ~40 pt.
- At 320 × 568 Medium only 79 pt of the mountain is above the fold today; a
  third text row would cut that to ~39 pt.

**e) Changes needed for each conflict.** In the "What should change" column
of the conflicts table (C1–C14). The ones to decide before Batch 1: **C9 and
C10** (Batch 1, launch). Before Batch 2: **C1 and C2**, plus the rotation
anchor in c. Before Batch 3: **C3–C6**. Template blanks, from items 2 and 12,
to fill once b is decided:

- `[SCENE_ASPECT]`: 320:740 logical, shown through a 350 pt window at scale
  0.9–1.066.
- Canvas: 3× the logical scene is 960 × 2220 px; the widest measured card
  (341.25 pt at 3×) needs 1024 px.
- Trail safe zone: the trail stroke is 26 units wide; the avatar occupies 58 ×
  58 units above each step point (x ± 29, y − 55 … y + 3); each landmark
  ±30 units around a point 42 units beside the trail.
- Summit anchor: (160, 120).

**f) Smallest hook points in the Home files.**

- **Score bar and title:** only inside `_buildClimb`
  (`home_screen.dart:734-788`), ideally by moving it into a new
  `MonthlyClimbCard` widget in `lib/widgets/monthly_climb/`, so Home keeps a
  one-line call. The score needs **no new storage read**: `getClimbProgress`
  already returns `correct` and `wrong` (`storage_service.dart:994-1020`),
  and Home currently keeps only `steps` (`home_screen.dart:292`). Keep the
  record and compute the score with `MonthlyMedalRules.score`.
- **Theme:** one extra resolved value in `_loadClimb`
  (`home_screen.dart:237-318`) passed down to `MonthlyMountain` as a
  parameter. `MonthlyMountain` stays presentation-only
  (`monthly_mountain.dart:7`).
- **Hop, mirroring, one-time environment motion:** entirely inside
  `MonthlyMountain` / `ClimbRoute`; Home unchanged. The existing
  `onMotionEnd` already reports the end of a step.
- **Month transition card:** hook where Home already sequences post-climb UI.
  It waits on `_climbAnimating` / `_onMountainMotionEnd` exactly like
  `_armDay0Paywall` (`home_screen.dart:314-329`), with its logic (case, flag
  claim, texts) in its own file. Home only calls "climb landed" and "month
  changed".
- **Launch screen:** `main.dart` / `app.dart` and `ios/`, not Home.
- **Analytics:** wrappers in `analytics_service.dart` and their current call
  sites. Expect a merge touchpoint with `1.1.0`'s `set_date` on
  `daily_test_completed`.
