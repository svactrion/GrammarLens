## 1. P14 — accepted answers on the live shared sets

### 1.1 The two facts that shape the design

1. **The serving window makes "backfill" small.** A date is served only
   from UTC today − 1 to today + 2 (`SERVING_WINDOW`), and a client reads a
   date once and caches it. At any moment at most **five dates** can still
   be read by anyone (today − 1 … today + 3). Older `set:*` keys (TTL 35
   days) are history: writing `acceptedAnswers` into them changes nothing
   for any learner. So the backfill is one pass over the horizon at deploy
   time, not a script over 35 sets. The 30-odd older sets in KV are still
   valuable as **measurement input** (read-only, like
   `scripts/fallback_pool.sh fetch`).
2. **Timing is generous.** A set is published at (D − 3) 00:07 UTC; the
   earliest read is (D − 2) 10:00 (a UTC+14 user prefetching tomorrow). A
   check one hour after publication lands ≈ 33 h before the first read
   (quality report §4.6). Only the deploy-day pass over today's and
   tomorrow's sets competes with the 1 h edge cache.

### 1.2 The three approaches

| | (a) Model check | (b) Rules layer | (c) Both |
|---|---|---|---|
| What it fixes | Defensible alternatives of any kind: "must"/"should", present perfect simple vs continuous, "has sun", "his" | Only surface variants of the key: contractions (`'m` / `am`), spelling variants (`neighbourhood` / `neighborhood`) | (a) for alternatives, (b) for variants |
| Of the owner's 10 corrections | 10 of 10 are in its reach (the two moves included) | 2 of 10 (`'m cooking`, `'re cleaning`) plus the US spelling inside one of the 2026-10-05 q4 entries; the other 7 are judgments, not variants | 10 of 10 |
| Where it runs | A second step in the hourly cron (one Anthropic call per run, as today), plus one deploy-day pass over the horizon | In **grading**, not in data: an extra normalisation step shared by the client and the proxy (like the folding), fixture-tested | Both |
| KV write | Rewrites `set:{date}` with `acceptedAnswers` and `checkedAt`; writes `review:{date}` when a finding cannot be repaired | None | As (a) |
| Keeps a bad accepted answer out | The gate of §1.4 | A closed table can only produce the forms it lists; the risk is a variant that is a real grammar difference (`'s` = is / has / possessive; `-ise` is not a variant of every `-ize`) | Both gates |
| Cost per set | ≈ $0.05 (one `claude-opus-5-5` check, measured in E) to ≈ $0.08 with the agreement gate | 0 | ≈ $0.05–0.08 |
| Needs a client release | No: the client already grades `acceptedAnswers` | **Yes** for the Daily Test (the matcher is in the app) and for the proxy's gate; the 1.3.0 clients keep today's grading | (a) no, (b) yes |
| What already-completed sets see | Nothing changes (§1.5) | Nothing changes | Nothing changes |

**(b) in detail, since it is tempting.** A rules layer belongs in the
normalisation shared by both sides, not in the data: writing "am cooking"
into every key's `acceptedAnswers` by rule would have to be run on every
set and would still miss sentence-level keys. Safe, closed classes:
unambiguous contractions expanded on both sides (`I'm`→`I am`, `n't`→` not`,
`'re`, `'ll`, `'ve`, `'d`?) and a short spelling table (`-our`/`-or`,
`-ise`/`-ize`, `-re`/`-er`, `travelling`/`traveling`). Not safe: `'s`
(three readings), `'d` (had / would), and anything on the key itself in an
`error_correction` item where the contraction *is* the tested form. Because
it changes the app's matcher it ships with 1.4.0, not server side, and its
reach is 2–3 of the 10 corrections. "Article-free forms" (the owner's third
class) is a judgment call, not a variant: the 2026-10-01 q3 case ("his" for
a key "the", where the instruction asked for one word) is a question with
two answers, exactly what the model check is for.

### 1.3 Recommendation: (a) now, server side, as an **annotate-after-publish** step; (b) later, in the 1.4.0 client's normaliser, limited to contractions and a spelling table, as its own Batch 0

**Why annotate-after-publish and not the pending → check → publish pipeline
of §4 (P7).** P7 was designed to *reject* sets. P14's goal is narrower: add
accepted answers to sets that are published anyway, without changing when
or whether a set is published. Annotating in place keeps the cron's
publishing behaviour, its tests and its timing exactly as they are, so the
risk of a date with no set does not rise. The price is one rule change:
`set:{date}` is written twice (publish, then annotate), which the
"write-once" comment and one test (`never overwrites a set that appeared
while its own call was running`) currently forbid. The annotate write is an
**additive patch of the same questions** (ids, texts, keys and wrong
answers unchanged, `acceptedAnswers` and `checkedAt` added), checked before
the write; a set that differs in anything else is left alone and logged.

**The run (one Anthropic call per run, as today).** For each date today …
today + 3, nearest first: a set with no `checkedAt` and `checks` left →
call the checker (count the check first, like an attempt), decide (§1.4),
write the patched set, stop. A date with no set falls through to generation
as today. Generation and annotation never share a run, so a date needs two
runs (00:07 and 01:07). `attempts:{date}` gains a `checks` counter (cap 2);
a check that fails (timeout, unreadable) is retried next hour; after the
cap the set stays as published, without alternatives, as today. The
deploy-day pass is the same code: on the first run after deploy the
horizon's dates have no `checkedAt`, so they are annotated one per hour,
nearest first (today's set within the hour, tomorrow's in two).

**What the checker proposes, what the proxy writes.** The checker prompt
and schema stay as built (`CHECK_VERSION` 2 after D3's wording change). The
decision function for annotation is a sibling of `decideQuestion`, add-only:

| Finding | Published set | Written where |
|---|---|---|
| `acceptableAlternatives` that pass the gate (§1.4) | added to `acceptedAnswers` | `set:{date}` |
| `acceptableWrongAnswers` (the owner's 2026-09-28 decision 2, implemented here) | moved from `commonWrongAnswers` to `acceptedAnswers` when at least one wrong answer remains and the comment is not shown anywhere else; otherwise not moved | `set:{date}`, and `review:{date}` |
| `original_not_wrong`, `key_incorrect`, `wrong_rule`, `explanation_excludes_alternative`, an alternative that is the original or a predicted wrong answer, a checker `reject` | nothing changes in the set (a published set cannot be repaired by an alternative) | `review:{date}` (14-day TTL): the question id, the finding codes, the proposed alternatives; never the learner, never a device |

`review:{date}` is the owner's weekly look, made concrete: `wrangler kv key
get` shows what the checker found that the proxy would not write. Pulling a
set stays the owner's manual act (delete `set:{date}`), as today.

### 1.4 The gate against a bad accepted answer

The owner's 2026-10-04 review: 6 of 35 live questions had a defensible
answer the key did not name. The failure that matters here is the other
direction: an accepted answer that is **not** right teaches every learner
who types it that it is. Four layers, the first three mechanical:

1. **Shape** (exists, `cleanAlternatives` + rows 6–8): blank, over 300
   characters, the key again, a repeat, more than 2 → dropped or not
   written; an alternative equal to the original sentence or to a predicted
   wrong answer → not written, `review`.
2. **The key is plain** (new gate rule, cheap): `correctAnswer` and every
   alternative must fold to themselves under D3's folding (ASCII letters,
   straight quotes), so an alternative can never collide with another
   answer through folding alone.
3. **Agreement** (new): an alternative is written only when **two
   independent reviews agree** on it: `claude-opus-5-5` and
   `claude-sonnet-5-5`, both with adaptive thinking, same prompt. One
   model's proposal alone goes to `review:{date}`. E measured the single
   checkers at 44 % (Sonnet 5), 79 % (Opus 5.5) and 100 % (Sonnet 4.6)
   recall with 4–15 % false rejects on clean questions; for *adding* an
   answer the cost of a false positive is high and the cost of a miss is
   the status quo, so precision is bought with a second call. Cost: two
   calls per set, ≈ $0.08, ≈ $2.4 a month. **Alternative (owner's call):**
   one Opus review with `review:{date}` for everything, ≈ $1.5 a month,
   and the owner's weekly look as the second reviewer.
4. **Measured before deploy** (§3.1): the gate's precision and recall
   against the owner's `accept_also` labels on the 35 pool questions and a
   blind sheet over the 25–30 older live sets in KV. Go/no-go: **no
   accepted answer the owner marks wrong** in the agreed set; recall of the
   owner's 10 corrections reported, not gated.

### 1.5 What the client sees

- **Sets read after the annotation** (every normal case): "Also correct:
  …" on a matching answer, counted correct, nothing in the error profile.
  No app change.
- **Sets already completed, and sets cached before the annotation:**
  unchanged. The cached `questions_json` is what the result screen re-grades
  from; the error entries and the Monthly Climb day are already written.
  Re-reading a cached day or re-grading history is **not proposed**: it
  would rewrite medal and climb history after the fact, and the horizon
  timing means a cached-but-unannotated set only happens on deploy day and
  for a device that prefetched tomorrow's set in the one hour before its
  annotation.
- **1.3.0 clients:** the same as 1.4.0 clients; the field has been read
  since 1.1.0.

### 2.2 The folding table for the seven languages

Principle kept from today: **a closed table, not fuzzy matching.** Folding
is applied after `normalizeAnswer` on both sides, only in the
keyboard-variant branch, and must never make a wrong answer right: the key
is always plain ASCII English (gate rule 2 of §1.4 enforces it), so a fold
can only move a learner's string *towards* the key, never between two
English forms. One table in one fixture, `answer_normalization.json`'s
`fold` section extended, implemented by hand on both sides (Dart has no
Unicode decomposition in the SDK; an explicit table is the same philosophy
as today and keeps the two sides identical by construction).

| Class | Keyboards | Rule | Example (typed → folded) |
|---|---|---|---|
| Full-width ASCII | ja, ko (IME left in full-width mode) | U+FF01–U+FF5E → U+0021–U+007E; ideographic space U+3000 → space | `ｃｏｏｋｉｎｇ` → `cooking`; `２０１８` → `2018` |
| Precomposed Latin letters with a diacritic | es, pt-BR, de, tr, and the iOS long-press pop-ups on every layout | an explicit map of the letters those layouts produce: á à â ã ä å é è ê ë í ì î ï ó ò ô õ ö ú ù û ü ý ÿ ñ ç ş ğ ı → the base letter; `ß` → `ss`; `æ` → `ae`, `œ` → `oe` | `cookíng` → `cooking`; `señt` → `sent`; `Straße`-style `ß` in an English word → `ss` |
| Dotless and dotted i | tr | `ı` → `i` (not a decomposition; kept from today); `İ` is already handled in `normalizeAnswer` | `cookıng` → `cooking` |
| Quotation marks and apostrophes | all; ja/ko/ar punctuation | ’ ‘ “ ” already in `normalizeAnswer`; add ʼ (U+02BC), ′ (U+2032), ´ (U+00B4) and ` (U+0060) used as apostrophes, 「」『』 (ja) and « » (es/pt/de/ar) → `"`, full-width ＇ ＂ via the first row | `isn´t` → `isn't`; `«the»` → `"the"` |
| Spaces and invisible marks | ja, ko, ar, and iOS smart punctuation | non-breaking space U+00A0 and ideographic space → space (collapsed by `normalizeAnswer`); zero-width U+200B–U+200D, RTL/LTR marks U+200E/U+200F, BOM U+FEFF → removed | `the station` → `the station` |
| Dashes | all | ‐ – — (U+2010–U+2015) → `-` | `well–known` → `well-known` |
| Digits and punctuation | ar (Arabic-Indic U+0660–0669, Eastern Arabic U+06F0–06F9, Arabic comma U+060C, question mark U+061F), ja (full-width, row 1) | → ASCII digits, `,`, `?` | `٢٠١٨` → `2018` |
| Spanish inverted marks | es | ¿ ¡ removed | `¿where` → `where` |

Not folded, on purpose: Hangul, kana and Arabic letters (an answer in
another script is not an English answer); `'s` and other contractions
(§1.2); any letter-to-letter change beyond diacritics. Two things change
in the code around the table: the fold may change length (`ß`, removed
marks), so `_keyboardVariantNote` stops pairing characters by index and
instead names the non-plain characters in the learner's answer (the
sentence stays as it is); and the Daily Test test group and the proxy's
scoring test stop naming the Turkish set.

**Which side is which:** the client half (`answer_matching.dart`, the Dart
fixture test) ships in the 1.4.0 build; the proxy half
(`shared_daily_test.ts`, the gate's plain-key rule, `convert.ts`) deploys
with D3 after measurement. Until both are out, the two sides differ only
in which learner strings they forgive, never in what the key is, so no
grading contradiction between a 1.3.0 client and a D3 proxy is possible.

### 2.3 What a Daily Test regression would look like, and how the measurement catches it

The shared prompt reaches every learner at once. E showed the wording
matters (v1 60 % defective questions, v2 30 %), so v3 is treated as a new
generator even though only one sentence changes.

| Regression | Visible in | Caught by |
|---|---|---|
| More questions with two defensible answers, or "optional time shift" items | owner labels; the checker's `acceptableAlternatives` count | the blind label sheet, v2 vs v3 on the same dates; the checker rate per set |
| Blankless `fill_in_blank`, sentenceless `error_correction`, multi-edit corrections, long or multi-sentence explanations | the gate's rejection codes (no labels needed) | `validateSharedSet` pass rate per variant, as in the generator comparison |
| Tone or wording drift (the explanation talks about "your language", or names a language) | reading `questions.md` | the owner's read; a grep over the outputs for language names |
| Longer outputs, `max_tokens` stops at `low` effort | tokens and `stop_reason` per call | the harness's per-call record |

**Design:** the same 6 dates as E (2026-10-10/11/13 + 10-12/14/15: three
themes, both splits, every topic in both types), generated with the live
generator (`claude-sonnet-5-5`, `low`) under v2 and under v3: 12
synchronous calls, ≈ $0.019 each → **≈ $0.25**. Both runs' questions go
into the label sheet blind (60 rows, ≈ 40 min). **Go/no-go for deploying
v3:** gate pass rate not below v2's on the same dates; the owner's defect
rate for v3 not above v2's by more than the sample can hide (with 30
questions a side, a difference under about 15 points is noise — a result
in that band means "no evidence of regression", and v3 ships because it is
the stated 1.4.0 decision); no language named in any output. **Rollback:**
`SHARED_PROMPT_VERSION` is one line, and every set records its version.

| **S-free** | 2 learner answers per S-gen item written blind by Claude at two levels ("B1 with one typical error", "correct") and labelled by the owner on the sheet | ≈ 100 answers, labelled with S-gen | the only source for `sentence_writing` and open `error_correction` scoring, where there is no key |

In all: **≈ 500 scored answers**, ≈ 100 calls of 5 items per scoring cell,
and about **2 h of owner labelling** (S-live ≈ 70 min, S-gen + S-free
≈ 45 min, S-synth review ≈ 15 min). If that is too much, S-live is the
first to cut (it informs P14 only; S-pool already gives 35 owner-labelled
questions).

### 3.2 Metrics

Per scoring cell, over the labelled answers:

- **Agreement with the owner's labels** on `isCorrect` (accuracy), and
  separately **false "correct"** (a wrong answer passed) and **false "needs
  work"** (a right or accepted answer failed), each as a rate with its
  count, split by item type and by source set.
- **Model disagreement, the owner's separate line:** for every answer, the

## 4. D11 — structured scoring feedback

### 4.1 The JSON shape (additive; today's six fields unchanged)

```json
{
  "feedback": [{
    "itemId": "q3",
    "isCorrect": false,
    "errorType": "gerund_vs_infinitive",
    "rule": "verb + gerund after 'avoid'",
    "correctedAnswer": "She decided to change jobs and is enjoying her new role.",
    "explanation": "…today's text, unchanged in role (see 4.5)…",
    "summary": "Two of the three blanks take the -ing form after 'enjoy' and 'avoid'. Your first answer was right.",
    "blanks": [
      { "index": 0, "correctAnswer": "to change", "accepted": true,  "note": "'Decide' takes a to-infinitive, so 'to change' is right." },
      { "index": 1, "correctAnswer": "enjoying",  "accepted": false, "note": "After 'is', the continuous form 'enjoying' fits the ongoing situation." },
      { "index": 2, "correctAnswer": "working",   "accepted": false, "note": "You left this one blank; 'avoid' is followed by -ing." }
    ]
  }]
}
```

- `blanks`: one entry per blank in prompt order for a `fill_in_blank` item
  (one entry when it has one blank); **one entry for every other item**
  (`error_correction`, `sentence_writing`), where `correctAnswer` is the
  corrected sentence and `note` the one-sentence reason. So the shape is
  uniform and the card renders one way.
- **No `userAnswer` per blank in the response.** The client already holds
  the learner's boxes (B8's `BlankAnswer` list, taken at Submit) and pairs
  them with `blanks[i]` by index; the model never has to split the
  assembled sentence back into boxes, and the request stays exactly what it
  is today (no new request field, so a 1.4.0 client against the old proxy
  never sends anything `validation.ts` rejects).
- `summary`: at most two sentences, the whole-item lesson; `note`: one
  sentence.

### 4.2 Proxy: prompt, schema, validation

The scoring schema gains `summary` (string) and `blanks` (array of
`{index, correctAnswer, accepted, note}`), both **required in the schema**
(structured outputs guarantee presence; the client still treats them as
optional). The prompt gets a paragraph: one entry per blank in order, the
correct form for that blank alone, `accepted` true for a right or
defensible answer, false for a wrong or empty box, the note one sentence,
the summary two at most, and `isCorrect` true only when every blank is
accepted. The proxy then checks, per item, with the request in hand:

| Check | On failure |
|---|---|
| `fill_in_blank`: `blanks.length` equals the number of `_{2,}` runs in the item's prompt (0 blanks → 1 entry); other types: exactly 1 entry; indexes 0 … n − 1 once each | the item's `blanks` and `summary` are **removed** from the response (the client renders today's paragraph); counted in the usage log as `structured_dropped` |
| `isCorrect` disagrees with `blanks.every(accepted)` | `isCorrect` is **set to** the blanks' value (the blanks are the finer judgment; this is the same rule the client applies) and the item is counted as `verdict_reconciled` |
| a note over 40 words or a summary with more than two sentences | passed through (length is measured, §3.2, not enforced; the client's `FeedbackText` handles long text) |

The response stays byte-identical in its six existing fields, so a 1.3.0
client reads it as before (extra keys are ignored by `ItemFeedback.fromJson`).

### 4.3 Client model and parser (additive rule)

```dart
class BlankFeedback { final int index; final String correctAnswer; final bool accepted; final String note; }
class ItemFeedback { …today's fields…; final String? summary; final List<BlankFeedback>? blanks; }
```

`ItemFeedback.fromJson`: `summary` is `_optionalText`; `blanks` is read
only when it is a list whose every entry has the four fields with the
right types and whose indexes are exactly 0 … n − 1; anything else → `null`
(old proxy, old stored record, malformed output). **B8 guard combination:**
with `hasUnfilledBlank` and a client-side `userBlanks` list of the same
length as `blanks`, every entry whose box is empty gets `accepted = false`
(the box is visibly empty; the model may have scored it from context), then
`isCorrect = blanks.every(accepted)`. Without `blanks`, today's rule
(`!hasUnfilledBlank && json.isCorrect`). The guard stays a pure function
and its tests gain the structured cases. `ScoringResult` is unchanged.

### 4.4 `MistakeBreakdown` on the structured shape

- With `blanks` and B8's `userBlanks` of the same length (two or more
  blanks): each `_BlankRows` row becomes **bar | the learner's text (or "—"
  / "Left blank") | → | the correct form**, the arrow and correct form in
  `onSurfaceVariant` on an accepted row and in the "Corrected" green on a
  rejected one; an accepted row gets a small check; the row's `note` under
  it in `bodySmall`. VoiceOver: "Blank 2: you wrote 'hold', correct 'holding', not accepted: …".
- With one `blanks` entry (single box or a blank-less item): the two boxes
  as today, the entry's `note` under them instead of the paragraph.
- **The B10 diff is not run on a structured record** (both boxes plain:
  the rows already say what changed; painting the full corrected sentence
  would repeat it). Old records and records from the old proxy keep the
  diff and the paragraph — the fallback renderer stays as it is.
- Under the boxes: `summary` through `FeedbackText` (chips still apply).
  B9's formatter is then exercised only by old records and by the Daily
  Test's composed texts.
- The Daily Test result cards are unaffected (deterministic grading, no
  scorer).

### 4.5 Storage

`error_entries.feedback_json TEXT`, nullable, **schema v25** via
`_addColumnIfMissing` (the B8 pattern, `user_blanks` as the model): a JSON
object `{"summary": …, "blanks": [...]}` written only for structured
records; null for every old row. `explanation` keeps today's text, so
Review's "Saved feedback" panel and `WeakSpot.latestExplanation` need no
query change. **Open (§5):** whether those two show the summary when a
record has one.

### 4.6 Tests

Proxy: the schema and prompt pins updated; the count check per item type
(0, 1, 3 blanks; `sentence_writing`), the index rule, the drop path, the
reconciliation rule, the usage-log counters as fixed fields; a 1.3.0-shaped
reading of the response (the six fields unchanged). Client: `fromJson` on
the old shape, the new shape, a malformed `blanks` (wrong length, missing
field, bad index) → null; the guard with an empty box over a model
`accepted: true`; `MistakeBreakdown` rows with the correct form and notes
in both themes, VoiceOver labels, the diff absent on a structured record
and present on an old one; migration v24 → v25 (old row null, new row
round-trips, replay, fresh install); the three schema-version assertions
bumped.

## 5. Risks and open questions (one option each; **owner's decision** marked)

1. **`explanation` vs `summary` on 1.3.0 clients.** If the D11 prompt makes
   `explanation` the two-sentence summary, 1.3.0 users lose the long
   feedback on multi-blank items; if it keeps today's paragraph *and* adds
   `summary` and `notes`, output grows ≈ 60 % and the paragraph duplicates
   the notes. **Option:** keep `explanation` as today's full text for the
   live clients until 1.4.0 has most users, add `summary` + `blanks`; revisit
   when the old route goes. **Owner's decision.**
2. **Writing a published set twice** (§1.3) ends the "write-once" rule. It
   is an additive patch checked before the write, but the rule and one test
   change. **Option:** accept, with the patch check and a `checkedAt`
   stamp; the alternative is the P7 pending pipeline, which changes
   publishing. **Owner's decision.**
3. **The agreement gate's second call** (§1.4): ≈ $1 a month and one more
   model in production, for precision that cannot be known until §3.1
   runs. **Option:** build both paths (agreement, or single Opus + review)
   behind one constant, decide after the measurement. **Owner's decision
   after the report.**
4. **A checker finding that cannot be repaired** (`wrong_rule`, an original
   that is not wrong) on a set already published: today nothing happens
   until the owner's weekly look. **Option:** `review:{date}` only, no
   automatic pull (a false reject would empty a date for everyone).
   Confirm. **Owner's decision.**
5. **Prompt v3's extra sentence** (reported-speech time frame, the owner's
   2026-10-04 note): a second change inside the same prompt version
   confounds the v2/v3 comparison. **Option:** include it (the measurement
   is a regression check, not an attribution study) — or defer it to a
   v4 with its own run. **Owner's decision.**
6. **Folding changes length**, so the keyboard note's character pairing
   must be rewritten (§2.2) and the Daily Test's note wording with it.
   **Option:** list the non-plain characters typed, no pairing. Routine.
7. **The legacy prompt** (`DAILY_TEST_SYSTEM_PROMPT`) keeps "Turkish". It
   serves nobody and is pinned. **Option:** leave it until the route is
   removed in Phase 3. Confirm. **Owner's decision.**
8. **Scoring effort for the generator** (D4): the practice generator is
   measured at `low` only (§3.3). **Option:** add `medium` for G-D if its
   labels are worse than G-B's; ≈ $0.1. Routine.
9. **Owner labelling time** (≈ 2 h) is the real cost of the run, not the
   dollars. **Option:** S-live can be dropped (P14's gate then rests on the
   35 pool questions, 10 of them with corrections). **Owner's decision.**
10. **Cap and key.** **Option:** $40 measured-spend cap, a separate API key
    for the run, revoked after. **Owner's decision (approval).**
11. **Deploy-day edge cache.** Today's set may be served without its
    alternatives for up to an hour after the first annotation. **Option:**
    accept; the deploy happens on a day the owner chooses, outside peak
    hours. Routine.
12. **The 1.3.0 clients receive D3's scorer.** Their feedback changes
    wording (keyboard note, language-neutral tone) and, with D11, gains
    unknown fields. Both are within what the client already tolerates;
    nothing to decide, recorded so the live change is not a surprise.
13. **Request-shape risk for 1.4.0 against the old proxy:** none, by
    design (§4.1): the client sends nothing new. If a later batch wants to
    send per-box answers, the proxy's allow-list must deploy first.
14. **Where the client half of the folding sits among the 1.4.0 batches:**
    **Option:** with B3's translation infrastructure, since the fixture
    and the per-language examples are written then; before B5's
    translations. **Owner's decision.**
