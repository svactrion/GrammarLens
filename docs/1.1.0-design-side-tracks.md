# 1.1.0 design side tracks

**Status: defined 2026-09-26, updated 2026-09-27. Nothing here is implemented.** This file records
owner decisions for the 1.1.0 side work (launch screen, monthly themes, trail
and scene, Home title, avatars, measurement). No code has been written for any
of it. Work starts only after the `1.1.0` → `main` merge, with Batch 0 (a
read-only check) first.

Written on branch `1.1.0-design`. The main 1.1.0 work, the shared Daily Test,
is in [`1.1.0-shared-daily-test.md`](1.1.0-shared-daily-test.md) and is not
changed by this file.

**How to read claims about the current code.** This file was written from the
docs, without reading `lib/`. Every statement about how the app works today is
marked **(to be verified in Batch 0)** unless it only repeats an existing
record, in which case the record is named. Batch 0 either confirms each one or
corrects this file before any code is written.

**Batch 0 is done** (report:
[`1.1.0-design-batch0-report.md`](1.1.0-design-batch0-report.md), 2026-09-27).
The owner's decisions on its findings are in "Decisions after Batch 0" below;
where one of them changes an earlier section, that section says so and names
the decision. Other "(to be verified in Batch 0)" marks are answered in the
report and left as written here.

## Decisions after Batch 0

Owner, 2026-09-27. Each decision names the report's conflict (C1–C14) or
finding it answers.

1. **Theme record: a new `climb_month_themes` table** (schema v22 → v23).
   **No backfill:** a month with no row counts as Green Slope.
   - *Evidence:* no per-month record exists while a month is running;
     `monthly_medal_results` is written only after the month ends, so there
     is nothing to write the theme into (C1, item 6).
   - *Why:* a new table, added with the existing idempotent migration pattern,
     touches no existing row and is ignored by a 1.0 build after a downgrade.
     A month without a row resolving to Green Slope is exactly what 1.0 users
     saw, so nothing needs to be filled in for the past (recommendation c).
2. **The rotation follows a global calendar:** the same month has the same
   theme for everyone.
   - *Evidence:* recommendation c (under C1).
   - *Why:* a rotation that turns per user (for example, every user starting
     on Green Slope) would make it impossible to separate a theme's effect
     from which month of use the user is in. Storing the theme exists for
     that measurement.
   - Anchor (owner, 2026-09-27): October 2026 = Green Slope; see "The four
     themes and the rotation".
3. **Dark mode — this decision CHANGED.** Every theme has a **light and a
   dark palette.** Green Slope's existing dark palette (then `lib/theme.dart`,
   `ClimbPalette`; since Batch 2 `lib/models/climb_theme.dart`) is the model and is kept as it is. Layers drawn in code
   paint from both palettes. **External WebP layers are the same in both
   modes**, and the named B-polish exception now applies **only to them**.
   - *Replaces:* "the scene is the same in light and dark mode", with the
     exception covering the whole scene.
   - *Evidence:* `ClimbPalette.of(brightness)` already returns a separate
     dark palette (C2, item 4). The old decision would also have changed
     Green Slope for every 1.0 user in dark mode, which contradicted "Batch 2:
     no visible change".
   - *Why:* the old decision was made to save cost (four themes × two modes
     doubles the work); the report shows the dark palette mechanism is already
     in the code, so a second palette per theme is a data entry, not new
     infrastructure.
4. **The trail is already a serpentine; Batch 3 improves the existing
   geometry.** Steps become **evenly spaced along the trail.**
   - *Evidence:* 4 legs in 28-day months, 5 legs in 29–31-day months already
     (C3); today the spacing per step ranges from 22.0 to 39.6 scene units
     (C4, item 2).
   - *Why:* even spacing moves every step on screen, but 1.0 is still in App
     Store review, so in practice no user sees their steps move.
5. **The trail's end and the summit are one point:** the summit layer sits on
   the trail's real end point.
   - *Evidence:* today the trail ends at (160, 120) while the peak and flag
     are at (162, 56), 64 units higher; the pawn never reaches the flag (C5,
     item 2).
   - *Why:* "the last day lands on the summit" is only true if the summit is
     where the last step is.
6. **Stop markers** (today's campfire, tent, cabin and lookout at days 7, 14,
   21 and 28) **stay shared across the four themes**, take their colors from
   the theme's palette, and **count inside the 4–6-object budget.**
   - *Evidence:* the four markers are already code-drawn from palette colors
     and are in the VoiceOver label; with 4–6 new environment items they would
     exceed the budget (C12, item 3, recommendation a).
   - *Why:* they mark days, which is what the trail counts, so they do not
     have the medal camps' points-vs-days problem; keeping them needs no new
     art; counting them keeps the scene as sparse as decided. So each theme
     adds at most two environment items.
7. **No separate Home title row:** the existing header "Monthly Climb ·
   [month]" becomes **"Mountain of Learning · [month]"**.
   - *Evidence:* a header already sits above the mountain and already wraps
     to two rows at the default text size; at 320 × 568 only 79 pt of the
     mountain is above the fold, and a ~40 pt title row would cut that to
     ~39 pt (C6, C7, item 13).
   - *Why:* vertical space on a small screen.
8. **[Q] is read from one source.** The medal maximum's `× 10` becomes
   `questionCount × 2` (the value stays the same, so rule v1 does not
   change), and Home's "5-question" copy reads the same source. Done as **a
   separate, small commit.**
   - *Evidence:* the value 5 lives in five places; the medal maximum and the
     Home copy do not follow `DailyTestService.questionCount` (C8, item 9).
   - *Why:* the score bar and the card's goal line read [Q] from the code; if
     the medal maximum and the copy kept their own 5, a change to [Q] would
     make them disagree silently. A separate commit keeps a rule-adjacent
     change out of the visual batches.
   - Not covered: the proxy's shared-set count and the bundled Day-0 set
     (outside the app's single source).
9. **The month transition card is also checked on return from the
   background** and is **shown once per month.** The card does **not read
   last month's medal until the launch-time month finalization has
   finished.**
   - *Evidence:* Home reloads the month on resume, so a new month can begin
     without a cold start (C14, item 14). `finalizePastMedalMonths` runs
     asynchronously at launch while Home loads, so last month's row may not
     exist yet when the card would read it (C13, item 15). A per-month
     `one_time_flags` key fits and is race-safe (item 15).
   - *Why:* checking only on cold start would miss users who keep the app in
     the background across the month change; reading before finalization
     could show case (b) to a user who earned a medal.
10. **Launch screen: `runApp` runs immediately** and shows the launch
    animation; **Firebase and RevenueCat initialization run in parallel**;
    Home opens **when both the animation and the initialization have
    finished.** The static launch screen and the animation **follow the
    system appearance**; Home follows the app's theme; the change between them
    is **a fade**.
    - *Evidence:* both initializations are awaited before `runApp` today, so
      no Flutter frame can appear during them (C9, item 16). The storyboard
      can only follow the system appearance (C10, item 16).
    - *Why:* the animation can only overlap launch work if `runApp` comes
      first. Letting the animation follow the system appearance keeps it
      identical to the static screen for every user; the fade covers the one
      place where the app's own theme can differ.
11. **Added to the Batch 0 checklist:** iOS's minimum supported version, and
    from it the smallest supported screen.
    - *Why:* the report measured down to 320 × 568; whether that size (and
      so the 79 pt figure behind decision 7) still matters depends on which
      devices the minimum iOS version supports.

## Decisions after Batch 3a

Owner, 2026-09-30, on the trail study
([`design/batch3a/report.md`](design/batch3a/report.md)). Batch 3b
(measure, then build) works from these. Where one of them changes an earlier
section, that section says so and names the decision.

- **D1. Trail: candidate (b) "Wide S".** Its first leg is made steeper.
  - **Acceptance criterion:** the avatar visibly rises over the first 4
    steps.
  - **How much steeper is not left open:** the amount is approved on
    measured renders; after approval the curve is frozen.
  - *Evidence:* (b) is the only candidate that beats today on every overlap
    measure (legs 77.8 pt apart, the resting avatar covers another part of
    the trail on 0–1 days, turn radii 89–109 units). Its weak point is the
    flattest first leg (−33°), where neighbouring steps are 0.6 pt apart in
    31-day months (report §3, §5).
  - *Why a measured, frozen amount:* the step table (D3) and every later
    batch are built on this curve; a curve that keeps changing would
    invalidate them each time.
- **D2. Day-28 rule: a stop marker that falls within the month's last 2
  steps is not drawn; the summit takes its place.**
  - Precisely: the marker at day *d* is drawn only if `days − d > 2`.
  - Result: in a 28-day month the day-28 marker merges with the summit; in
    29- and 30-day months it is hidden; in a 31-day month it is shown.
  - **The rule is by step, not by screen size:** the same month shows the
    same markers on every device.
  - *Evidence:* no candidate has a clear spot for the day-28 marker in
    28/29-day months; near the summit the narrow top leaves no room that the
    summit does not take (report §4).
  - *Why:* at the summit's distance, a marker competes with the summit for
    the same few units of space and says less than the summit does.
  - **Note for Batch 5:** a hidden marker never takes a medal or reward with
    it. Anything later tied to a marker passes to the summit.
- **D3. Stop coordinates: a fixed table per month length (28–31).**
  - The table is **not written by hand**; a script generates it from the
    frozen curve. A test regenerates the table from the curve and compares;
    if the curve changes, the test fails.
  - Coordinates are stored **normalized (0–1) in mountain space**, not in
    screen coordinates.
  - **The camera is a separate layer**, so a change of framing does not
    invalidate the table.
  - *Why:* a generated table cannot drift from the curve unnoticed, and a
    normalized table is independent of card width and framing, both of
    which Batch 3b and later batches may still change (D5).
- **D4. Avatar facing: no avatar is mirrored, and no facing data is
  added.** *(Changes "Trail and scene": "the avatar faces the direction it
  walks".)*
  - The side-on avatars (snail, bee, turtle, hedgehog) will face against the
    walking direction on some legs. This is **accepted knowingly**.
  - *Evidence:* mirroring only shows on 4 of the 12 avatars, and they do
    not all face the same way, so correct mirroring needs a facing per
    avatar (report §4).
  - *Why:* few avatars are side-on, and a per-avatar facing is extra
    complexity that is not worth it.
  - Batch 8's 4 new avatars are also added without facing data.
- **D5. Mountain framing.**
  - **Problem:** in today's close framing the mountain does not read. At
    first glance the user sees only the avatar and the trail; the rest looks
    like a flat color. That contradicts the mountain metaphor.
  - **Root cause:** there is no ridge or summit edge in the frame.
  - **1.1.0 scope:**
    - (a) **Batch 3b:** a measured comparison of the current framing with a
      wider one;
    - (b) **Batch 4a/4b:** a layer slot for a ridge/summit silhouette in the
      background;
    - (c) **Batch 6:** once a month, after the month transition card, a zoom
      from the whole mountain to the avatar's position.
  - **Rejected:** a zoom on every open. *Why:* a repeated wait, and it
    delays reaching the Daily Test.
  - **Parked for 1.2:** a "see the mountain" button, or a tappable card.
- **D6. The 14 pt shift at 320 pt** (report §0: at 320 × 568 Medium the
  mountain starts 14 pt lower than Batch 0 measured) **is fixed in this
  batch**: diagnosis first, the fix after approval, with a regression test.
  - If the shift turns out to be independent of the new mountain code, it is
    **not fixed here**; it is reported as a separate item.
  - *Why:* at 320 × 568 only 65 pt of the mountain shows above the fold;
    14 pt is a fifth of it. Fixing a cause that is not part of this work
    here would mix an unrelated change into a design batch.

## Rules

- **No API cost.** Nothing that increases Anthropic API cost is in scope. All
  side work is client-side. *Why:* the main point of 1.1.0 is making Daily
  Test cost independent of the number of users; side work must not undo that.
- **Side work never holds back the shared Daily Test release.** Any part that
  is not ready moves to the next version. *Why:* the shared Daily Test is the
  release's reason to exist; the side work is optional polish.
  **Overridden for 1.1.0 (owner, 2026-09-30, `build-log.md` "1.1.0 ships
  with the full scope"):** 1.1.0 does not ship before the theme package
  (Batches 4–6) is done; Batch 7 may still move.
- **The B-polish visual system is kept.** The one exception (external WebP
  layers look the same in light and dark mode; narrowed by Batch 0 decision
  3) is written out with its reason under "Monthly themes → Dark mode".
  *Why:* B-polish was device-reviewed; changing it for side work would reopen
  settled decisions.

## Launch screen

Decided 2026-09-26 (also recorded in `build-log.md`, 2026-09-26, "first
deploy" entry).

- Logo and the "GrammarLens" wordmark. The logo settles into place with a
  slight scale-up; the wordmark fades in. At most ~1.2 s, running in parallel
  with launch work (never adding wait time).
- *(Batch 0 decision 10.)* `runApp` runs immediately and shows the
  animation while Firebase and RevenueCat initialize; Home opens when both
  have finished. The animation follows the system appearance like the static
  screen; Home follows the app's theme, and the change between them is a
  fade. Launch work durations are not measured yet (report item 16), so
  whether the animation ever outlasts launch work is checked on a device.
- Plays on **cold start only**; not when returning from the background.
  *Why:* a repeated animation on every resume is friction, not branding.
- The iOS static launch screen is **identical to the animation's first
  frame**, so there is no visible jump between the native screen and Flutter.
  With **Reduce Motion** on, the static logo is shown.
- Idea for a later version: the wordmark coming into focus through a lens
  transition.
- **Batch 1 built 2026-09-27** (`build-log.md`, 2026-09-27, "Batch 1:
  launch screen" and "Batch 1 follow-up"). With Reduce Motion the logo stays
  at its first-frame scale (0.92) so there is no jump from the static
  screen.
- **Duration (owner, 2026-09-27, after seeing it on a device): 1.2 s
  stays.** Logo 0.92 → 1.0 over 0–600 ms (easeOutCubic), wordmark fade
  300–800 ms, hold to 1000 ms, then a 200 ms fade to the app. *Cost:* launch
  work takes 11–13 ms on the phone (profile), so every cold start gets about
  1.2 s longer. *Ready alternative* if "the launch is slow" feedback comes:
  logo 0–350 ms, wordmark 150–500 ms, last frame to 650 ms, 150 ms fade
  (about 0.8 s).
- **Size (owner, 2026-09-27, after the device check): asked for 40 %
  larger; 25 % applied.** At 1.4 the wordmark is 303.4 pt wide and leaves
  8 pt per side on a 320 pt screen; 1.25 is the largest scale that keeps
  24 pt (270.9 pt wide, 24.5 pt per side). Logo box 125 pt, gap 20 pt,
  wordmark 42.5 pt (58 pt tall); the logo's center is 39 pt above the
  screen's center, so logo, gap and wordmark (203 pt) are centered.
- **First install:** Welcome's entrance waits until the splash's fade has
  finished (it used to start, and partly play, under the splash).

## Monthly themes

### Scope

Visual and identity only: palette, background layers, theme-specific
environment items, a theme-specific summit, the theme name and a themed medal.
**Questions and mechanics do not change.** *Why:* content tied to themes would
need its own generation work (API cost) and its own review; see "Deferred to a
later version".

### The four themes and the rotation

The theme changes every month and rotates in this order:

1. **Green Slope** — the current green mountain; default and fallback.
2. **Ember Peak** — volcanic.
3. **Glacier Peak** — glacier.
4. **Red Canyon** — sand / terracotta.

**Rotation anchor (owner, 2026-09-27):** October 2026 = Green Slope, then
Ember Peak (November), Glacier Peak (December), Red Canyon (January), and so
on. It follows the global calendar (Batch 0 decision 2) and is a constant in
the code, **not tied to the release date**. *Why:* a fixed anchor gives every
month one known theme regardless of when 1.1.0 ships or when a user installs.

The default theme keeps its current name, **Green Slope**, as in the existing
docs (`prd-gamification.md`, `gamification-handoff.md`). *Why (owner,
2026-09-27; replaces the new name in the first version of this file):*
keeping the existing name avoids a possible migration and stays consistent
with 1.0. Draft id: `green_slope`. Whether "Green Slope" already exists as an
id or string in the code or stored data is to be verified in Batch 0.

### Theme id stored with the month

- When a month starts, the theme id is **written into that month's record**.
  Past months are always shown with their stored theme; the rotation formula is
  used only for months that have not started yet.
- *Why:* adding a theme later must not shift which theme past months had; and
  measurement must be able to separate a "month 3 drop" from "that month's
  theme".
- A month with no stored or resolvable theme falls back silently to Green
  Slope.
- *(Batch 0 decisions 1 and 2.)* There is no monthly record to write into
  while a month runs, so the theme goes into a new `climb_month_themes` table
  (schema v22 → v23), with no backfill: a month without a row is Green Slope.
  The rotation formula is a global calendar, the same theme for everyone in
  a given month, anchored at October 2026 = Green Slope.

### Themes are data, not code

Each theme is defined as data: id, name, one-line tagline, a light and a
dark palette (Batch 0 decision 3), layer slots, summit, emblem. *Why:* a new theme should be a data entry plus assets,
not new widget code; the first added theme after these four is the real test of
that (see "Deferred").

### Shared geometry

Trail geometry and step positions are **the same in all four themes**. The
summit is a theme-specific layer that sits on the trail's shared end point
(Batch 0 decision 5: today's peak and flag are 64 units above the trail's
end; they become one point). The stop markers are shared too (decision 6).
*Why:* one geometry to test for 28/29/30/31-day months and text sizes, instead
of four.

### Theme tables

| Theme | Tone | Environment items | Summit | Emblem |
|---|---|---|---|---|
| Green Slope | Green, warm sky | Pine, shrub, wildflower | Grassy hilltop with a flag | Pine |
| Ember Peak | Dark basalt with an orange lava glow | Smoke, charred rock, lava crack | Smoking crater | Flame / crater |
| Glacier Peak | White and glacier blue | Ice block, icicle, crevasse | A pointed crown of ice | Ice crystal |
| Red Canyon | Sand and terracotta | Cactus, rock arch, dry brush | Flat-topped plateau (mesa) | Rock arch |

Theme-specific constraints:

- **Ember Peak:** the lava red must not be close to the destructive color
  (`#DC3232`). *Why:* red already means "delete / error" in the app.
- **Glacier Peak:** no season cues: no falling snow, no winter clothing. High
  altitude and a bright sky instead. *Why:* themes rotate by month, not by
  season, and users are in both hemispheres; a "winter" theme in July would
  look wrong.

### Taglines (use word for word)

- Green Slope: "Green slopes and an easy trail to find your rhythm."
- Ember Peak: "Smoke on the ridge, warm rock underfoot."
- Glacier Peak: "Thin air, bright ice, and a view worth the climb."
- Red Canyon: "Sun-baked rock and a mesa waiting at the top."

### Medal

- One shared body in three metals (Bronze / Silver / Gold), with a
  theme-specific emblem and a month/year label on top (for example
  "October 2026"). **7 assets in total** (3 bodies + 4 emblems), combined as
  layers.
- The body design may later be replaced with an external design; the emblems
  stay the same. *Why:* layers keep the asset count linear and let the body
  change without touching the themes.
- The **Welcome badge stays unthemed.** *Why:* it belongs to the user's first
  day, not to a month.

### Dark mode

**Changed 2026-09-27 (Batch 0 decision 3).** The earlier decision ("the scene
is the same in light and dark mode", for the whole scene, to save art and
review work) is replaced:

- **Every theme has a light and a dark palette.** Green Slope's existing
  dark palette (`ClimbThemes.greenSlope` in `lib/models/climb_theme.dart`,
  moved there from `lib/theme.dart` in Batch 2) is the model and is kept
  unchanged, so Green Slope looks the same as in 1.0 in both modes.
- **Layers drawn in code** paint from the palette of the current mode.
- **External WebP layers** are the same in both modes. They are the only
  **named exception** to the B-polish rule "no brand color as a surface in
  dark mode / neutral dark mode"; they count as illustrations, like the
  avatars.
- *Why:* the old decision was a cost decision; Batch 0 showed the dark
  palette mechanism already exists in the code (report C2, item 4).
- All four themes are checked on a device in dark mode, including any WebP
  layer against the dark palette around it.
- The exception is written into `build-log.md` and `design-audit.md` at the
  end of the work (see "Implementation order → Last"), not now.

### Production of the artwork

- **Default: drawn in code**, as vectors painted from the theme palette.
- Each layer slot can be replaced by a **WebP file** if the theme data names
  one. If the file is missing or broken, that slot falls back to the code
  drawing. *Why:* the scene never breaks because of an asset, and art can be
  upgraded slot by slot.
- For externally produced images, anchor points and the trail's safe zone are
  defined (values come from Batch 0; see the template in the appendix).
- If an external tool is used: which tool and on which date is written into
  `build-log.md`; its commercial-use terms are checked; it is added to Credits
  if required.
- Files go through the same pipeline as the avatars (PNG → WebP, resizing).

### Month transition card

A card shown **once**, on the first open of a new month, on Home; it can be
closed. *(Batch 0 decision 9: "first open" includes a return from the
background, not only a cold start; the card is shown once per month, and it
does not read last month's medal until the launch-time month finalization
has finished.)* Showing it once uses the existing `one_time_flags` table (schema v22,
recorded in `build-log.md`, 2026-09-22; its exact use for this card is to be
verified in Batch 0).

Three cases:

- **(a) A medal was earned last month.** Top: the themed medal and the month
  label (for example "October 2026 · Silver"). Below: "You reached Silver on
  Ember Peak." Then "November: Glacier Peak.", the new theme's tagline, and
  "Go for Gold this month." If Gold was earned, that last line is instead
  "Can you win Gold again?" *Why (owner, 2026-09-27; replaces "Can you reach
  the summit again?"):* the summit is the trail's last day, Gold is a score;
  they are not the same thing.
- **(b) No medal was earned.** Top: "New month, fresh start." Below: the
  tagline and the goal line:

  "Answer all [Q] questions on [N] days to earn your first [Theme] medal.
  Correct answers get you there sooner."

  - [Q] is the number of Daily Test questions per day.
  - [N] = the Bronze threshold ÷ the lowest score of a fully answered day
    ([Q] × 1, every answer wrong), rounded up.
  - Both are **read from the code, never hard-coded.**
  - **Fallback:** if [N] is greater than the days left in the month, counting
    the day the card is shown, the goal line is replaced by "Climb this month
    to earn your first [Theme] medal."
  - Missed days are never mentioned. *Why:* the card is an invitation, not a
    report of failure. *Why this goal line (owner, 2026-09-27; replaces "Climb
    [X] days"):* a medal's day count is a range that depends on accuracy; [N]
    is the one number that is always true (a user who answers every question
    on [N] days reaches Bronze even if every answer is wrong), and the second
    sentence says accuracy shortens it.
  - Worked example from the docs, not the code (to be verified in Batch 0):
    with [Q] = 5 and rule v1, a 30-day month has a maximum of 300 points,
    Bronze = 75, [N] = ceil(75 ÷ 5) = 15; a 31-day month has Bronze =
    ceil(77.5) = 78, [N] = 16.
  - Whether "answer all [Q] questions" matches how a blank (0-point) answer
    can happen is to be verified in Batch 0 (see the checklist).
- **(c) The user's first month.** No card; the Welcome flow greets them.

One button: **"Start climbing"**. If today's Daily Test is not done, it opens
the test; if it is done, it closes the card.

**Open point — resolved 2026-09-27.** The first version of this file found
that, per medal rule v1 (`gamification-handoff.md`, `roadmap.md`), medals are
**score-based** (correct +2, wrong +1, skipped +0; the monthly maximum is
`daysInMonth × 10`; Bronze/Silver/Gold are ceil(25/50/75 %) of that maximum;
no minimum-day gate), while the "[X] days" line and the medal camps assumed a
threshold in days. Resolved by the owner: the medal camps are replaced by a
score bar ("Trail and scene"), and case (b) uses the [N] goal line above. The
rule itself is still to be confirmed against the code in Batch 0.

## Trail and scene

- **Serpentine (zigzag) trail, 4–5 legs.** *(Batch 0 decision 4: this is
  already the case today; Batch 3 improves the existing geometry.)*
- Step positions are spaced **evenly along the trail** according to the
  number of days in the month; the **last day of the month always lands on the
  summit**. *(Batch 0 decisions 4 and 5: today's spacing is uneven and the
  summit sits above the trail's end; both change in Batch 3.)* Steps count **participation days**, not calendar days (the current
  mechanic does not change).
- **Score bar instead of medal camps** (owner, 2026-09-27). The trail keeps
  showing days. On the mountain card, **under the trail**, a thin score bar
  with Bronze, Silver and Gold marks; the marks are computed from the
  thresholds in the code. *Why:* medals are based on points, the trail counts
  participation days; a medal's day count is a range that depends on
  accuracy, so a camp at a fixed day position could mislead the user. *(Batch
  0: the Daily Test card sits above the mountain and cannot be pushed down,
  report C7; the Home title no longer adds a row, decision 7.)*
- The avatar **faces the direction it walks** at each turn (horizontal
  mirroring) and **hops to a new step along a small arc**; unchanged by the
  score bar decision. With Reduce Motion on, it moves without animation.
  *(Batch 3a decision D4: the mirroring part is dropped; no avatar is
  mirrored. The hop stays.)*
- **Idle sway animation: rejected.** *Why:* battery use, distraction, and the
  risk of breaking `pumpAndSettle` in tests (an endless animation never
  settles).
- **Spiral trail: rejected.** *Why:* steps that fall on the far side of the
