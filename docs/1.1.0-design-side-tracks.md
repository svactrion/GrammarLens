# 1.1.0 design side tracks

**Status: defined 2026-09-26. Nothing here is implemented.** This file records
owner decisions for the 1.1.0 side work (launch screen, monthly themes, trail
and scene, Home title, avatars, measurement). No code has been written for any
of it. Work starts only after the `1.1.0` → `main` merge, with Batch 0 (a
read-only check) first.

Written on branch `1.1.0-design`. The main 1.1.0 work, the shared Daily Test,
is in [`1.1.0-shared-daily-test.md`](1.1.0-shared-daily-test.md) and is not
changed by this file.

**How to read claims about the current code.** This file was written from the
docs, without reading `lib/`. Every statement about how the app works today is
marked **(to be verified in Batch 0)** unless it only repeats an existing
record, in which case the record is named. Batch 0 either confirms each one or
corrects this file before any code is written.

---

## Rules

- **No API cost.** Nothing that increases Anthropic API cost is in scope. All
  side work is client-side. *Why:* the main point of 1.1.0 is making Daily
  Test cost independent of the number of users; side work must not undo that.
- **Side work never holds back the shared Daily Test release.** Any part that
  is not ready moves to the next version. *Why:* the shared Daily Test is the
  release's reason to exist; the side work is optional polish.
- **The B-polish visual system is kept.** The one exception (the scene looks
  the same in light and dark mode) is written out with its reason under
  "Monthly themes → Dark mode". *Why:* B-polish was device-reviewed; changing
  it for side work would reopen settled decisions.

## Launch screen

Decided 2026-09-26 (also recorded in `build-log.md`, 2026-09-26, "first
deploy" entry).

- Logo and the "GrammarLens" wordmark. The logo settles into place with a
  slight scale-up; the wordmark fades in. At most ~1.2 s, running in parallel
  with launch work (never adding wait time).
- Plays on **cold start only**; not when returning from the background.
  *Why:* a repeated animation on every resume is friction, not branding.
- The iOS static launch screen is **identical to the animation's first
  frame**, so there is no visible jump between the native screen and Flutter.
  With **Reduce Motion** on, the static logo is shown.
- Idea for a later version: the wordmark coming into focus through a lens
  transition.

## Monthly themes

### Scope

Visual and identity only: palette, background layers, theme-specific
environment items, a theme-specific summit, the theme name and a themed medal.
**Questions and mechanics do not change.** *Why:* content tied to themes would
need its own generation work (API cost) and its own review; see "Deferred to a
later version".

### The four themes and the rotation

The theme changes every month and rotates in this order:

1. **Greenway Peak** — the current green mountain; default and fallback.
2. **Ember Peak** — volcanic.
3. **Glacier Peak** — glacier.
4. **Red Canyon** — sand / terracotta.

Note: the existing docs call today's theme **Green Slope**
(`prd-gamification.md`, `gamification-handoff.md`). Greenway Peak is its new
display name. Whether "Green Slope" also exists as an id or string in the code
is to be verified in Batch 0.

### Theme id stored with the month

- When a month starts, the theme id is **written into that month's record**.
  Past months are always shown with their stored theme; the rotation formula is
  used only for months that have not started yet.
- *Why:* adding a theme later must not shift which theme past months had; and
  measurement must be able to separate a "month 3 drop" from "that month's
  theme".
- A month with no stored or resolvable theme falls back silently to Greenway
  Peak.
- Whether the monthly record already has a theme/mountain field, and what the
  migration looks like, is to be verified in Batch 0.

### Themes are data, not code

Each theme is defined as data: id, name, one-line tagline, palette, layer
slots, summit, emblem. *Why:* a new theme should be a data entry plus assets,
not new widget code; the first added theme after these four is the real test of
that (see "Deferred").

### Shared geometry

Trail geometry and step positions are **the same in all four themes**. The
summit is a theme-specific layer that sits on the trail's shared end point.
*Why:* one geometry to test for 28/29/30/31-day months and text sizes, instead
of four.

### Theme tables

| Theme | Tone | Environment items | Summit | Emblem |
|---|---|---|---|---|
| Greenway Peak | Green, warm sky | Pine, shrub, wildflower | Grassy hilltop with a flag | Pine |
| Ember Peak | Dark basalt with an orange lava glow | Smoke, charred rock, lava crack | Smoking crater | Flame / crater |
| Glacier Peak | White and glacier blue | Ice block, icicle, crevasse | A pointed crown of ice | Ice crystal |
| Red Canyon | Sand and terracotta | Cactus, rock arch, dry brush | Flat-topped plateau (mesa) | Rock arch |

Theme-specific constraints:

- **Ember Peak:** the lava red must not be close to the destructive color
  (`#DC3232`). *Why:* red already means "delete / error" in the app.
- **Glacier Peak:** no season cues: no falling snow, no winter clothing. High
  altitude and a bright sky instead. *Why:* themes rotate by month, not by
  season, and users are in both hemispheres; a "winter" theme in July would
  look wrong.

### Taglines (use word for word)

- Greenway Peak: "Green slopes and an easy trail to find your rhythm."
- Ember Peak: "Smoke on the ridge, warm rock underfoot."
- Glacier Peak: "Thin air, bright ice, and a view worth the climb."
- Red Canyon: "Sun-baked rock and a mesa waiting at the top."

### Medal

- One shared body in three metals (Bronze / Silver / Gold), with a
  theme-specific emblem and a month/year label on top (for example
  "October 2026"). **7 assets in total** (3 bodies + 4 emblems), combined as
  layers.
- The body design may later be replaced with an external design; the emblems
  stay the same. *Why:* layers keep the asset count linear and let the body
  change without touching the themes.
- The **Welcome badge stays unthemed.** *Why:* it belongs to the user's first
  day, not to a month.

### Dark mode

- The scene is **the same in light and dark mode**.
- This is a **named exception** to the B-polish rule "no brand color as a
  surface in dark mode / neutral dark mode". The scene counts as an
  illustration, like the avatars.
- *Why:* four themes × two modes doubles the art and review work; an
  illustration with its own sky reads fine on a dark app surface.
- All four themes will be checked on a device in dark mode. If one theme is
  too bright there, **only that theme** gets a dark palette.
- The earlier docs mention a Green Slope light/dark preview
  (`prd-gamification.md`). Whether today's scene has separate dark colors, and
  so whether this is a visible change for Greenway Peak, is to be verified in
  Batch 0.
- The exception is written into `build-log.md` and `design-audit.md` at the
  end of the work (see "Implementation order → Last"), not now.

### Production of the artwork

- **Default: drawn in code**, as vectors painted from the theme palette.
- Each layer slot can be replaced by a **WebP file** if the theme data names
  one. If the file is missing or broken, that slot falls back to the code
  drawing. *Why:* the scene never breaks because of an asset, and art can be
  upgraded slot by slot.
- For externally produced images, anchor points and the trail's safe zone are
  defined (values come from Batch 0; see the template in the appendix).
- If an external tool is used: which tool and on which date is written into
  `build-log.md`; its commercial-use terms are checked; it is added to Credits
  if required.
- Files go through the same pipeline as the avatars (PNG → WebP, resizing).

### Month transition card

A card shown **once**, on the first open of a new month, on Home; it can be
closed. Showing it once uses the existing `one_time_flags` table (schema v22,
recorded in `build-log.md`, 2026-09-22; its exact use for this card is to be
verified in Batch 0).

Three cases:

- **(a) A medal was earned last month.** Top: the themed medal and the month
  label (for example "October 2026 · Silver"). Below: "You reached Silver on
  Ember Peak." Then "November: Glacier Peak.", the new theme's tagline, and
  "Go for Gold this month." If Gold was earned, that last line is instead
  "Can you reach the summit again?"
- **(b) No medal was earned.** Top: "New month, fresh start." Below: the
  tagline and "Climb [X] days to earn your first Glacier Peak medal." [X] is
  **read from the Bronze threshold in the code, never hard-coded.** Missed days
  are never mentioned. *Why:* the card is an invitation, not a report of
  failure.
- **(c) The user's first month.** No card; the Welcome flow greets them.

One button: **"Start climbing"**. If today's Daily Test is not done, it opens
the test; if it is done, it closes the card.

**Open point (found while writing this file, from the docs, not the code):**
per medal rule v1 (`gamification-handoff.md`, `roadmap.md`), medals are
**score-based**: correct +2, wrong +1, skipped +0; the monthly maximum is
`daysInMonth × 10`; Bronze/Silver/Gold are ceil(25/50/75 %) of that maximum;
there is no minimum-day gate. So "the Bronze threshold" is a number of points,
not a number of days, and "[X] days" needs a stated conversion (for example the
minimum number of perfect days, which would understate what most users need).
To be verified in Batch 0 and decided by the owner before Batch 6. The same
applies to the medal camps on the trail (below).

## Trail and scene

- **Serpentine (zigzag) trail, 4–5 legs.**
- Step positions are spaced **evenly along the trail** according to the
  number of days in the month; the **last day of the month always lands on the
  summit**. Steps count **participation days**, not calendar days (the current
  mechanic does not change).
- **Medal camps:** markers on the trail at the steps that correspond to the
  Bronze, Silver and Gold thresholds. Thresholds are read from the code.
  See the open point above: thresholds are points, steps are days, so the
  mapping is to be verified in Batch 0 and decided before Batch 3.
- The avatar **faces the direction it walks** at each turn (horizontal
  mirroring) and **hops to a new step along a small arc**. With Reduce Motion
  on, it moves without animation.
- **Idle sway animation: rejected.** *Why:* battery use, distraction, and the
  risk of breaking `pumpAndSettle` in tests (an endless animation never
  settles).
- **"Walked path vs path ahead" styling: not chosen.** Readability is checked
  in the device test instead.
- **Environment items are sparse and still:** 4–6 objects in the whole scene,
  near ones large, far ones small. Nothing enters the trail's safe zone or the
  area around the camps.
- **One-time opening motion** (for example smoke drifting once on Ember Peak,
  ice glinting once on Glacier Peak):
  - plays once per cold start; does not repeat when switching tabs; does not
    play with Reduce Motion on;
  - order: if an avatar step is pending, that plays first and the
    environment motion is skipped for that open; the month transition card
    comes last, after the scene has stopped;
  - **this is the first part to move to the next version** if time runs
    short.
- How today's Home animations are ordered (step animation, Day-0 flow) is to
  be verified in Batch 0.

## Home title

A fixed title above the mountain card: **"Mountain of Learning"**, `titleMedium`
w700. To be checked on a device that the Daily Test card is not pushed below
the bottom of the screen. *Why:* the scene becomes the Home screen's main
element with the themes; a title names it without adding a control.

## Measurement

- A `theme_id` parameter is added to the existing Monthly Climb events. Which
  events exactly (candidates: `daily_test_completed`, `welcome_badge_earned`,
  `medal_month_finalized`) is decided in Batch 6; `profile_medals_viewed`
  covers several months and has no single theme.
- An event for the month transition card: card shown, and "Start climbing"
  tapped, each with the case (`a` / `b`) as a parameter.
- After the code is merged, the new parameters are registered in Firebase as
  custom dimensions. Added to [`analytics-plan.md`](analytics-plan.md) as
  "planned (1.1.0), not implemented".

## Appendix: external image tool template

To be used as written; the bracketed fields are filled in after Batch 0.

```
You are producing one illustration layer for a mobile app's monthly climbing scene.
APP CONTEXT: GrammarLens is an English-learning iOS app. The home screen shows a mountain trail; a small 3D-style cute animal avatar climbs one step per day. Each month uses one of four mountain themes. You are drawing a single LAYER of one theme. Layers are stacked in code, so every layer must follow the geometry rules exactly.
THEME: [THEME_NAME] — [ONE-LINE THEME DESCRIPTION]
LAYER: [sky | far background | environment item | summit | medal emblem]
PALETTE (only these colors plus tints/shades): [HEX LIST]
STYLE: flat, clean vector-like illustration; soft shapes, subtle gradients at most; no photorealism, no heavy texture, no outlines thicker than [N] px. Calm and friendly, suitable for 13+. Lower detail and saturation than the avatar so it never competes with it. Must look good on both a light and a near-black background: avoid large areas of pure white or pure black, keep main tones mid-range. No season cues: no falling snow, autumn leaves, holiday items or winter clothing.
GEOMETRY (hard rules): canvas [W] x [H] px, aspect [SCENE_ASPECT]. Sky layer: full-bleed, opaque, no objects. All other layers: transparent PNG. Trail safe zone: leave [SAFE_ZONE] completely empty. Summit: centered horizontally, base touching the bottom edge at [ANCHOR], max [W] x [H] px. Environment item: one isolated object, base on the bottom edge, max [W] x [H] px, no ground shadow outside the object. Medal emblem: centered symbol, transparent, [SIZE] px square, readable at 32 px, single tone that works on bronze, silver and gold.
NEVER INCLUDE: text, letters, numbers, logos, watermarks, signatures; people, animals or characters; real landmarks, brands or copyrighted characters; a strong error red (#DC3232-like) or strong success green as dominant tones.
OUTPUT: one image per request at the exact canvas size; file name [theme_id]_[layer]_[variant].png.
```
